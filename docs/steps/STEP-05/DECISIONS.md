# STEP 05 decisions

- D1 (05.1) Key hierarchy: `ENCRYPTION_KEY` is key version 1 and never changes (feature 3188). Secondary roots `ENCRYPTION_KEY_V2` and `ENCRYPTION_KEY_V3` support rotation (3189). A data key is HKDF-SHA256 of the root of its version, salted with the version, with `purpose|scope` as the info. Version, purpose and scope are also bound into the GCM additional data, so a payload cannot be replayed under another purpose, company or user. New data uses `ENCRYPTION_ACTIVE_KEY_VERSION`; old versions stay readable while their key is set. `rotateBatch` re-encrypts one jsonb column in batches and checks the old version in the update, so parallel runs are safe.
- D2 (05.1) The blind index always uses key version 1, so it never changes during a rotation. It is keyed (HMAC over the normalized value) and separated per field name.
- D3 (05.1) Reads of the purposes `processor-credentials`, `oauth-tokens` and `kyc` are written to `secret_access_log` (feature 3198). `files` and `pii` are not logged one by one because they are too frequent; the log failing never blocks the read, it is logged as an error.
- D4 (05.1) Features not built as code: KMS plug-in layer (3191) and the home-made key pair (3192) are future-ready only through the root-key function `rootKeys()` in `services/encryption/keys.ts`, which is the one place to replace; client-side zero-knowledge encryption (3186) is not built because the server must read files to validate and convert them. Backup encryption (3185) already exists in `scripts/backup.sh` (STEP 01).
- D5 (05.2) Office files with macros, embedded objects, ActiveX or remote templates are rejected, not repaired (features 3652 asks for "macro removal"): rewriting an Office package leaves the risk of an incomplete clean-up, and a refused file is easy for the user to fix by saving without macros. Legacy OLE formats (.doc, .xls) are refused for the same reason.
- D6 (05.2) PDF files are rebuilt page by page into a new document. Scripts, open actions, embedded files, form actions, annotations (including links) and metadata do not survive; the rebuilt file is scanned again and refused if any active name is left. Encrypted PDF files are refused.
- D7 (05.2) SVG files are sanitized (DOMPurify, no style, no href, no script, no foreignObject, no DOCTYPE or entities) and then rasterized to PNG; no vector markup is ever stored (feature 3647). The stored name and content type follow the final PNG.
- D8 (05.2) Allowed types: images (PNG, JPEG, GIF, WebP, SVG as PNG), PDF, CSV, DOCX, XLSX; KYC takes images and PDF only (5 MB), logos take images only. Size limits: images 5 MB, PDF/CSV/Office 10 MB, KYC 5 MB, SVG 2 MB, images at most 50 megapixels. The whole check stops after 30 seconds.
- D9 (05.2) The raw-input polyglot check looks for script text and foreign signatures in the head and tail, and for data after the end of the image or PDF. Images and PDF files are re-encoded afterwards, so anything hidden in the middle is dropped by the rebuild.
- D10 (05.2b) Quarantine keeps metadata only (name, size, hash, reason, uploader), never the bytes: a suspicious file is refused, not stored, and a review record plus a security event are written. Reasons that create a record: executable, polyglot, script content, macro, archive bomb or path, active PDF content, known-malware hash, scanner hit. `file_quarantine` is read by platform staff in the admin storage page (05.6).
- D11 (05.2b) Scanner hook: with `MALWARE_SCANNER_URL` set, every cleaned file is scanned through an HTTPS gateway (contract in `lib/storage/scanner.ts`: POST bytes, answer `{ infected, signature }`). A scanner error fails closed (503, nothing stored). Without the variable the scan status is `skipped`. The scan is synchronous (the file is small and capped), not a later job. Native clamd TCP is not spoken; the gateway keeps the serverless host free of raw sockets.
- D12 (05.2b) Chunked upload: 1 MB chunks held in `upload_chunks` (bytea) until the file is assembled, expire after 1 hour, only the owner of the session can add chunks, a repeated chunk replaces the earlier one, and the database function `kd_upload_begin_complete` lets exactly one request assemble the file. Feature 3290 (browser straight to Google Drive) is not built: the server must validate and encrypt every file first, so bytes never go from the browser to a provider. Presigned upload URLs (3291) are therefore the session endpoints, with a one hour life.
- D13 (05.2b) Quota: total storage per company from the entitlement `storage.quota_mb` and monthly upload volume from `storage.monthly_upload_mb` (defaults 1 GiB and 2 GiB in `config/storage.ts`). Upload and download rate-limit policies `upload` (30 a minute) and `download` (60 a minute) were added to `RATE_POLICIES` in `config/security.ts` (STEP 04 file).
- D14 (05.3) Providers only ever receive AES-256-GCM ciphertext. Key purpose is `kyc` for the KYC category and `files` for the rest; the scope is the company id (`platform` for platform files), so a file cannot be decrypted under another company. IV, tag and key version are stored in the file record; the ciphertext is the object. After decrypting, the SHA-256 of the bytes must equal the stored hash (integrity check, feature 3453).
- D15 (05.3) Supabase Storage: one private bucket (`kd-files`), object path `tenants/{company}/{category}/{file}.kdenc`. Google Drive: REST calls with the minimal scope `drive.file`, folders `tenants/{company}/{category}` created on first use and cached in `drive_connections.folder_cache`, retries with exponential backoff on 429, 5xx and Drive rate-limit answers, a 401 marks the link revoked. Platform files (no company) always use Supabase.
- D16 (05.3) Signed links (`/api/storage/download/{token}`): random token, only the hash is stored, 30 seconds to 1 hour life, at most 5 uses by default, default requires a signed-in person of the same company; links open to anyone exist only on request and never for KYC. The route is a plain handler because it answers with binary data, so it does by hand what the API wrapper does (correlation id, rate limit `download`, session and tenant check, error mapping). It supports single byte ranges and sends `nosniff`, `attachment` (inline only for images and PDF) and a sandboxing CSP. Per-tenant bandwidth throttling (3462) is the `download` rate limit only.
- D17 (05.3) Duplicates: a company keeps one live record per category and content hash; uploading the same bytes again returns the existing record and writes a `duplicate` access entry. Delete moves to a 30 day trash (restorable); the nightly retention job moves files past `retention_until` (invoices 10 years, KYC 7, exports 1, none for logos/attachments) to the trash and removes trash older than 30 days from the provider.
- D18 (05.3) Export PDFs get a footer mark (product, first 8 characters of the company id, date) when stored. CSV exports are not marked because a mark would corrupt re-import; image resizing, AVIF/WebP variants, PDF font subsetting and similar media optimization (features 3477-3490 except metadata stripping and watermark) are not part of this build.
- D19 (05.3) `put` is the single entry point for every stored file, including documents generated by other STEPs: they pass the same validation (PDFs are rebuilt, images re-encoded). Storage quota and monthly upload volume are checked there. The monthly counter is advanced before the provider write, so a failed write still counts toward the month.
- D20 (05.4) Provider chain per company: a linked Drive in state `connected` is tried first, Supabase Storage second; without a working link the chain is Supabase only. A provider that throws `ProviderUnavailableError` at upload time is skipped, the file is stored with the next one, and `files.storage_provider` records where it went. The fallback writes an audit entry `storage.fallback` and one notification per company and hour (`kd_drive_claim_fallback_notice`). Other errors (a bug, bad data) are not retried on another provider.
- D21 (05.4) The 15 minute health job sets a failing link to `error` (new files then go to Supabase at once, without waiting for a failed upload) and sets it back to `connected` when Drive answers again. A `revoked` link stays revoked until the owner links Drive again (05.5). If the notification service is not installed the notice is skipped; the audit entry is always written.
- D22 (05.5) Drive link: OAuth 2.0 code flow with PKCE and a signed 10 minute state cookie scoped to `/api/storage/drive`; scope `drive.file` only; `access_type=offline` and `prompt=consent` so Google always returns a refresh token. The callback address to register in the Google Cloud console is `<NEXT_PUBLIC_APP_URL>/api/storage/drive/callback` (the sign-in client of STEP 03 is reused; add this second redirect URI to it). The pending state must match the signed-in person and company; connecting needs the permission `storage.manage` (owner, CEO, super admin) and a fresh step-up. Tokens are stored encrypted (`oauth-tokens`, scope = company id).
- D23 (05.5) Unlinking asks Google to revoke the grant (best effort) and soft-deletes the link. If files are still in Drive the call is refused unless the owner confirms (`force`), because those files cannot be opened without the link. Linking again restores access.
- D24 (05.5) The settings page `/settings/storage` shows the provider in use, file counts per provider, the quota bar with the 80, 95 and 100 percent notices (feature 3457), the monthly upload limit and the link state. The overage policy (3458) is "block": uploads above the quota are refused.
- D25 (05.6) Migration of one file: read the encrypted object from the source, copy it to the target, read the copy back and compare the SHA-256 of the encrypted bytes, then switch `storage_provider` and `storage_ref` in one conditional update (it only applies if the record still points at the old copy). If the file changed or was deleted meanwhile, the copy is dropped. The old copy is deleted only when requested, and only after the switch. The plaintext hash is checked again whenever the file is read.
- D26 (05.6) Move jobs (`storage_migrations`, `storage_migration_items`) are resumable: the cron job `storage-migrate` claims up to 5 items a minute with `FOR UPDATE SKIP LOCKED`, an item stuck for 10 minutes is claimed again, and a failing item is retried up to four times before it counts as failed. One running or paused move per company. Pause, resume and cancel are available to the owner (own company) and platform staff.
- D27 (05.6) Starting a move needs the permission `storage.migrate` (owner, CEO, super admin; level L0 because it is the company's own data) and a fresh step-up. A move to Google Drive is refused unless the link is working. Platform files and companies without a Drive link stay on the platform storage. `/admin/storage` shows platform storage health, Drive link states, file counts, all moves, the quarantine list (dismiss or confirm) and the known-malware hash list.
- D28 (05.7a) Providers: generic SMTP (nodemailer; the host is resolved and must be a public address, the connection then goes to that exact address), Resend, SendGrid, Mailgun and Postmark over their HTTPS send APIs, and Amazon SES through its SMTP interface (host from the region), so no request signing is needed. Thirteen SMTP presets (feature 452) fill host, port and security. The request shapes of the four API providers and the feedback formats were written from the providers' public documentation as known to the build and were not re-read live in this session; the "send test" button of the settings page (05.7b) proves each one when a provider is set up. Amazon SES bounce feedback (through SNS) is not read.
- D29 (05.7a) Chain and limits: a company with its own provider uses only its providers; otherwise the platform providers by priority and last the `SMTP_*` environment. A failing provider (busy, unreachable or with wrong credentials) hands the message to the next one; a refusal of the message itself (bad address, rejected content) fails it for good. Per provider daily and monthly limits come from the settings; the company limit comes from the plan (`email.daily_limit`, default 1000) and is 100 a day for the first 7 days (ramp-up). A message over a limit waits for the next day without using an attempt. Retries wait 1, 5, 15, 60 and 240 minutes; after 6 attempts the message fails.
- D30 (05.7a) The outbox stores the rendered message. `kd_email_enqueue` applies, in one statement, the idempotency key (same key: no second row), the one-minute duplicate guard (same recipient, template and data) and the suppression list. Content of messages older than 30 days is erased and rows are removed after 90 days.
- D31 (05.7a) Tracking: open pixel and click redirects only in e-mail bodies and not for `auth.`, `security.`, `kyc.` and `payment.` templates. The click address holds only a token and a link index; the real address is read from the stored message, so it cannot be used as an open redirect. Non-transactional templates (`digest.`, `marketing.`, `notification.`, `report.`) carry the RFC 8058 one-click unsubscribe header; the unsubscribe route puts the address on the company's suppression list.
- D32 (05.7a) Feedback receivers (`/api/email/webhooks/{resend|mailgun|postmark|sendgrid}`) verify the provider signature (Svix HMAC, Mailgun HMAC, Postmark basic authentication, SendGrid ECDSA) before reading the body; an invalid call raises the security event `webhook_signature_invalid`. The secret is the `webhookSecret` stored (encrypted) next to the API key of the matching provider row; `?c=<company id>` selects a company's provider. Hard bounces and complaints suppress the address at once. These paths and the unsubscribe and tracking paths were added to the CSRF and bot-check exemption lists of `lib/middleware` (STEP 04 files).
- D33 (05.7a) Not built: sending to unverified addresses is not blocked (feature 485) because a verification mail must reach an unverified address and the contract has no flag for it; the platform SMTP quota alerts at 80, 95 and 100 percent (459) show as usage on the admin page instead of alert messages; the e-mail deliverability score (472) is the SPF/DKIM/DMARC check result of 05.7b.
