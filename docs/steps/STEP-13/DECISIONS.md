# STEP 13 - Decisions

D1 (2026-10-18). Branch base. `origin/integration` holds only STEP 01; STEPS 02 to 12 live on the session branch `claude/clever-goldberg-8ncdae`. STEP 13 consumes contracts implemented by STEPS 02 to 10, so it continues on this branch (as STEPS 11 and 12 did). The branch already contains the latest `origin/integration` (verified with `git merge-base --is-ancestor`).

D2 (2026-10-18). Baseline. `scripts/integration-check.sh --quick` stops at its first step: the generated barrels `lib/i18n/strings/en.ts`, `config/nav-map.ts` and `config/permissions.ts` are out of date. They belong to the Integrator and are stale since the fragments of STEPS 07 onward were added; this STEP does not edit or regenerate them (it writes fragment files only). The other baseline steps were run by hand and pass: `npm run lint`, `npm run typecheck`, `scripts/check-all.sh`.

D3 (2026-10-18). Token identity of an expired link. The tokens contract returns only a reason for an expired or revoked link, so the re-request page cannot learn which document the link was for. `migrations/S13_001_portal_core.sql` adds `kd_portal_token_lookup(hash)`, a read-only security-definer function (service role only) that returns the identity of the document behind a token hash. It reads no secret (never the code hash). Request R1 in DEPENDENCY_REQUESTS.md asks STEP 04 or the Integrator to put the identity into the contract so the function can be dropped.

D4 (2026-10-18). Code cookie. After a correct one-time code, a signed cookie (`kd_p_<link>`, HttpOnly, SameSite Lax, one hour, HMAC with `HMAC_TOKEN_SECRET`, bound to the link id) opens that link only. Without a request (no cookies) the check is false. The "remember this device for 30 days" bypass (FEATURE_LIST 1687) is not built: it needs a device identity that is stored without a login, which would weaken the gate.

D5 (2026-10-18). Rate limits. The limiter policy names are fixed in `config/security.ts` (shared). Token pages use the existing `auth` policy (10 a minute) per address and per link, and `strict` (5 a minute) for the code and re-request routes, which matches "10 requests a minute per link".

D6 (2026-10-18). Document views. `components/client/views/registry.ts` maps a document type to its page view. 13.1 ships the doors (gate, states) and an empty registry; 13.2, 13.3 and 13.6 add the views. A link whose type has no view is answered as an invalid link. `services/estimate/public.ts` (STEP 09) refuses links that need a code; 13.3 will use the lower-level estimate functions after the gate instead.

D7 (2026-10-18). Ownership. Helpers of this STEP live under `services/portal/` (the only owned place for plain code); `schemas/` and `lib/` are not owned by STEP 13. The generated barrel `lib/i18n/strings/en.ts` is updated by `npm run gen` (it gains one import for `lib/i18n/strings/en/s13-portal.ts`), as the earlier STEPs did; `scripts/check-ownership.mjs` flags that file, and the Integrator regenerates it at merge anyway.

D8 (2026-10-18). Pay now. STEP 10 makes payment links with `createPaymentLink(actor, ...)`, which needs an actor only for the company id (and a creator column). The invoice page's "Pay now" calls it with a fixed portal actor: nil user id, role `staff`, the company of the verified invoice link, no permissions granted anywhere (the function checks none). The link lives two hours (`PORTAL_PAY_LINK_HOURS`) and the payer is sent to its `/pay/<token>` page. A request for a public `createClientPaymentLink` in STEP 10 would replace this (R2).

D9 (2026-10-18). Consent gate. The processor's secure form opens only after the payer ticks one box and the server stores the proof (`consent_records`: time, masked/hashed/encrypted address, device, wording version, exact wording and its hash; plus the two purposes in the platform consent log). The gate is in the page, not in STEP 10's pay route (outside this STEP), so a direct call to that route would skip it; the evidence pack (13.9) reports a payment without consent as "no consent record" instead of inventing one.

D10 (2026-10-18). Invoice content. The page draws the same data as the PDF (`invoicePdfData`, STEP 09) so page and PDF cannot disagree; the PDF button returns the stored snapshot of what was sent (`readSnapshot`); "viewed" is recorded through `recordInvoiceViewed` as STEP 09 asked. Timeline is derived from the status (sent, viewed, paid) because the invoice event table belongs to STEP 09. Not built: partial-payment input (1730), BNPL (1729), bank transfer instructions as a payment method (1727, shown instead as a "Pay by bank transfer" block from the seller's remit-to details), wallet buttons (1728, inside the processor's own form), the success page with confetti (1734, the checkout panel shows its own result), client-hub "pay another invoice" (13.3). Method choice (1723) is made by STEP 10 routing, not by the payer.

D11 (2026-10-18). Estimates. The page uses `getEstimateByToken` and `decideEstimate` (STEP 09), which store the signature record (typed name, time, address, browser, content checksum). Both refuse a link that needs a code, so such an estimate shows as an unavailable link until request R3 is met. Drawn signatures and "request changes" are not built (the estimate service has no state for them); a decline with a note is the way to ask for changes. The estimate PDF is drawn from the stored estimate (`renderEstimatePdf`).

D12 (2026-10-18). Receipts. The receipt link carries a payment id; `receiptData` (STEP 10) refuses a payment that was not received, and the page shows that as an unavailable link. The checksum (first 16 hex characters of the SHA-256 of the facts in a fixed order) is printed on the page and in the PDF. The PDF renderer `receipt` is registered on the PDF contract through `services/portal/register.ts`.

D13 (2026-10-18). Client hub. The hub link carries the client id. The list is the 100 newest invoices of that client that were sent (never drafts, pending, void or proforma), with a status summary and a client-side filter and search. "Open" makes a seven-day invoice link (`HUB_OPEN_LINK_DAYS`) after checking that the invoice belongs to the client and company of the hub link. Not built: receipts listed in the hub (the payment list belongs to STEP 10; each receipt link is sent by email in 13.4), "Pay all unpaid" (one payment for several invoices is not in the payment contract), pagination beyond 100 invoices.

D14 (2026-10-18). Client emails. Nine new templates live in `emails/client/` (receipt, refund, estimate reminder, estimate expired, final notice, thank you, credit note, proforma, new link), with the ids `client.*` so open and click tracking stays on (it feeds the delivery proof) and no unsubscribe header is added. Invoice, estimate, overdue reminder and statement messages already exist (STEP 09 `emails/invoice`, STEP 08 `emails/crm`) and are reused. Subscription messages (1787 to 1789) belong to STEP 14. One line was added to `emails/catalog.ts`, as STEP 05 asked every STEP to do. The forward warning is a shared notice in every `client.*` template that holds a private link; the STEP 09 invoice, estimate and reminder templates lack it (request R4 asks STEP 09 to use `ForwardNotice` from `emails/client/client-frame.tsx`).

D15 (2026-10-18). Delivery proof. `sendClientMail` (services/portal/client-mail.ts) sends through the email contract, then writes one append-only `delivery_proofs` row per outbox message: document, masked address, the full address encrypted (purpose `pii`, company scope), subject, SHA-256 of the body and the link id. Later events (delivered, opened, clicked, bounced, complained) are read from `email_outbox` and `email_events`, so no second copy of that history exists. A failed proof write is logged and never hides the send. If the e-mail service treats a send as a duplicate (same recipient and data within a minute) no new outbox row exists and no second proof is written. The migration is `S13_003_delivery_proofs` (S13_002 was used by the consent proof), so the later migrations of this STEP take the next free numbers.

D16 (2026-10-18). Owner view. `/client-mail` (permission `portal.mail.read`, owner and staff) lists the last 100 messages with status, open time and masked address. The re-send button (1798) and the copy-link button (1799) are not built here: a portal link is shown once and only its hash is stored, so it cannot be copied later, and a re-send must rebuild the document message, which the document's own send action (STEP 09) does; both come with the owner workflows in 13.7.

D17 (2026-10-18). Branding. STEP 07 already keeps primary colour, accent colour, font and logo (`branding` settings section) and the custom domain records. This STEP adds what was missing in `tenant_branding` (`S13_004_branding`, because 002 and 003 were taken): secondary colour, e-mail signature (cleaned HTML) and a client footer line, and an append-only `branding_history` (save, reset, import with before and after). Save checks accessibility: primary and secondary colours need contrast 4.5 against white (white text on a button), the accent colour 3. Fonts are the four safe stacks of STEP 07 (`system`, `inter`, `serif`, `mono`); nothing is loaded from the internet. Reset returns colours and font to the platform values and clears signature and footer; the logo stays. Export and import use a small JSON file (`kd-branding`, version 1) checked strictly; the import goes through the same contrast check as a save. Branded pages always draw in the light theme (the neutrals are set with the brand colours), so the checked contrast also holds when the visitor's device is in dark mode.

D18 (2026-10-18). Where the brand shows. Client pages: `BrandedFrame` inside every token page (colours, font, logo, company name, footer line). Messages: `services/branding/register.ts` registers a brand resolver with the e-mail service (company name, primary colour, footer line). PDFs keep using the invoice seller block (STEP 09), which already reads the same settings. The logo of a company is public by design and served by `GET /api/portal/logo/<company id>` (images only, rate limited, no link needed). Plans: the platform mark ("Powered by") belongs to the page shell and is hidden for plans with `branding.white_label`; this needs the page to know the company before the page body runs, which is only possible on the company's own domain (the host names the company). On the platform's address the shell stays the platform's, so a white-label company reaches a fully clean look through its custom domain (plan key `domain.custom`). The plan catalogue has one key for both the badge and full white label, so both use `branding.white_label`.

D19 (2026-10-18). Custom domain serving. `tenantForHost` returns a company only for a verified, routed, not removed domain of a company whose plan has `domain.custom`; every other host (including the platform's own) is no company. A company's domain serves that company's links only: `resolvePortalAccess` answers "invalid" for a link of another company. Restricting a custom domain to portal routes (blocking dashboard and admin paths on that host) belongs to `proxy.ts` (shared): request R5.

D20 (2026-10-18). Contracts. Migration `S13_005_contracts`: `contract_templates`, `contracts`, `contract_versions` (append only, one row per save), `contract_signers`, `contract_events` (append only) and the function `kd_contract_save`, which creates or edits a draft, counts the version, replaces the signers and writes the event in one step (a stale save is refused, a sent contract cannot be edited). The `signatures` table (the evidence) comes with the signing page in 13.6.b. The display number (`CT-000123`) comes from one database sequence, so numbers are unique but a company can see gaps (acceptable: contracts have no legal numbering rule here). Four pre-built templates live in code (`services/contract/library.ts`); a company can write its own. Merge fields are the eight in `merge.ts`; values are HTML-escaped; a field with no value or an unknown field stops the send. The wording is rich text cleaned with the platform sanitizer; the editor is a plain HTML text box (no rich-text library), which is recorded as a known limit.

D21 (2026-10-18). Sending. Sending freezes the merged wording, stores its SHA-256 (`body_hash`, covering title and wording) and invites the signers. A signer link uses the tokens contract with document type `contract`, the document id is the signer id (so the page knows who signs), and a one-time code is always required; the code goes to the signer's own address through a recipient resolver registered by `services/contract/register.ts`. Parallel contracts invite everybody; sequential ones invite position 1 and `inviteNextSigner` (called by the signing page in 13.6.b) invites the next. A reminder issues a fresh link (the old one stops working), at most once a day by hand and every three days up to three times by the daily job. Cancelling a contract revokes every signing link. The daily job (`cron/jobs/s13-contracts.ts`) expires unsigned contracts past their signing date, sends the reminders and tells the owner (notification) when a signed contract is about to end (`renewal_notice_days`). Every contract message is also written as a delivery proof (13.4).

D22 (2026-10-18). Not built in 13.6.a: auto-create an estimate or invoice from a contract (2266, 2267; the columns `invoice_id` and `estimate_id` exist, the action needs the STEP 09 create functions and is left for the owner workflows), a side-by-side diff and restore of versions (the versions are stored and listed through the API), and e-mail to signers when a contract is cancelled (their link simply stops working). The send, remind and cancel actions are owner-only (`contract.send`); staff can write drafts. The owner send gate with staff request and approval is built in 13.7.

D23 (2026-10-18). Signing. Migration `S13_006_signatures` adds `signatures` (append only, one per signer) and the functions `kd_contract_sign` and `kd_contract_decline`. The database function enforces the rules in one locked step: the contract is open, the signer has not signed or declined, the wording checksum the signer saw still matches (so a signature always belongs to exactly the wording on the page), the signer's turn has come (sequential contracts), and the last signature closes the contract. Two clicks or two browsers cannot sign twice (unique index). Evidence per signature: typed name, method, picture checksum, wording checksum, the exact statement accepted and its checksum, masked and hashed address, the full address encrypted, browser and device (same helper as the consent proof of 13.2). A decline ends the contract as declined and revokes every signing link. The signing page is `/c/<token>` (the tokens contract, document type `contract`, document id = signer id, one-time code always required); the first look marks the signer and the contract as viewed.

D24 (2026-10-18). Signature pictures. A drawn signature is a canvas PNG; an uploaded one is a PNG or JPEG of at most 500 KB. The server decodes the picture and draws it again as a PNG of at most 600 by 200 pixels on white (this removes metadata and anything hidden), refuses anything that is not a real image, and stores it through the storage contract (category `contract`). Typed signatures need no picture. The signing request ties the method to the picture (typed: none; drawn or uploaded: required).

D25 (2026-10-18). Signed copy and seal. When the last signer signs, `finalizeContract` draws the PDF (`services/esign/contract-pdf.tsx`: wording, a signature block per signer, and a certificate page with times, masked addresses, devices, methods and checksums), stores it through the storage contract (the company's Google Drive when linked, otherwise Supabase Storage, both encrypted), and keeps its SHA-256 and a seal on the contract. The seal is an HMAC-SHA256, keyed with the platform secret `HMAC_TOKEN_SECRET`, over the contract id, the wording checksum, the file checksum and the checksum of every signature record, so changing the file, a signature record or the wording breaks it; `verifySignedContract` checks all three and the owner page shows the result. This is a tamper-evident seal, not a certificate-authority (PKI) signature; a PDF with an embedded digital certificate is not built (it needs a signing certificate that the platform does not hold). Each signer receives a fresh link to their copy, and the owner a notification. If making the copy fails, the signature stays valid and the daily job (`finalizePending`) finishes it; the signing page also tries once when a signer asks for the download.

D26 (2026-10-18). What 13.7 builds, and what earlier STEPs already own. Several items of the 13.7 list are already delivered by other STEPs and are not built again (rule 7): the owner-only send of invoices and estimates with staff approval and the batch send (STEP 09 `services/invoice/send.ts`, `batch.ts`, rule `invoice.send`), the dunning ladder, promise-to-pay and reminder pauses (STEP 09 `reminders.ts`), duplicate clients, merge, archive, do-not-contact and reminder opt-out and bulk edit (STEP 08), and industry presets, terms and notes libraries, ownership transfer and the grace period (STEP 07). The dispute note belongs to the dispute case in 13.8. 13.7 builds what is left for the client portal: (1) the owner's decision on link re-requests, (2) the owner send gate for contracts, (3) the messages to clients that nobody presses send for, (4) a safe bulk reminder for estimates.

D27 (2026-10-18). Link requests. The owner sees the waiting requests (`/client-mail/requests`, permission `portal.link.decide`) and approves or denies each once. The decision is taken first with a compare-and-set update, so two owners cannot both send a link; if the message then fails the request goes back to waiting. Approve issues a fresh link through the tokens contract (`reissue`, which keeps the lifetime and the one-time-code rule) and sends `client.new-link` to the address on file for that document (the client, or the signer of a contract), never to an address from the request. A document with no address (a payment link, a payslip) cannot be approved. Deny stores a reason and tells the client nothing, so the form cannot be used to probe. Migration `S13_007_owner_workflows` adds the reason column.

D28 (2026-10-18). Contract send gate. The owner sends at once. A staff member asks (`contract.request_send`): the ask goes through the approval service (rule `contract.send`, level L1, 24 hours), the owner is notified, and the draft cannot be edited while the ask is open (edits are refused; "take the request back" unlocks it). A job every five minutes (`cron/jobs/s13-approvals.ts`) sends the approved contract, but only if its version is still the one the owner was asked about; otherwise, or when the approval was rejected or expired, the request is cleared and the reason is shown to staff. The server checks the permission on every call; hiding the button is not the protection. The contract log gained the kinds `send_requested` and `send_rejected`.

D29 (2026-10-18). Messages without a button. `workers/s13/client-notices.event.ts` sends the receipt (`payment.captured`), the thank-you (`invoice.paid`) and the refund note (`payment.refunded`); each has an e-mail key built from the payment, invoice or refund, so a repeated event sends once. A daily job sends one "estimate expired" note to clients of estimates that ended in the last seven days. A client with do-not-contact gets only the receipt and the refund note (a record of a sale), not the thank-you or the expiry note; reminders also respect the reminder opt-out. Estimate reminders are never automatic: the owner starts them in bulk. Bulk safeguards: the owner first sees the list, confirms the exact number (a list that changed is refused), at most 100 per run, nobody reminded in the last week, one result per estimate, one failure never stops the rest, and running it again skips what was sent. Estimate links in these messages need no one-time code (request R3 explains why).

D30 (2026-10-18). Dispute cases. Migration `S13_008_disputes`: `disputes` (one case per processor event and per processor dispute id), `dispute_evidence` and `dispute_events` (both append only), and `refund_requests`. A case is made only from the `dispute.opened` event that STEP 10 publishes (worker `dispute.intake`, safe to run again); nobody creates one by hand. The owner is notified at once. The event payload carries only the ids, so the reason starts as "general", the amount is what was captured, and the answer date is an estimate (`DISPUTE_RESPONSE_DAYS`, 7); the owner enters the real reason code and date from the processor's dashboard, which also restarts the alerts. If STEP 10 later adds `reasonCode`, `dueBy` and `disputedAmount` to the event (request R6), the intake already uses them. Status workflow (pure, in `status.ts`): new, gathering, submitted, then won, lost, accepted or withdrawn; closing sets the closing time; no step back. `dispute.won` and `dispute.lost` events close the open case. The chargeback amount and fee deduction from the wallet (1550, 1551) belong to the wallet in STEP 14 and are not built here.

D31 (2026-10-18). Reason codes. Every processor names its codes differently and the rule for processor code is to read the processor's own documentation, which this sub-step does not need to do: `registerReasonMapper(processorId, mapper)` is the hook an adapter uses for its own codes, and until it does the code text is sorted by plain keywords (fraud, not received, not as described, duplicate, subscription cancelled, credit not processed, general). Each category has a short hint about which proof helps most. The adapter hook `evidenceFormat` (STEP 10 contract) is used by the evidence pack in 13.9.

D32 (2026-10-18). Deadlines. The owner is alerted 72 hours and 24 hours before the answer is due and once when it is overdue; each alert is sent once per case and date (the time is stored on the case). The job is `cron/jobs/s13-disputes.ts`, hourly (the cron convention of this repository, instead of a `workers/s13` file). The platform team has a read-only dispute centre at `/admin/disputes` with the same numbers across companies (permission `dispute.read.all`).

D33 (2026-10-18). Client refund requests. The receipt page shows "Ask for a refund" when the payment can still be refunded: inside the refund window of STEP 10 (`REFUND_WINDOW_DAYS`), with an amount left, no request waiting, and no open dispute (a disputed payment is settled in the dispute, otherwise the client could be paid twice). The client chooses an amount up to what is left and gives a reason; the address is hashed, the owner is notified, and the portal event `refund_request` is stored. The owner approves or denies at `/disputes/refund-requests` (permission `dispute.refund.decide`). Approving takes the decision first and then calls `refundPayment` of STEP 10 as the signed-in owner, with the key `refund-request-<id>`, so the payments service keeps its own limits, large-refund approval and idempotency; if it fails the request is marked failed with a note and the owner refunds by hand. The client gets the `client.refund` note from the payment event (13.7); a denial sends nothing (the owner writes to the client).

D34 (2026-10-18). Evidence pack content. `collectEvidence` (services/evidence/collect.ts) gathers nine sections for the payment behind a dispute, from this company's rows only: (1) the invoice as sent, with the checksum of the stored sent-PDF, (2) the receipt, (3) the consent records with the exact words, version, checksum, time, device and the full network address (decrypted for this evidence only; the other places show it masked) together with the refund policy text and period, (4) delivery proof: the messages that carried the invoice and what happened to each, plus accepted estimates, (5) the communication log of every message sent to that client, (6) client identity: payer address and country, pages viewed with time, masked address and device, and the 3D Secure result as recorded, (7) the timeline of all of it in time order, ending with the dispute, (8) the audit chain proof: the chain check of the company and the entries about the invoice, payment and dispute with their hashes, (9) platform details. The pack holds no card number. WhatsApp threads (1915 of the sources) are STEP 16; the log lists e-mail only. A section with nothing recorded says so in the PDF (a reader can tell "no record" from "left out"). The PDF is `lib/pdf/evidence-pack-pdf.tsx`.

D35 (2026-10-18). Stored packs. Migration `S13_009_evidence_packs` (append only, one row per version of a dispute). "Generate evidence pack" (`/api/disputes/evidence`, permission `dispute.manage`, one click) collects the evidence, draws the PDF, builds the ZIP and stores both through the storage contract in the category `evidence` (encrypted; the company's Google Drive when linked, otherwise Supabase Storage). The ZIP holds the pack PDF, the invoice PDF as it was sent, the receipt PDF, `data.json` (everything collected), `processor-format.json` when the adapter has one, `manifest.json` (name, size and SHA-256 of every file) and a README. The ZIP is written by `services/evidence/zip.ts` (files stored without compression; no new package, because package.json belongs to the Integrator); an independent reader and python's zip reader accept it. The checksums of the PDF and the ZIP are written to the audit chain (`dispute.evidence_pack_created`), and a download first checks the stored file against its checksum. A first pack moves a new case to "gathering"; a new pack is a new version, never a change. The sent-invoice PDF is the stored snapshot of STEP 09; it is left out (and the pack says so) when none exists.

D36 (2026-10-18). Retention. The pack records `retain_until` (18 months, `PACK_RETENTION_MONTHS`, the minimum the feature list asks for). The storage contract keeps files of the category `evidence` for seven years (`config/storage.ts`), which is longer, so the file itself outlives the promise; the shorter promise is what the pack page shows. Packs of a closed case can still be downloaded; making a new one is refused.

D37 (2026-10-18). Processor format and submission. `evidenceFormat` is the optional adapter hook of the payment contract; `processorSections` (services/evidence/facts.ts) gives it the facts (invoice, receipt, consent with the full address, refund policy, delivery, identity and 3D Secure, timeline) and never a card number or card fingerprint. No adapter implements the hook yet, and the rule for processor code is to read the processor's own documentation first, so this STEP writes no processor-specific layout: the pack says "includes the processor's own format" only when an adapter returned one. Automatic submission of the pack to the processor through its API and e-mailing it to the processor (3921, 3923) need a submit-evidence call that the adapter contract does not have; the owner downloads the PDF or ZIP and sends it from the processor's dashboard. Both are recorded as a request to STEP 10 (R7). The dispute centre for the platform team (`/admin/disputes`) is read only and shows no pack files; packs are downloaded by the company's own people.
