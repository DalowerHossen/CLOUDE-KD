# STEP 07 - Sub-steps plan

Session branch: claude/clever-goldberg-8ncdae (contains STEPs 01 to 06; `origin/integration` is an ancestor). Migrations `S07_001` onward with `_down.sql`; assertions `sql/assertions/s07_*.sql`; logic checks `scripts/verify/step07-*`. Per sub-step: prettier on touched files, lint, typecheck, `scripts/check-all.sh`, `PGHOST=/tmp/pgsock bash scripts/db-apply.sh --clean` when a migration exists, security checklist Z1 to Z14, one commit `feat(step07): 07.k <summary>`.

Owned paths (OWNERSHIP_MAP row 07): `app/(dashboard)/{onboarding,team}/`, `app/(dashboard)/settings/` (except `storage`, `email`), `app/(dashboard)/support/`, `services/{company,team,kyc,domain,support,lifecycle}/`, `app/api/{companies,settings,team,kyc,support}/`, `app/(admin)/admin/page.tsx`, `app/(admin)/admin/{users,tenants,kyc,support,feature-flags,staff,setup}/`, `components/{onboarding,settings}/`, `emails/onboarding/`, `migrations/S07_*`. Extra paths (lib, config, verify scripts) follow the `NN` naming and are added to `config/ownership.json` and named in the handoff.

Design rules:

- Tenant settings live in one table `company_settings` (one row per company and section, jsonb value checked by a strict zod schema per section, `version` column for the optimistic lock, audit trigger). Sections: `profile`, `branding`, `invoice`, `notifications`, `display`, `security`, `approval`, `onboarding`. Other STEPs read a section through `services/company/settings.ts`.
- The tenant is always taken from the session (`getTenantContext`); a foreign id answers 404. Platform screens act on a company only through an explicit company id and audit it with `companyId`.
- Every settings write is optimistic-locked, validated strictly, sanitized, audited. Staff cannot raise their own permissions (a staff actor can never write `memberships`).
- KYC documents are stored only through the storage contract (category `kyc`); a document view by a reviewer goes through one service function that writes the access log first.
- Approvals use the approval contract; because the contract has no callback, a cron job reads decisions and applies them (same pattern as STEP 06).
