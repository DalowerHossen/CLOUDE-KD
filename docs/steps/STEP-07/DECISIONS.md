# STEP 07 decisions

- D1 (07.1) Tenant settings are one table, `company_settings`, with one row per company and section and a jsonb value. Each section has a strict zod schema in `lib/company/sections.ts` (profile, branding, invoice, display, onboarding; later security, approval, notifications). A read fills missing keys from the defaults. A write goes through the function `kd_company_setting_save`, which checks the version (0 means create) and raises a conflict on a mismatch, then the service writes an audit entry. Text fields refuse angle brackets, so stored values can never be read as markup. The browser has no direct database access to these tables.
- D2 (07.1) Industry presets (six) only set the invoice defaults and show focus hints. The chosen industry is stored in the profile section; the chart of accounts, tax rates, templates and dashboard widgets that the feature list ties to a preset belong to the accounting, tax, invoice and dashboard STEPs, which read `profile.industry`. Not built here: interactive tour, tooltips, demo data (it needs clients and invoices from STEPs 08 and 09), the "need help" button, video tutorials, logo cropping.
- D3 (07.1) Wizard: five steps (company, logo, brand, invoicing, payments), saved after each step, resumable, skippable at any time. The payments step only explains and lets the owner finish, because payment methods are connected by the platform team (REQ-ADMIN-CONNECT). The checklist counts company details, logo, invoice defaults and the milestones first client, first invoice and first payment; milestones are recorded by the event handler `workers/onboarding/milestones.event.ts` from `client.created`, `invoice.created` and `payment.captured`. The checklist component is exported for the dashboard home (STEP 09). A day 1, 3, 7 and 14 guidance series is queued once when the wizard is first opened (template ids start with `notification.`, so the unsubscribe header applies).
- D4 (07.1) Logo: PNG, JPEG or WebP up to 1 MB, stored through the storage contract (category `logo`, encrypted); only the file id is kept. A new logo applies to documents made afterwards. The logo is read back by a plain route that serves only the signed-in company's own logo.
- D5 (07.2) Settings screens are five pages (company, branding, invoicing, notifications, display) that share one generic form driven by a field list (`lib/company/forms.ts`); the server checks every save against the strict section schema, so the list only decides what is shown. Staff with `company.read` see the values read-only; only `company.manage` (owner) saves. The version is sent with every save; a stale version answers a conflict and the screen asks for a reload. Showing other currencies next to dollar amounts is locked unless the plan has `display.multi_currency` (read through the entitlement contract, with the plan catalogue as the fallback until it is registered). The UI stays English; there is no language setting.
- D6 (07.2) The `invoice.nextNumber` setting is where numbering starts; the invoice STEP (09) owns the running counter and must not move below numbers already used. The company-level `notifications` section (who is told: owner only or owner and staff, optional summary e-mail) is stored here; STEP 05 can read it with `getSection(companyId, 'notifications')` instead of its fixed list (handoff request). Personal notification choices stay on `/notifications`.
- D7 (07.3) Invitations: the token is 32 random bytes (base64url); only its SHA-256 is stored; it works once, ends after 7 days, can be sent again (at most 5 times; each send replaces the token) or cancelled; one open invitation per address and company (unique index). An address that already has an account is refused with the same words as any other refusal, so the answer reveals nothing. The invited person opens `/join?token=...` (a page in the sign-in group), which creates the account (e-mail counts as confirmed because the link arrived there), applies the platform password rules and the Turnstile check, and calls `kd_invitation_accept`, which creates the profile and the staff membership and closes the invitation in one database step; if it fails, the new account is removed. Seats: the owner plus active staff plus open invitations are counted against `staff.seats`.
- D8 (07.3) Permissions: the owner gives staff exact actions from the registered permissions that list `staff` among their default roles (`validateStaffGrants` refuses everything else). Presets (Sales, Accounts, Support, Manager, Viewer) are expanded to those exact actions and only fill the editor; nothing is stored as "preset", so a preset applied today does not grow by itself when new permissions arrive (the owner applies it again). Staff can never receive `team.*`, KYC, roles, flags, storage or e-mail rights, and cannot call the team routes, so they cannot raise their own permissions. Every change writes an audit entry with the added and removed actions and tells the person. Deactivate and remove close every session of the person at once; removal is a soft delete and keeps the work they did.
- D9 (07.3) Staff security rules (require two-factor, staff idle timeout, IP allow list) and approval rules (actions staff can only prepare, amount cap) are stored in the `security` and `approval` settings sections and edited on `/team/security` (permission `team.security`, owner only; the settings API hides these two sections from everyone else). Enforcement belongs to the sign-in and session code of STEP 03 and to the STEPs that own the actions (invoices, exports); this STEP delivers the stored rules and `getSection(companyId, 'security' | 'approval')` for them (DEPENDENCY_REQUESTS). Session lists and revoking staff sessions already exist on `/account/security` (STEP 03) and are linked, not rebuilt. The staff activity view reads the audit log of the company for one person.
- D10 (07.4) KYC data model: one open submission per company (`kyc_submissions`, status draft, submitted, in review, changes requested, approved, rejected, expired), four documents per submission (ID front, ID back, business registration, proof of address; `kyc_documents`, one live row per type), an append-only log of reviewer document views, and the owners' details encrypted with the `kyc` purpose and the company as scope. Documents are files in the storage contract (category `kyc`); the browser never gets a document back after upload, only names and states. Rules: 5 MB, JPEG, PNG, WebP or PDF (the storage file validator checks the content), photos at least 600 by 400 pixels, a document with a date of its own must not be expired, replacing a document removes the earlier file. The same content sent by two companies sets a duplicate flag for the reviewer. Sending needs a network that is not a VPN, proxy or Tor (`networkContext: 'kyc'`).
- D11 (07.4) `kyc` contract: `status` maps the detailed states to the five contract states (draft and expired read "not_submitted"; "changes_requested" reads "rejected" because the owner must act); `isVerified` is true only for an approved submission whose end date has not passed. An open renewal does not remove an approval that is still valid. Gated features (merchant-of-record unlock, payment and payout limits, gateway routing) are decided by STEPs 10 and 14 from this contract; the owner screen only shows the state.
- D12 (07.5) Review flow: the queue (`/admin/kyc`, permission `kyc.review`) lists submitted and in-review cases. Opening a document needs `kyc.review` and `kyc.file.read`, writes a row to `kyc_document_views` and the audit log first, and only then reads and returns the decrypted file with no caching. A reviewer starts the review (which runs the screening hook), accepts or rejects each document with a reason, sets a risk level and an internal note, and then either recommends approval, asks for changes (needs a rejected document) or rejects with a reason shown to the owner. Recommending creates an approval request `kyc.approve` (level L2, CEO) with the reviewer as requester, so the person who reviews is never the person who approves (maker-checker). The cron job `kyc-sync` (every 15 minutes) applies the CEO's decision: approved gives a verification valid for two years (the earlier approval of the company ends), a refusal returns the case to the reviewer. Approval, rejection and change requests publish `kyc.approved` and `kyc.rejected`, which STEP 05 turns into notifications to the owner.
- D13 (07.5) Screening: no sanctions or anti-money-laundering provider is built in, because an adapter must be written from the provider's own documentation. `lib/kyc/screening.ts` is the hook: a provider registers itself and is called for the company and every owner when a review starts; without one the screen says "not configured" and the reviewer checks by hand. A "matches found" result blocks the recommendation until the reviewer rejects or asks for changes. Expiry: the same job warns the owner 30 days before a verification ends (once) and marks ended ones as expired; `isVerified` already turns false at the end date, so payouts and the merchant-of-record unlock stop without waiting for the job. The "re-verification cycle" is the two-year validity; big-payout four-eyes approval belongs to the payout STEP (10), which can call the same approval engine.
- D14 (07.6) Custom domains: up to 5 per company, gated by the plan entitlement `domain.custom` (the screen shows the steps but adding is refused without the plan). The owner creates two DNS records: a TXT record `_kd-verify.<host>` with `kd-verify=<token>` that proves ownership (required) and a CNAME of the host to the platform host (needed for visitors; apex names use ALIAS or ANAME). A check reads the DNS, marks the domain verified when the TXT record matches, and records whether the CNAME points to the platform. When both are right, one HTTPS request to the host asks the hosting platform's certificate state; before that request the host's addresses must all be public (no private, loopback, link-local or reserved range), so a name cannot aim the server at the inside network. Certificates are issued and renewed by the hosting platform; this STEP only reports the state ("pending", "active", "problem"). A verified domain whose proof record is missing for 7 days becomes "needs attention" and the owner is told. One primary domain per company, only a verified domain can be primary (database constraint). The job `domain-check` checks every domain not checked for 6 hours.
- D15 (07.6) Not built here: serving client pages on custom hosts. `companyForHost(hostname)` in `services/domain/domains.ts` answers which company owns a verified host; the proxy chain (STEP 01/04) and the client portal STEP must call it, and the hosting platform must have the domain added as an alias (a manual or API step of the deployment, listed in the handoff).
- D16 (07.7) Security policy: the `policy` section (shortest password, complexity, sign-in alerts, owner approval of staff exports) is edited on `/settings/security`; staff rules stay on `/team/security`. Like the staff rules, enforcement of the password and sign-in items belongs to STEP 03 (it reads `getSection(companyId, 'policy')`); the export approval is enforced here.
- D17 (07.7) Export and backup: a request is queued and the job `lifecycle` (every 5 minutes) builds a gzip file of JSON from the tables registered in `lib/lifecycle/registry.ts` (only registered tables and columns; the registry refuses columns whose names suggest a secret), stores it through the storage contract (category `export`, encrypted at rest), records a SHA-256 checksum and keeps it for 7 days; the owner downloads it through a 5 minute signed link after a fresh step-up, and every download is audited. Scheduled backups (daily or weekly, owner choice) use the same path, and the last 10 are kept. A staff member's export waits for the owner through the approval engine (`data.export`, level L1) when the policy says so. Other STEPs register their tables with one call (`registerTenantExport`), listed in the handoff. Not built: restoring a backup into the live company. A restore must write into tables owned by many STEPs and can overwrite newer data, so it stays a supervised operation (support with CEO approval) until each STEP offers an import function.
- D18 (07.7) Closure: the owner types the company name and confirms with a fresh step-up; the account then closes after 30 days (data request kind `closure`, one open closure per company). The owner can cancel until then and nothing changes. At the end of the grace period the job suspends every membership, ends every session, removes custom domains and sets the company to `closed`; records that the law requires stay stored under the retention rules of STEP 05 and STEP 02 (the closure does not shorten them). Suspension to read-only mode and abuse handling are platform actions in 07.8.
- D19 (07.8) Admin home and people: `/admin` shows counters (companies by state, owners, company staff, platform staff, verifications to review, open alerts, open incidents, open support tickets) and the latest 15 audit entries. Counters of tables that another STEP or a later sub-step owns read "not available yet" instead of failing. `/admin/users` and `/admin/tenants` are server-rendered lists with search, filters and 25 rows per page; the filters live in the address. Detail pages show sign-ins, activity, members and internal notes. Permissions: `admin.home`, `people.read`, `people.note` (all platform roles) and `people.manage` (CEO and super admin, level L2).
- D20 (07.8) Suspend and reactivate (user or company) need a reason of 10 to 1000 characters and a fresh step-up. The CEO and admin staff create an approval request (rules `user.suspend`, `user.reactivate`, `tenant.suspend`, `tenant.reactivate`, level L2) and the row in `admin_actions` waits; the cron job `admin-actions` (every 5 minutes) applies the decision. The super admin acts directly. Only one open action per subject, nobody changes their own account, and platform staff are changed only by the super admin. Suspending a user sets the profile to disabled and ends all sessions; suspending a company sets it to suspended (tenant API refuses it) and ends the sessions of its members. Confirming an e-mail by hand uses the auth admin API. Impersonation stays with STEP 03 (`/admin/impersonation`); the user page only links to it for the super admin.
- D21 (07.9) Admin staff (`/admin/staff`, `staff.read` for super admin and CEO, `staff.manage` for the super admin only, fresh step-up): the super admin creates the account with a name, e-mail and sub-role. The account gets a random password nobody sees; the person receives the one-time set-password link of STEP 03 (reset token, 1 hour style lifetime from `PASSWORD_RESET_TTL_SECONDS`) and sets two-step sign-in at the first sign-in as the platform rules demand. The link can be sent again. The sub-role can be changed. Suspending or reactivating staff stays in the people screens (D20).
- D22 (07.9) Shifts: a weekly plan per person (up to 42 slots, day, start and end in UTC, no overlap, replaced in one database function so a refused plan keeps the old one). `onDutyNow(subRole?)` in `services/team/admin-staff.ts` lists active staff on duty; support routing (07.10) uses it. Holidays and time zones per person are not built.
- D23 (07.9) Announcements (`/admin/announcements`, `announcement.manage` for super admin and CEO): title, message, kind (information, maintenance, warning), audience (all or owners), start and end (at most 90 days), withdraw at any time. Companies read them on `/announcements` (nav item "Notices") and through `GET /api/announcements`. A banner on every company page needs the shared dashboard layout, which belongs to another STEP; it is listed in the handoff.
- D24 (07.9) Feature flags (`/admin/feature-flags`, read for super admin and CEO, change `flags.manage` for the super admin): global flags and per-company overrides with a rollout percentage, optimistic lock on the version, step-up and audit entry on each change. The rule `flags.manage` is level L3 in the approval list, but like the solo-mode switch of STEP 02 the super admin has no higher approver, so the change is applied directly and audited. Setup wizard (`/admin/setup`, super admin): approval mode (applies the solo-mode switch), e-mail sender confirmed, security overview confirmed; each step is stored once in `platform_setup`.
- D25 (07.8 correction) The sub-role rule (STEP 02) lets an admin staff member use only the permission domains of their sub-role. The platform home, the people screens and their notes therefore belong to the super admin and the CEO only (`admin.home`, `people.read`, `people.note`, `people.manage`); the menu entries follow. Support agents work in the support queue, which shows the company and the person who asked.
- D26 (07.10) Support tickets: a company owner (all tickets of the company) or staff member (own tickets) opens a ticket with subject, topic, priority (low, normal, high) and a first message; at most 50 open tickets per company. Numbers are `T-000001` from a sequence. The first-answer and solution deadlines come from the priority (urgent 1h/8h, high 4h/24h, normal 8h/48h, low 24h/96h) and are recalculated from the creation time when an agent changes the priority. A new ticket goes to the on-duty support agent with the fewest open tickets (shifts from 07.9); with nobody on duty it waits unassigned in the queue. An agent reply sets "waiting for you"; a reply from the company reopens the ticket; solved tickets close by themselves after 7 days; the company can close, reopen and rate (1 to 5) a solved or closed ticket. Internal notes are never returned to the company (database constraint, policy and service). Agents (`support.agent`: super admin, CEO, admin staff with the support sub-role) open the queue (views: unassigned, mine, all open, late), answer, leave internal notes, take, assign (only to active support agents, CEO or super admin), change state and priority. Opening a ticket as an agent is written to the audit log. The job `support-sweep` (every 10 minutes) closes quiet solved tickets and sends one late-first-answer notice per ticket. Company users are told through the notification contract; no new domain events were added because event names are fixed by the contracts.
- D27 (07.11) Feedback and NPS: the satisfaction question (0 to 10 and an optional reason) is due for a person when the company is at least 14 days old and the person has not answered in 90 days or waved it away in 30 days; free feedback (idea, problem, praise, other) can be sent from `/feedback` at any time. `FeedbackPanel` (`components/feedback`) can be placed on any company page; the shared dashboard layout belongs to another STEP, so the handoff asks the layout owner to show it (`GET /api/feedback` says whether it is due). The super admin and the CEO see the score (promoters minus detractors, last 90 days) and the latest comments with the company name in `/admin/feedback`.
- D28 (07.11) Several companies: a person with memberships in more than one company lists them at `/settings/companies` and switches the active one. A switch updates the profile and the signed account claim (server only), needs a fresh step-up, is audited for both companies, and the page then takes a new token. Adding another company (owner only) is part of the enterprise plan; there is no dedicated plan key yet, so the plan key `sso.ready` (enterprise only) is used, and the handoff asks the plan owner for a `company.multi` key. Up to 10 companies per person. Other STEPs keep reading `actor.companyId`, so nothing else changes.
- D29 (07.11) Single sign-on readiness: the settings section `sso` (standard SAML 2.0 or OpenID Connect, provider name, issuer and sign-in addresses over https, client or entity identifier, up to 5 e-mail domains, staff must use it) is stored like any other section. The checklist needs the enterprise plan (`sso.ready`), complete provider details, at least one domain, an approved business verification and two-factor sign-in for the owner. When all hold, the owner asks for activation with a fresh step-up: this opens a support ticket with the details and records the milestone `sso_requested` (once). Signing people in through the provider is not built here: it needs the provider's own documentation and belongs to the authentication STEP; until it exists, saving these settings changes nothing about how people sign in.
