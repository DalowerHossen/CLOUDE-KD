# STEP 07 decisions

- D1 (07.1) Tenant settings are one table, `company_settings`, with one row per company and section and a jsonb value. Each section has a strict zod schema in `lib/company/sections.ts` (profile, branding, invoice, display, onboarding; later security, approval, notifications). A read fills missing keys from the defaults. A write goes through the function `kd_company_setting_save`, which checks the version (0 means create) and raises a conflict on a mismatch, then the service writes an audit entry. Text fields refuse angle brackets, so stored values can never be read as markup. The browser has no direct database access to these tables.
- D2 (07.1) Industry presets (six) only set the invoice defaults and show focus hints. The chosen industry is stored in the profile section; the chart of accounts, tax rates, templates and dashboard widgets that the feature list ties to a preset belong to the accounting, tax, invoice and dashboard STEPs, which read `profile.industry`. Not built here: interactive tour, tooltips, demo data (it needs clients and invoices from STEPs 08 and 09), the "need help" button, video tutorials, logo cropping.
- D3 (07.1) Wizard: five steps (company, logo, brand, invoicing, payments), saved after each step, resumable, skippable at any time. The payments step only explains and lets the owner finish, because payment methods are connected by the platform team (REQ-ADMIN-CONNECT). The checklist counts company details, logo, invoice defaults and the milestones first client, first invoice and first payment; milestones are recorded by the event handler `workers/onboarding/milestones.event.ts` from `client.created`, `invoice.created` and `payment.captured`. The checklist component is exported for the dashboard home (STEP 09). A day 1, 3, 7 and 14 guidance series is queued once when the wizard is first opened (template ids start with `notification.`, so the unsubscribe header applies).
- D4 (07.1) Logo: PNG, JPEG or WebP up to 1 MB, stored through the storage contract (category `logo`, encrypted); only the file id is kept. A new logo applies to documents made afterwards. The logo is read back by a plain route that serves only the signed-in company's own logo.
- D5 (07.2) Settings screens are five pages (company, branding, invoicing, notifications, display) that share one generic form driven by a field list (`lib/company/forms.ts`); the server checks every save against the strict section schema, so the list only decides what is shown. Staff with `company.read` see the values read-only; only `company.manage` (owner) saves. The version is sent with every save; a stale version answers a conflict and the screen asks for a reload. Showing other currencies next to dollar amounts is locked unless the plan has `display.multi_currency` (read through the entitlement contract, with the plan catalogue as the fallback until it is registered). The UI stays English; there is no language setting.
- D6 (07.2) The `invoice.nextNumber` setting is where numbering starts; the invoice STEP (09) owns the running counter and must not move below numbers already used. The company-level `notifications` section (who is told: owner only or owner and staff, optional summary e-mail) is stored here; STEP 05 can read it with `getSection(companyId, 'notifications')` instead of its fixed list (handoff request). Personal notification choices stay on `/notifications`.
- D7 (07.3) Invitations: the token is 32 random bytes (base64url); only its SHA-256 is stored; it works once, ends after 7 days, can be sent again (at most 5 times; each send replaces the token) or cancelled; one open invitation per address and company (unique index). An address that already has an account is refused with the same words as any other refusal, so the answer reveals nothing. The invited person opens `/join?token=...` (a page in the sign-in group), which creates the account (e-mail counts as confirmed because the link arrived there), applies the platform password rules and the Turnstile check, and calls `kd_invitation_accept`, which creates the profile and the staff membership and closes the invitation in one database step; if it fails, the new account is removed. Seats: the owner plus active staff plus open invitations are counted against `staff.seats`.
- D8 (07.3) Permissions: the owner gives staff exact actions from the registered permissions that list `staff` among their default roles (`validateStaffGrants` refuses everything else). Presets (Sales, Accounts, Support, Manager, Viewer) are expanded to those exact actions and only fill the editor; nothing is stored as "preset", so a preset applied today does not grow by itself when new permissions arrive (the owner applies it again). Staff can never receive `team.*`, KYC, roles, flags, storage or e-mail rights, and cannot call the team routes, so they cannot raise their own permissions. Every change writes an audit entry with the added and removed actions and tells the person. Deactivate and remove close every session of the person at once; removal is a soft delete and keeps the work they did.
- D9 (07.3) Staff security rules (require two-factor, staff idle timeout, IP allow list) and approval rules (actions staff can only prepare, amount cap) are stored in the `security` and `approval` settings sections and edited on `/team/security` (permission `team.security`, owner only; the settings API hides these two sections from everyone else). Enforcement belongs to the sign-in and session code of STEP 03 and to the STEPs that own the actions (invoices, exports); this STEP delivers the stored rules and `getSection(companyId, 'security' | 'approval')` for them (DEPENDENCY_REQUESTS). Session lists and revoking staff sessions already exist on `/account/security` (STEP 03) and are linked, not rebuilt. The staff activity view reads the audit log of the company for one person.
- D10 (07.4) KYC data model: one open submission per company (`kyc_submissions`, status draft, submitted, in review, changes requested, approved, rejected, expired), four documents per submission (ID front, ID back, business registration, proof of address; `kyc_documents`, one live row per type), an append-only log of reviewer document views, and the owners' details encrypted with the `kyc` purpose and the company as scope. Documents are files in the storage contract (category `kyc`); the browser never gets a document back after upload, only names and states. Rules: 5 MB, JPEG, PNG, WebP or PDF (the storage file validator checks the content), photos at least 600 by 400 pixels, a document with a date of its own must not be expired, replacing a document removes the earlier file. The same content sent by two companies sets a duplicate flag for the reviewer. Sending needs a network that is not a VPN, proxy or Tor (`networkContext: 'kyc'`).
- D11 (07.4) `kyc` contract: `status` maps the detailed states to the five contract states (draft and expired read "not_submitted"; "changes_requested" reads "rejected" because the owner must act); `isVerified` is true only for an approved submission whose end date has not passed. An open renewal does not remove an approval that is still valid. Gated features (merchant-of-record unlock, payment and payout limits, gateway routing) are decided by STEPs 10 and 14 from this contract; the owner screen only shows the state.
