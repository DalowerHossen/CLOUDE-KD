# STEP 07 decisions

- D1 (07.1) Tenant settings are one table, `company_settings`, with one row per company and section and a jsonb value. Each section has a strict zod schema in `lib/company/sections.ts` (profile, branding, invoice, display, onboarding; later security, approval, notifications). A read fills missing keys from the defaults. A write goes through the function `kd_company_setting_save`, which checks the version (0 means create) and raises a conflict on a mismatch, then the service writes an audit entry. Text fields refuse angle brackets, so stored values can never be read as markup. The browser has no direct database access to these tables.
- D2 (07.1) Industry presets (six) only set the invoice defaults and show focus hints. The chosen industry is stored in the profile section; the chart of accounts, tax rates, templates and dashboard widgets that the feature list ties to a preset belong to the accounting, tax, invoice and dashboard STEPs, which read `profile.industry`. Not built here: interactive tour, tooltips, demo data (it needs clients and invoices from STEPs 08 and 09), the "need help" button, video tutorials, logo cropping.
- D3 (07.1) Wizard: five steps (company, logo, brand, invoicing, payments), saved after each step, resumable, skippable at any time. The payments step only explains and lets the owner finish, because payment methods are connected by the platform team (REQ-ADMIN-CONNECT). The checklist counts company details, logo, invoice defaults and the milestones first client, first invoice and first payment; milestones are recorded by the event handler `workers/onboarding/milestones.event.ts` from `client.created`, `invoice.created` and `payment.captured`. The checklist component is exported for the dashboard home (STEP 09). A day 1, 3, 7 and 14 guidance series is queued once when the wizard is first opened (template ids start with `notification.`, so the unsubscribe header applies).
- D4 (07.1) Logo: PNG, JPEG or WebP up to 1 MB, stored through the storage contract (category `logo`, encrypted); only the file id is kept. A new logo applies to documents made afterwards. The logo is read back by a plain route that serves only the signed-in company's own logo.
- D5 (07.2) Settings screens are five pages (company, branding, invoicing, notifications, display) that share one generic form driven by a field list (`lib/company/forms.ts`); the server checks every save against the strict section schema, so the list only decides what is shown. Staff with `company.read` see the values read-only; only `company.manage` (owner) saves. The version is sent with every save; a stale version answers a conflict and the screen asks for a reload. Showing other currencies next to dollar amounts is locked unless the plan has `display.multi_currency` (read through the entitlement contract, with the plan catalogue as the fallback until it is registered). The UI stays English; there is no language setting.
- D6 (07.2) The `invoice.nextNumber` setting is where numbering starts; the invoice STEP (09) owns the running counter and must not move below numbers already used. The company-level `notifications` section (who is told: owner only or owner and staff, optional summary e-mail) is stored here; STEP 05 can read it with `getSection(companyId, 'notifications')` instead of its fixed list (handoff request). Personal notification choices stay on `/notifications`.
