# STEP 06 decisions

- D1 (06.1) Cookie choice: the browser keeps it in the cookie `kd_consent` (`v<policy version>.a<0|1>.m<0|1>`, 180 days, readable by script on purpose, because no tracking script may start before it says yes). The same choice is recorded on the server through the consent contract (`analytics` and `marketing`, keyed by a random visitor id in the cookie `kd_visitor`, never by name or address) as evidence; a "no" withdraws the earlier record. Changing `COOKIE_POLICY_VERSION` asks every visitor again. Necessary cookies need no consent and are always on. Rejecting is as easy as accepting (same level, same size).
- D2 (06.1) The header builds its mega menu from the navigation fragments (`config/nav/s06.ts`, group `public-header`): top-level items with children (items whose `parent` is the top item) open a panel, and the footer columns are the top-level `public-footer` items with their children. Entries are added together with the pages they point to, so the dead-link guard never sees a link without a page. A menu entry shows a description when the string `<label key>Description` exists.
- D3 (06.1) The language policy is English only: no language switch exists. The theme toggle (light, dark, system, contrast) stays in the header.
- D4 (06.2) A public page is a list of typed blocks (hero, features, steps, pricing teaser and table, testimonials, trust, FAQ, call to action, rich text, contact form, jobs, columns), each checked by a strict schema (`lib/cms/blocks.ts`): unknown fields are refused, links must be an internal path, an https address or a mailto address, block ids are unique. Built-in content of the eight core pages lives in `lib/cms/defaults/` and is shown until the CMS stores a version (06.3). The defaults make only claims the product supports (encryption, two-factor sign-in, audit trail, access control); there are no invented customer names, counts or testimonials, so the testimonials block shows nothing until real ones are added.
- D5 (06.2) The pricing table is built from the plan catalogue (`config/plans.ts`), the same data the entitlement service enforces, so the page cannot promise something a plan does not give. Prices are owned by billing (STEP 14): the page shows a price under a plan name only when the `prices` field of the block holds one (set in the CMS); until then it shows limits only. The pricing contract has no public price source, which is noted in the handoff.
- D6 (06.2) Contact form: honeypot field (a filled field gets the normal success answer and stores nothing), Turnstile check on the server, rate limit policy `strict` (5 a minute), message stored in `contact_messages` first and then mailed to `CONTACT_INBOX` (or the `SMTP_FROM` address) with a confirmation to the sender through templates `system.contact-received` and `system.contact-ack`. Messages are removed from view after 24 months.
- D7 (06.2) The page titles carry the brand through the title template of the root layout, so the default titles do not repeat it; the front page uses the full brand title.
- D8 (06.3) Versions: a page has at most one unfinished version (draft, waiting for approval or scheduled) and one live version; older ones are archived. Saving edits the open draft in place; publishing a draft makes the previous live version archived. Revert copies an older version into a new draft, so history is never rewritten. Stored versions win over the built-in content; a page with no stored version keeps its built-in content.
- D9 (06.3) Approval: the CEO and the super admin publish directly. A content manager's publish creates an approval request (action `cms.publish`, level L2) and the version waits as "pending approval". The approval contract has no callback, so a cron job (every 5 minutes, `cron/jobs/s06-cms.ts`) reads the decision: approved versions go live (or stay scheduled), rejected, cancelled or expired ones return to draft. The same job releases scheduled versions that are due.
- D10 (06.3) Media: images are stored through the storage contract as platform files (category `cms`, no company) and served by `/api/cms/media/[id]` without a session; the route serves only platform files of that category with an image type, so no other file can be reached through it. Uploads are limited to about 3.5 MB.
- D11 (06.3) The content manager sub-role covers the domains content, cms, blog and help. Later permissions (seo, analytics, marketing, leads) therefore reach only the CEO and the super admin until the Integrator adds the domains; this is listed in the handoff requests.
- D12 (06.3) The editor is one generic component that walks the block data, so every block type (and new ones) is editable without a form per type; the server checks every save against the strict schema and cleans rich text. The preview renders the same block components as the public page, from the unsaved content.
- D13 (06.4) The twelve legal pages (terms, privacy, refunds, cookies, DPA, sub-processors, acceptable use, SLA, GDPR, CCPA, accessibility, responsible disclosure) have built-in texts in `lib/cms/defaults/legal.ts` and are edited like any page (kind `legal`, slugs `legal/<name>`); the set is fixed (`dynamicParams = false`), so unknown addresses answer 404. The built-in texts are plain-language starting points that make no promise the product cannot keep (no certifications are claimed); the owner's lawyer should review them before launch, which is listed in the handoff.
- D14 (06.4) Acceptance log: table `legal_acceptances` (one row per subject, document and version; rows cannot be changed or deleted). The subject is the signed-in user or the random visitor id. The version identifier is `v<number>` of the stored CMS version, or `built-in-<date>` for the built-in text, so a new published version asks for a new acceptance. Accepting terms or the refund policy is also recorded through the consent contract (purposes `terms`, `refund_policy`). `hasAcceptedCurrent(subject, slug)` in `services/cms/legal.ts` is what sign-up and sign-in (STEP 03) call to ask again after a change; the public acceptance route is `/api/public-site/legal/accept`.
- D15 (06.5) Blog: posts, authors, categories and tags live in their own tables (migration S06_004). The body is written in a Tiptap editor (headings 2 and 3, lists, quotes, code, links) and cleaned with DOMPurify on the server before it is stored (`sanitizeHtml`); the public page cleans it again when it shows it. Editing history is kept by a database trigger whenever the title, summary or body changes; a version can be restored into the draft. Saves use the version number (optimistic lock). Status flow: draft, waiting for approval (content managers, action `blog.publish`, level L2, applied by the cron job `blog-publish` every 5 minutes), scheduled, published. Only the CEO and the super admin edit a published post in place or delete it.
- D16 (06.5) Blog extras: the reading time is computed at 200 words a minute; related posts are scored by shared tags (2 points each) and category (1 point); search uses a stored full-text vector (PostgreSQL `websearch`); archive pages and tag pages are not indexed (`noindex, follow`) to avoid thin duplicate pages; share buttons are plain links (no script, no tracking); the view counter stores a number only and no visitor data. Reader comments are not built: they would need moderation tooling and spam control that the platform has no owner for yet. Cover and author images come from the CMS media library.
- D17 (06.5) The public layout has no `loading.tsx`: with one, the page streams after the status line is sent, so a missing page would answer 200 instead of 404. Public pages are cached (ISR) or fast, so no loading screen is needed.
- D18 (06.6) Structured data: eight types (Organization, WebSite with site search, BreadcrumbList, Article, FAQPage, SoftwareApplication, JobPosting, ItemList) built by pure functions in `lib/seo/jsonld.ts`; which page carries which is decided in `lib/seo/page-jsonld.ts` from the slug and blocks (front page: Organization, WebSite and SoftwareApplication; every other page: BreadcrumbList; FAQ and job blocks add FAQPage and JobPosting). The script text escapes angle brackets and ampersands. SoftwareApplication lists no offer, because prices belong to billing (STEP 14) and the site only shows prices the owner typed into the pricing block. The component uses `dangerouslySetInnerHTML` with an inline lint exception and one entry in the `DANGEROUS_INNER_HTML` list of `scripts/verify/step04-static.mjs`; the handoff asks the Integrator to move both into the shared configuration.
- D19 (06.6) Crawler rules: `app/robots.ts` disallows the API and every product, sign-in, portal, payment and admin prefix (`config/seo.ts`, checked against the route folders by `scripts/verify/step06-seo.ts`), and points to the sitemap. The sitemap lists only public pages (core pages, the twelve legal pages, the blog and its posts) and leaves out pages the CMS marks hidden. The product layouts already set `noindex`. Tag and archive pages are `noindex, follow`. `/.well-known/security.txt` points to the contact page and the responsible disclosure page.
- D20 (06.6) Share images are generated per page and post at `/api/seo/og/<page|post>/<slug>` (1200 by 630) from the stored title, never from text in the address. A post with a cover image uses the cover instead. Verification tags (Google, Bing, Yandex, Pinterest, Facebook), social profiles and organization facts are stored in `seo_settings` and edited in `/admin/seo` by the CEO and the super admin with a fresh step-up. The audit (`/admin/seo`) checks title and description length and duplicates, the main heading, image descriptions, internal links and thin blog posts; it reads stored content and makes no network calls. 301 redirect management is not built: pages cannot be renamed after publishing in this STEP, and the proxy chain (STEP 01) is the right owner of redirects; listed in the handoff.
- D21 (06.7) Providers: Google Analytics 4, Google Tag Manager and Microsoft Clarity need the analytics choice; Meta Pixel, TikTok, LinkedIn Insight, X and Pinterest need the marketing choice (`lib/analytics/providers.ts`). Identifiers are stored in `seo_settings` (key `pixels`), checked by a pattern per provider, edited in `/admin/analytics` by the CEO and the super admin with a fresh step-up. The loader (`components/marketing/tracking-loader.tsx`) is mounted only by the public frame, reads the consent cookie, and refuses to run on private prefixes; the providers' scripts are added by code, so no inline script is needed and the nonce policy stays unchanged (the loader's own script is trusted, `strict-dynamic`). GA4 is started with anonymized addresses and without Google signals or ad personalization.
- D22 (06.7) First-party counters: `analytics_daily` counts page views and four conversion events per day and page, with no cookie, no address and no visitor id, so it needs no consent (this is also the cookie-free analytics option). Private addresses are never counted. Meta conversions API: a server route forwards `Lead` and `CompleteRegistration` only when the consent cookie says marketing is allowed and `META_CAPI_ACCESS_TOKEN` is set; the browser and the server use the same event id so Meta counts one event. The loaders were written from the providers' public snippet shapes; outbound access to their documentation was blocked in this session, so the owner must confirm each provider in its own test tool after setting the identifiers (listed in the handoff).
- D23 (06.7) Content security policy: the current policy (`connect-src 'self'`, `img-src 'self' data: blob:`) blocks the data the providers send, so providers load but cannot report. This is a safe failure. The origins each provider needs are listed in `lib/analytics/providers.ts` (`originsFor`); the Integrator is asked in DEPENDENCY_REQUESTS to let `buildCsp` add them to `connect-src` and `img-src` for public paths only, and only when the `kd_consent` cookie allows the category.
- D24 (06.8) Scope kept to what the platform can run without owners or data it does not have: testimonials manager (the testimonials block with no items of its own shows approved ones; none are invented), lead capture with explicit unchecked agreement (consent contract purpose `email_marketing`, honeypot, Turnstile, strict rate limit) and a leads list with status, e-mail campaigns to agreed leads only (plain text, `marketing.` templates carry the one-click unsubscribe header and honor the suppression list; sending needs a fresh step-up and is limited to the CEO and the super admin; the campaign is claimed before sending so a double click cannot send twice), a three-message welcome series queued with `sendAt` (now, +3 days, +7 days), three free tools (invoice generator with three templates, late fee calculator, sales tax calculator; browser only, nothing stored, money through decimal.js), and A/B experiments on the hero block.
- D25 (06.8) A/B framework: an experiment has 2 to 4 variants (the first is always `control`), a goal event, a status (draft, running, stopped) and an optional winner. Visitors who allowed analytics cookies get a random variant that is remembered in the cookie `kd_ab`; others always see the control and are not counted. Exposures and goals are anonymous daily counters (`ab_stats`). Significance is a two-proportion z-test (`lib/marketing/significance.ts`) and counts only with at least 100 visitors per variant and p below 0.05. Choosing a winner stops the experiment and the server renders the winning text from then on. Variants can change the hero heading, summary and main button text only.
- D26 (06.8) Not built: a separate template library download page (the three invoice templates live inside the generator), customer-facing retention tools beyond the welcome series (they need the product data of other STEPs), and drip steps that are editable per lead segment. The e-mail texts of the series are templates in the catalogue and can be edited with the template manager of STEP 05.
- D27 (06.9) Help center and knowledge base: articles are CMS pages of kind `help` with addresses `help/<category>/<name>`; eight built-in articles in `lib/cms/defaults/help.ts` describe the product in general terms and are overridden by edited versions; staff add articles in `/admin/cms?kind=help`. The help center search filters the list in the browser, so no query leaves the page. FAQ, roadmap and changelog are normal CMS pages (built-in text, no invented dates, customers or promises; the roadmap says it is a plan, not a promise). A catch-all route `app/(public)/[slug]` serves pages that staff add under one address; application addresses (`lib/cms/reserved.ts`) cannot be taken.
- D28 (06.9) Status page: it shows the overall state, two services we can measure (the website that rendered the page and the database check of the health service), a 90-day bar chart and the incident list. From the incident service it keeps only the title, severity, state and times; summaries, causes, notes and post-mortems stay internal because no field in the incident record is marked as public. SEV4 incidents are not shown. The uptime figure is an estimate from recorded SEV1 and SEV2 incident times and says so. Payments and e-mail are not listed as services because the platform has no probe for them yet; STEP 04 can add probes and a public summary field (DEPENDENCY_REQUESTS).
