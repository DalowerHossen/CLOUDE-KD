# STEP 06 decisions

- D1 (06.1) Cookie choice: the browser keeps it in the cookie `kd_consent` (`v<policy version>.a<0|1>.m<0|1>`, 180 days, readable by script on purpose, because no tracking script may start before it says yes). The same choice is recorded on the server through the consent contract (`analytics` and `marketing`, keyed by a random visitor id in the cookie `kd_visitor`, never by name or address) as evidence; a "no" withdraws the earlier record. Changing `COOKIE_POLICY_VERSION` asks every visitor again. Necessary cookies need no consent and are always on. Rejecting is as easy as accepting (same level, same size).
- D2 (06.1) The header builds its mega menu from the navigation fragments (`config/nav/s06.ts`, group `public-header`): top-level items with children (items whose `parent` is the top item) open a panel, and the footer columns are the top-level `public-footer` items with their children. Entries are added together with the pages they point to, so the dead-link guard never sees a link without a page. A menu entry shows a description when the string `<label key>Description` exists.
- D3 (06.1) The language policy is English only: no language switch exists. The theme toggle (light, dark, system, contrast) stays in the header.
- D4 (06.2) A public page is a list of typed blocks (hero, features, steps, pricing teaser and table, testimonials, trust, FAQ, call to action, rich text, contact form, jobs, columns), each checked by a strict schema (`lib/cms/blocks.ts`): unknown fields are refused, links must be an internal path, an https address or a mailto address, block ids are unique. Built-in content of the eight core pages lives in `lib/cms/defaults/` and is shown until the CMS stores a version (06.3). The defaults make only claims the product supports (encryption, two-factor sign-in, audit trail, access control); there are no invented customer names, counts or testimonials, so the testimonials block shows nothing until real ones are added.
- D5 (06.2) The pricing table is built from the plan catalogue (`config/plans.ts`), the same data the entitlement service enforces, so the page cannot promise something a plan does not give. Prices are owned by billing (STEP 14): the page shows a price under a plan name only when the `prices` field of the block holds one (set in the CMS); until then it shows limits only. The pricing contract has no public price source, which is noted in the handoff.
- D6 (06.2) Contact form: honeypot field (a filled field gets the normal success answer and stores nothing), Turnstile check on the server, rate limit policy `strict` (5 a minute), message stored in `contact_messages` first and then mailed to `CONTACT_INBOX` (or the `SMTP_FROM` address) with a confirmation to the sender through templates `system.contact-received` and `system.contact-ack`. Messages are removed from view after 24 months.
- D7 (06.2) The page titles carry the brand through the title template of the root layout, so the default titles do not repeat it; the front page uses the full brand title.
