# STEP 16 - Decisions

D1 (2026-10-23). Where the code lives (16.1.a). `OWNERSHIP_MAP.md` gives STEP 16 `lib/integrations/`, `services/publicapi/` and `app/api/{public/v1,integrations,...}/`, but no `app/api/developers/`, so the key management routes are under `app/api/integrations/keys/**` (the plan said `app/api/developers/keys`). The developer pages stay under `app/(dashboard)/developers` (16.1.b). Pure rules (scopes, key format, rate window, anomaly rule) are in `lib/integrations/api-key-rules.ts`; the wrapper of the public API routes is `lib/integrations/public-api.ts`; limits and names are in `config/s16-api.ts`. Strings are in `lib/i18n/strings/en/s16-developers.ts` (namespace `s16Developers`).

D2 (2026-10-23). API keys (16.1.a). Migration `S16_001_api_keys`. A key is `kd_live_` or `kd_test_` followed by 32 random base62 characters (about 190 bits, rejection sampling, no modulo bias). The secret is in the answer that makes the key (or the rotated key) and nowhere else; the database keeps its SHA-256 hash (a fast hash is right for a random secret of this size), the first 14 characters and the last 4 for display. Because the secret is in the answer, the create and rotate routes are deliberately not idempotent (a stored replay would put the secret into the idempotency store); they need a fresh identity check (300 seconds) and a double submit makes a second key that the owner can revoke. A key has scopes `read:<resource>` and `write:<resource>` for clients, products, invoices, estimates, webhooks and `read:payments` (payments are read only), a write scope also allows the read of the same resource, a limit per minute (1 to 10000, default 120), an optional expiry (at most 730 days), at most 50 active keys per company, and a mode: `live` or `sandbox` (the test prefix and the mode must agree, a database check). The identity of a key (hash, prefix, mode, company, the key it replaced) never changes and a revoked key stays revoked (database triggers). Rotation makes a new key with the same name, scopes, mode and limit and sets the old key to expire after the overlap (0 to 72 hours, 24 by default, never later than its own expiry); a key can be rotated once while its replacement is active. Unknown, revoked and expired keys give the same 401; repeated failures from one address use the `strict` policy of the security contract and raise a `token_abuse` event when the limit is hit. A key outside its scope gets 403 naming the scope. The limit is a counter per key and minute in `api_key_windows` (one atomic upsert; `X-RateLimit-Limit`, `-Remaining` and `-Reset` on every answer including errors, `Retry-After` on 429). Usage per key and day is in `api_key_usage`; the last use time and address are marked at most once a minute; every 200th request of a day checks whether the day is more than five times the average of the seven days before (days without requests count as zero) and raises a security event `other` with reason `api_usage_anomaly`. Audit entries are written for create, change, rotate and revoke (and by the database trigger on `api_keys`), and every mutating public call must return an audit entry (metadata holds the key id and mode). Not built: an IP allow list per key, key expiry notices (16.11 cron), the usage page (16.1.b).

D3 (2026-10-23). Sandbox (16.1.a). The tables of the other STEPs have no sandbox flag and may not be changed, so a sandbox key never touches them: it reads and writes `api_sandbox_records` (resource, a jsonb document, optimistic version), a table of its own. The first sandbox key of a company seeds a small demo set (two clients, two products, two invoices, an estimate and a payment) and a reset removes the records and seeds again. The wrapper tells the handlers the mode of the key; the resource layer of 16.1.b must choose the source with `dataSourceFor(mode)`. The isolation is therefore a rule of the resource layer plus the separate table, not a database wall; the check script tests the rule and 16.1.b tests each resource with a sandbox key.

D4 (2026-10-23). Public API resources (16.1.b). Routes are under `app/api/public/v1/**`, each wrapped by `withPublicApi`; the endpoint list is one registry (`lib/integrations/public-registry.ts`) that the OpenAPI 3.1 document (`/api/public/v1/openapi.json`, open to everyone, cached 5 minutes), the documentation page and the check script all read, and the check script fails when a route file has no registry entry or the other way round. The JSON schemas of the document are made from the same Zod schemas that validate the requests (`lib/integrations/openapi.ts`; the project has no schema generator package, so the converter handles the kinds of schema the API uses and throws on any other). Field names are snake_case; money is text with up to four decimals; the currency is always `USD`; every answer is `{ data, meta }` with `meta.correlation_id`, `meta.version` and, for lists, `meta.next_cursor`. Live reads: clients, products, invoices (with items on the single read), payments and estimates, read straight from the tables of STEP 08, 09 and 10 with the company of the key (read only, soft-deleted rows excluded). Internal fields are never returned: cost prices, notes, credit and risk fields, processor ids, payer address and country, card identity, internal notes. Lists use a cursor on the id (UUID v7, time ordered; the cursor is the id in base64url and anything else is refused with 400), `limit` 1 to 100 (25), `sort` `created_desc` or `created_asc`, `updated_since`, and filters per resource (status, email, kind, sku, client id, issue date range, invoice id). Sandbox keys read the sandbox table with the same filters, sort and paging in memory (`selectRows`, tested without a database). Writes: `POST` for clients, products, invoices and estimates (an `Idempotency-Key` is required) and `PATCH` for clients and products (the `version` is required, a mismatch gives 409) work on sandbox keys only; a live key gets 501 with a plain message (BLOCKERS B1, request R1). Sandbox invoices and estimates are drafts priced with `Money` (quantity times price, tax per line, rounded half up to four places); an invoice or estimate needs an existing sandbox client. Payments are read only. Audit entries of sandbox writes use resource types `sandbox_client`, `sandbox_product`, `sandbox_invoice` and `sandbox_estimate`. Open endpoint: `GET /api/public/v1/status` returns `operational`, the version and the time (the incident feed of feature 2148 is not built: the incidents of STEP 04 are internal and have no public flag). Not built: the payment link endpoint (B1), client statements, the SDK package (feature 2206; a package request is not made yet), webhook endpoint resources (16.2), the usage dashboard beyond the per-key table, and an API changelog feed. Developer portal (`/developers`, owner only): the key list with state, last use and expiry, a form that makes a key and shows the secret once with a copy button, rotate (secret shown once, old key works 24 more hours), revoke, a key page with scopes, limit and 30 days of usage, and the documentation page (authentication, limits, pagination, idempotency, sandbox, errors, money, the endpoint table and a changelog). The key actions need the fresh identity check; the pages say so when it is missing.

D5 (2026-10-23). Outgoing webhooks (16.2). Migration `S16_002_webhooks_out` (`webhook_endpoints`, `webhook_deliveries` as the outbox, `webhook_delivery_attempts` as the append-only log). Events: a company subscribes an endpoint to business events only (`WEBHOOK_EVENTS` in `config/s16-api.ts`: invoice, estimate, payment, dispute, payout, client and subscription events); security, sign-in, KYC, file, expense and payroll events never leave the platform (feature 2164's "payment.received" is `payment.captured`). The body is `{ id, type, created, api_version, data }` where `data` is the payload of the domain event as the owning STEP published it; the platform does not filter that payload, so a STEP must not put internal fields into the payload of a subscribable event. Fan-out: the event handler `webhookout.fan-out` writes one delivery per active endpoint of the event's company that subscribed (a database unique index on endpoint and event makes a second delivery of the same event change nothing). Sending: the cron job `s16-webhooks` runs every minute, takes due deliveries with a claim function (`for update skip locked`, 60 second lock) and sends each; the first try therefore happens within a minute of the event. Signing: `X-KD-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`; during the 24 hour overlap after a secret rotation the header holds two `v1` values (new and old secret); other headers are `X-KD-Event`, `X-KD-Event-Id` (the receiver's dedupe key), `X-KD-Delivery` and `X-KD-Attempt`. The secret is `whsec_` plus 40 random characters, shown once, kept encrypted with the encryption contract (purpose `oauth-tokens`, scope the company) and decrypted only to sign. The create and rotate routes are not idempotent for the same reason as API keys (D2). Retries: eight tries in all, after a failed try 1 minute, 5 minutes, 30 minutes, 2, 6, 12 and 24 hours; then the delivery is `dead`. Any 2xx is success; 3xx is a failure (redirects are never followed), and so are timeouts (10 seconds), connection and certificate errors. Switch-off: after 10 failed tries in a row (across deliveries; any success resets the count) the endpoint becomes `disabled`, the owner is told (audit entry and notification) and no automatic delivery is sent; setting it active again clears the count; an owner may also pause an endpoint. A deleted, paused or switched-off endpoint cancels its waiting deliveries. Test ping: one signed `webhook.test` event sent at once and answered in the request; it works for a paused or switched-off endpoint and never changes the failure count. Replay: a finished delivery (not one still waiting) is copied as a new `replay` delivery with the original payload and a fresh signature time, tried with the full retry schedule, and only for an active endpoint. The SSRF guard (`lib/integrations/ssrf.ts`) has two layers: when the address is saved (and again before every try) it must be https, with no credentials or fragment, port 443 or 1024 to 65535, a host name that is not an IP address in any spelling (decimal, hex, octal and short forms are normalised by the URL parser and then refused) and not `localhost`, a single label, or ending in `.local`, `.internal`, `.localhost`, `.lan`, `.localdomain`, `.home.arpa`, `.corp`, `.intranet` or `.private`; at connect time the host name is resolved, every address must be public (IPv4 private, loopback, link-local including the cloud metadata address, shared, documentation, multicast and reserved ranges; IPv6 loopback, unique local, link-local, multicast, documentation, Teredo, and IPv4 inside mapped, NAT64 and 6to4 addresses), and the connection goes to the address that was checked so the name cannot change in between. The answer body is read up to 2000 characters. Limits: 20 endpoints per company. Pages: `/developers/webhooks` (list, add with the secret shown once, test, pause or switch on, remove, and the instructions for checking a request) and an endpoint page with the secret ending, the old secret's end time, the switch-off reason, the delivery log and a send-again button. Permissions `integrations.webhook.read` and `.manage` (owner by default). Not built: a public API resource for webhook endpoints (scopes `read:webhooks` and `write:webhooks` exist and are used by 16.6), per-event filters on payload fields, a per-endpoint rate limit, mutual TLS, an IP allow list for the receiver's side (our sending addresses are not fixed), and e-mail to the owner when an endpoint is switched off (the in-app notice is sent).

D6 (2026-10-23). WhatsApp: connection, templates, sending, inbound, consent (16.3.a). Migration `S16_003_whatsapp` (`whatsapp_accounts`, `whatsapp_templates`, `whatsapp_contacts`, `whatsapp_messages`). Facts come from the official Meta pages read this session (`docs/integrations/whatsapp.md`, with sources, date and the list of what was not read). Each company brings its own WhatsApp Business Account and Meta app (the access token of a system user and the app secret, both encrypted with purpose `oauth-tokens`); there is one account per company. The webhook address is per account, `/api/webhooks/whatsapp/<random 32 character key>`, so the platform knows which app secret to check; the verify token is made by the platform, shown once and kept as a hash. A new account starts in sandbox mode: nothing is sent to Meta, templates are approved at once and sent messages are recorded as delivered with a made-up id, so the whole flow can be tried; the owner switches to live. The Graph API version is `v26.0` (the version of the send-message pages; one setting in `config/s16-whatsapp.ts`). Sending: free text (at most 4096 characters) needs the person's 24 hour window to be open (the person wrote in the last 24 hours); a template needs the status APPROVED; both need the person to have opted in or the window to be open, and never go to a person who opted out. The rule is applied twice: in the service before anything is written (with a plain reason) and in the database (a trigger refuses an outgoing message to someone who opted out, or who neither opted in nor wrote in 24 hours). Opt-in is recorded by the owner with where the person agreed (source), or by the person with a start word; opt-out by the owner or by a stop word. The stop and start words are our own rule (STOP, STOP ALL, UNSUBSCRIBE, CANCEL, END, QUIT, OPT OUT, OPTOUT; START, UNSTOP, SUBSCRIBE; exact match after trimming and dropping punctuation, so "please stop" does not opt out) because Meta's pages list none. A person who opted out is not set back to "no decision". Decisions are also written to the platform consent log (purpose `whatsapp`) on a best-effort basis; the contacts table, per company, is the source of truth because the consent contract looks a subject up without a company. An idempotency key makes a repeated send return the first message (unique per company). The inbound webhook checks `X-Hub-Signature-256` against the account's app secret before the body is parsed; a bad signature raises a `webhook_signature_invalid` security event and answers 401; an unknown key answers 404; the GET handshake answers 403 for every failure (unknown address, wrong mode, wrong token). It stores each incoming message once by its id (a repeated delivery changes nothing and Meta's retries are safe), opens the 24 hour window, applies stop and start words, moves our messages forward by status (sent, delivered, read, failed; a status never goes back, and failed and read are final, in code and in the database; a read can arrive without a delivered), and updates the template status from `message_template_status_update` events. Templates: header (text only), body, footer, positional or named parameters with example values, no buttons, no media header; created at Meta through `POST /{waba}/message_templates`, listed and synced with the default fields, deleted with the template id so only that language goes. Not built (not read in the documentation or outside 16.3.a): media messages and the media upload API (inbound media is stored as its type only), template buttons and media headers, the template library (16.3.a lists it in the feature list; it needs the library endpoint, not read), template editing, the Application Subscriptions API (the owner subscribes in the Meta dashboard), automation rules, campaigns and bulk sending and the tier limit (16.3.b), a WhatsApp number per client picker, and a live test against Meta (the host `graph.facebook.com` is not reachable from this environment).

D7 (2026-10-23). WhatsApp automation: rules, campaigns, delivery reports (16.3.b). Migration `S16_004_whatsapp_automation` (`whatsapp_rules`, `whatsapp_rule_runs`, `whatsapp_campaigns`, `whatsapp_campaign_items`, a `daily_limit` column on the account, and the function `kd_whatsapp_template_recipients_24h`). Rules: a rule starts on one of seven events (invoice sent, paid or overdue; payment captured, failed or refunded; client created) or a number of days (0 to 60) before an invoice falls due; it sends one template whose body parameters are filled from text and from tokens (`{client.name}`, `{client.contact_name}`, `{invoice.number}`, `{invoice.total}`, `{invoice.amount_due}`, `{invoice.due_date}`, `{payment.amount}`); the tokens a rule may use depend on its trigger (checked when the rule is saved). The client is found from the ids in the event payload (`clientId`, `invoiceId`, `paymentId`; only real UUIDs are used) by reading the client, invoice and payment tables read only; an event with none of these (the payload shapes were read in STEP 08, 09 and 10 on 2026-10-23) finds no client and the run is skipped with that reason. A new rule is off and a dry run: a dry run records the text that would be sent and sends nothing; the owner switches it on and then to live. A client who asked not to be contacted is always left out; a client who asked for no payment reminders is left out of overdue and due-date rules. A run is written once per rule and source (the event id, or `due_soon:<invoice id>`), so a repeated event or a second daily sweep sends nothing twice; a delay (0 to 7 days) holds the run until its time; the cron job every minute sends due runs, puts runs stuck in "working" for 10 minutes back, and a run that errors three times is marked failed. The message goes through the same `deliver` path as a manual send with the idempotency key `rule:<run id>`, so the opt-in rule, the 24 hour window and the approved-template rule apply; if one of them refuses, the run is "left out" with that reason. Campaigns: a draft has a template, values (client tokens only), a segment (tags, lowest and highest balance owed on open invoices, no invoice since a date, has open invoices or not, only people who opted in, which is the default) and a dry-run switch (the default). Starting a draft fixes the audience (up to 5000 people; one row per phone number; clients with no valid number, who asked not to be contacted, who opted out or who never opted in are kept as left-out rows with the reason) and makes it running, or scheduled for a future time. Every minute a batch of 20 people per running campaign is sent, never beyond the daily limit: the count is the number of different people who got a template message from the company in the last 24 hours (failed ones not counted; people inside an open window are counted too, which is more careful than Meta, whose limit counts conversations started outside a window). The limit starts at 250, is updated from Meta's `whatsapp_business_manager_messaging_limit` field when the connection is checked, and the owner may set it lower; what does not fit waits for the next day. A started campaign cannot change its template, values or segment (database), moves only forward (draft, scheduled, running, paused, then finished or cancelled; the last two are final) and an item that was sent never changes. Failed items that retrying could fix (not "the number is not on WhatsApp" or "sender equals recipient") are copied into a new follow-up campaign on request, because a finished campaign is final. The report shows the people by status, the messages by delivery state from the status webhook (accepted, delivered, read, not delivered), the delivered and read share (one decimal), the reasons messages failed and people were left out, and the first 100 people with their text. Starting or repeating a live campaign needs a fresh identity check and an idempotency key. New permission `whatsapp.campaigns.manage` (owner by default); rules use `whatsapp.manage`. Not built: a CSV export of the report, per-client values other than the client name (no custom fields), scheduling a campaign by the page (the API accepts a time), sending campaign messages as free text inside an open window, per-day send time windows (quiet hours), A/B tests (16.9), and the WhatsApp template library.

D8 (2026-10-23). Social media: connections, adapters, composer, publishing (16.4.a, part 1). The sub-step is split: 16.4.a covers the framework and the networks whose documentation could be read (Facebook Pages, Instagram, Threads, and a sandbox network); the other four (LinkedIn, X, Telegram, Pinterest) become 16.4.a2 and wait for their documentation hosts to be allowed (BLOCKERS B3). Facts, sources, date and what was not read are in `docs/integrations/social.md`. Migration `S16_005_social` (`social_accounts`, `social_posts`, `social_hashtag_groups`). Adding a network later is one adapter file in `lib/social/adapters/` and one line in `lib/social/registry.ts`. Connection: by pasting an access token and the id the network shows (the Page id, the Instagram professional account id, the Threads user id); the token is sealed with purpose `oauth-tokens` (scoped to the company), never returned, and replaced by pasting a new one; an optional "valid for N days" is kept for the expiry notice; the OAuth authorization windows and the code exchange were not read and are not built. A check reads the name of the account from the network (Facebook `name`, Instagram `username`); a refusal that cannot be retried marks the account "connect again". Writing: a post has text, an optional https link, an optional https image address (Instagram needs a JPEG; the networks fetch the image themselves, so it must be public; files from the company's storage are not offered because it is not known that their signed links can be fetched by Meta), a hashtag group that is added on a new line without repeating a tag, and an optional time. Each network's rules are checked while typing and again before sending: Instagram needs an image (JPEG), a caption of at most 2200 characters, 30 hashtags and 20 mentions, and shows no link; Threads allows 500 characters where an emoji counts as its UTF-8 bytes (our reading of the page's note; other characters count one), needs text or an image and takes links in the text; Facebook takes text, a link or one image (not a link and an image together). Publishing: a post is claimed (draft, scheduled or failed to publishing, one worker only) and sent. Facebook publishes at once (`/feed` with message and link, or `/photos` with the image address; the permalink is built as documented). Instagram makes the container, reads its status up to five times two seconds apart, and publishes; if the container is still in progress the post waits and the cron job finishes it. Threads makes the container and the cron job publishes it about 30 seconds later as Meta recommends. A temporary failure (network, 429, server error, Meta rate-limit codes 4, 17, 32, 613) is tried again after 5, 10 minutes (three tries); anything else is final and shown on the post; a 401 also marks the account "connect again". Limit per account in a moving 24 hours: Instagram 50 (the pages read say both 100 and 50; the lower figure is used and is one setting), Threads 250, Facebook none documented; a scheduled post that hits the limit is moved an hour later. The cron job `s16-social` (every minute) publishes due scheduled posts and finishes waiting ones, and fails a post stuck in "publishing" for 30 minutes. A post moves one way, and what was sent cannot be changed (database). Hashtag groups: up to 50 per company, up to 30 tags each. Pages: `/social` (accounts, hashtag groups) and `/social/posts` (composer with counts and problems, list with publish and cancel). Permissions: `social.read`, `social.manage` (accounts, with a fresh identity check) and `social.post`. Tokens are never put into an address, a log or an error text (a Meta read sends the token in an Authorization header; a write sends it in the body or header as the page shows). Not built here (moved to 16.4.b or not read): the calendar view, recurring schedules, auto-post rules, the evergreen queue, approval before publishing, post analytics, share buttons and widgets, Pinterest, Telegram, LinkedIn and X, native Facebook scheduling, video, stories, reels and carousels, deleting or editing a published post, and token refresh for Threads (the refresh call was not read).

D9 (2026-10-23). Social media: schedules, rules, approval, evergreen queue, link tracking, analytics, share buttons (16.4.b). Migration `S16_006_social_schedule` (settings, approval history, schedules, rules, rule runs, evergreen items and plans, tracked links with hourly clicks, post statistics, columns on posts and accounts, a redefined post guard, and the function `kd_social_click`). Schedules: days of the week and a time in an IANA time zone (names checked with `Intl`); the clock arithmetic is ours (`lib/social/schedule.ts`, a local day and time to UTC, with the clock changes handled and tested for Dhaka, Kolkata and New York). A schedule makes a post for each coming slot 14 days ahead (at most 30 per run); the cron job `social-hourly` makes them again every hour; a database unique index on schedule and slot makes each slot once. Switching a schedule off, changing or removing it cancels the posts it made that have not gone out and frees their slots, then makes them again from the new pattern. Calendar: a month grid (times in UTC), a list of drafts and scheduled posts with a move form and cancel. Daily frequency: an account may be given a lower limit per 24 hours than its network; the lower of the two applies (Instagram 50 stays the network figure of D8). Approval: a company setting; when on, a post must be approved before it is published. A scheduled post (made by hand, by a schedule, a rule or the evergreen queue) is sent for approval at once; a draft is sent with a button. The request goes through the approval service with the action `social.post.publish` (level L1, 24 hours); the owner decides on `/social/approvals` (permission `social.approve`, staff cannot); a refusal needs a reason and sends the post back to drafts. Changing the text of a post that is waiting or approved removes the approval (the database refuses to publish a changed approved post and a post whose approval is pending or refused). A post nobody answers is approved by itself after the hours the company chose (empty: never; cron every 15 minutes), and the history says so. Every step is added to an append-only history (`social_post_approvals`). The publishing job skips posts that wait for or were refused approval, so they cannot hold up other posts. Rules: "when the trigger key is fired, make a post for these accounts from this text"; the text may use `{title}`, `{url}`, `{summary}` and `{image}` only (other names are refused when the rule is saved); a rule is off and a dry run when made (it records the text it would have made); it makes drafts or posts that go out one minute later (still subject to approval); a source is handled once per rule (the run row is written first and is the claim); posts that break a network's rules are left out with the reason. The platform has no content events yet, so rules are started with `POST /api/social/rules/fire` (REQUEST R5). Changing a rule needs a fresh identity check. Evergreen: items with up to six text variants used in turn, a priority 1 to 5 and the account; a plan per account (every N days at a local time, with a time zone); the cron job (15 minutes) posts the item with the highest priority that was shared longest ago, and if its text breaks a rule of the network tries the next (up to five); a short queue is noted in the audit log once a week and shown on the page. Link tracking: when a post is published, each https address in its text (and its link) is replaced by `<site>/api/social/l/<code>` (10 random base62 characters, at most 5 per post); the saved post keeps the original; the route counts the click (a database function that updates the link and the hour in one statement) and answers 302 to the stored address only, so it is not an open redirect (404 for an unknown code, rate limit `download` per address, no referrer). Tracking can be switched off for the company. No visitor data is kept, only counts per hour. Analytics: posts published in the period against the one before, clicks, posts per account, the best hours by clicks (UTC for now), the top posts by clicks, and for Threads posts the numbers read through the insights call (views, likes, replies, reposts, quotes, shares and our engagement rate; refreshed hourly, at most every 6 hours per post). Share buttons: `components/social/share-bar.tsx` offers copy link, the share sheet of the device where the browser has one, and an e-mail link; no network script is loaded. Not built: insights of Facebook and Instagram posts (the pages were not read), follower growth, the social proof widget and footer links to the company's own accounts (STEP 06 owns the public pages), Open Graph cards, share counters, share URLs of the networks (the pages were not readable), bulk upload of posts by file, an approval chain with several levels, timezone choice on the analytics page, and event workers for rules (R5).

D10 (2026-10-23). Automation tools: Zapier, Make, browser extension (16.6). No migration (hook subscriptions are rows of `webhook_endpoints` with the `source` of 16.2). The Zapier and Make documentation was not read (those hosts are not reachable and the sub-step writes only our own endpoints, which the two tools call; no code calls Zapier or Make). The two tools therefore use one set of plain REST endpoints under `/api/public/v1/automation/**` (not `app/api/integrations/{zapier,make}` as planned, because key-authenticated writes cannot sit behind the browser CSRF check; `/api/public/` is the exempt prefix). Authentication is the API key with its scopes; OAuth 2.0 sign-in (features 2190, 2194, 2201) is not built. Triggers (features 2181 to 2184): polling endpoints `GET .../triggers/{invoice-paid|client-created|payment-received|estimate-approved}` return the latest events newest first (limit 1 to 100, optional `since`), each with a stable `id` (the record id, one event per record) and `event_time` (paid time, creation time, capture time, decision time), so a repeat poll returns the same ids and the tool tells new from old by id; they need the read scope of the resource. Hook subscription: `POST .../hooks` (trigger, source `zapier` or `make`, target URL) makes a webhook endpoint of source zapier or make for the matching event, so signing, retries, the delivery log, the SSRF guard and the switch-off rule are those of D5; the signing secret is in the answer and shown once, so the call is not idempotent (as for keys); `DELETE .../hooks/{id}` removes only hooks of source zapier or make. Live keys only (sandbox keys get 501 for hooks because no real event ever happens). Actions: create client, invoice and estimate are the existing POST endpoints (sandbox keys only until request R1 is met); `POST .../actions/record-payment-note` adds a note to a payment (sandbox keys only; the scope is `write:invoices` because payments have no write scope). `send_invoice` and `record_payment` as a real payment are not built (the contracts have no operation for them, R1). Summary endpoint `GET .../summary` (read:invoices): counts of draft, open, overdue and paid invoices and the amount still owed from the latest 100 invoices. A key acts as a person for the records it makes: the id of the key is stored as `created_by` of a hook. D11 (2026-10-23). Receipt OCR with Google Cloud Vision (16.8). Migration `S16_009_ocr` (`ocr_settings`, `ocr_jobs`, the claim function `kd_claim_ocr_jobs`). Documentation: the web pages of Cloud Vision redirect to a host that is blocked here, so the official API description (the Google API discovery document, revision 20260918) was read instead; what it covers and what it does not (prices, quotas, size limits, PDF, service account tokens, error meanings) is in `docs/integrations/google-vision.md`. Each company brings its own Google API key (sent as the `key` parameter, the only way the description shows; kept encrypted with purpose `oauth-tokens`; never returned, never in a log or an error text) and must agree, with a recorded time and person, that receipt images are sent to Google; Google chooses the region (no `parent` is set). OCR is off until the key and the consent exist (a database check). Request: one image, feature `DOCUMENT_TEXT_DETECTION` (the dense text mode the description recommends for documents), optional language hints (up to five). Only JPEG and PNG up to 4 MB (our own limit; the real one was not read) are sent; a PDF fails with a plain message and the expense service is told `null`. Queue: a receipt that the expense service stored with status pending becomes a job (unique per receipt) by the cron job `ocr-jobs` (every minute) or by the owner; the cron job claims up to five due jobs with a lock of five minutes (a job whose lock ran out is claimed again), reads the image, extracts the fields, tells the expense service through `services/ocr/ports.ts` (`applyOcrResult`, the one direct cross-STEP call, requests R2 of this STEP and R6 of STEP 15), and marks the job done after that. A temporary failure (network, 429, 5xx, Google status 4, 8 or 14) is tried again after 2 and 10 minutes, three tries in all; a refusal (wrong key, API not enabled, bad image) is final at once. A final failure sets the job `failed` and calls `applyOcrResult(..., null)` exactly once (a flag claimed in the database before the call; if the call itself fails the flag is released so it can be tried again). A job that read nothing useful fails with "Nothing could be read" and the same `null`. A company reads at most its daily limit (default 200, up to 5000) in 24 hours; over the limit, jobs wait an hour without using a try. Extraction (pure, `lib/ocr/extract-rules.ts`): lines are rebuilt from the symbols and their detected breaks, each with the mean confidence of its words. Vendor: the first of the first eight lines that has mostly letters and is not a title, address, phone, web address or number line. Date: ISO, "12 Mar 2026", "March 12, 2026" and numeric dates; when both numbers could be the month, the company's setting (day first or month first) decides and the rule's confidence is 0.65; impossible dates, dates before 2000 and dates more than a day ahead are refused. Total: the last line labelled grand total, total due, amount due, balance due or total (subtotals, total tax, total items and similar are skipped), with the amount on the same line or alone on the next; with no label, the largest amount with cents at confidence 0.4. Tax: lines labelled tax, VAT, GST (CGST, SGST, IGST), HST or PST (tax numbers, titles and rates are skipped); a "total tax" line wins, several tax lines are added (confidence 0.7); a tax larger than the total is dropped. Amounts are understood as `1,234.56`, `1.234,56` and `12,50`, percentages are skipped, and everything is USD text with four decimals through `Money`. The confidence of a field is the lower of the rule's own confidence and the OCR confidence of the words of the line it came from, so a blurry line lowers every field taken from it; fields below 0.7 are marked "check" on the page. Manual correction: the owner edits vendor, date, total and tax of a read receipt (strict input); corrected fields count as confidence 1 and go to the expense service again; "read again" puts a done or failed job back in the queue (a repeat is the owner's decision, so the failure flag is reset). The text of the receipt is not stored, only the four fields and their confidence. Permissions `integrations.ocr.read` and `integrations.ocr.manage` (owner); saving settings needs a fresh identity check. Not built: PDF and multi-page files (`files.annotate` was not read), the other providers, line item extraction, currency detection (USD only), automatic creation of an expense from a receipt (the expense form offers the fields as suggestions; there is no event in the contract list for it), receipt de-duplication by content beyond the checksum STEP 15 already has, a dedicated region setting, per-key quota display, and a live test (no Google key was available).

A campaign can be cancelled (waiting messages are cancelled); pausing is not offered.
