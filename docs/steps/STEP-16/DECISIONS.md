# STEP 16 - Decisions

D1 (2026-10-23). Where the code lives (16.1.a). `OWNERSHIP_MAP.md` gives STEP 16 `lib/integrations/`, `services/publicapi/` and `app/api/{public/v1,integrations,...}/`, but no `app/api/developers/`, so the key management routes are under `app/api/integrations/keys/**` (the plan said `app/api/developers/keys`). The developer pages stay under `app/(dashboard)/developers` (16.1.b). Pure rules (scopes, key format, rate window, anomaly rule) are in `lib/integrations/api-key-rules.ts`; the wrapper of the public API routes is `lib/integrations/public-api.ts`; limits and names are in `config/s16-api.ts`. Strings are in `lib/i18n/strings/en/s16-developers.ts` (namespace `s16Developers`).

D2 (2026-10-23). API keys (16.1.a). Migration `S16_001_api_keys`. A key is `kd_live_` or `kd_test_` followed by 32 random base62 characters (about 190 bits, rejection sampling, no modulo bias). The secret is in the answer that makes the key (or the rotated key) and nowhere else; the database keeps its SHA-256 hash (a fast hash is right for a random secret of this size), the first 14 characters and the last 4 for display. Because the secret is in the answer, the create and rotate routes are deliberately not idempotent (a stored replay would put the secret into the idempotency store); they need a fresh identity check (300 seconds) and a double submit makes a second key that the owner can revoke. A key has scopes `read:<resource>` and `write:<resource>` for clients, products, invoices, estimates, webhooks and `read:payments` (payments are read only), a write scope also allows the read of the same resource, a limit per minute (1 to 10000, default 120), an optional expiry (at most 730 days), at most 50 active keys per company, and a mode: `live` or `sandbox` (the test prefix and the mode must agree, a database check). The identity of a key (hash, prefix, mode, company, the key it replaced) never changes and a revoked key stays revoked (database triggers). Rotation makes a new key with the same name, scopes, mode and limit and sets the old key to expire after the overlap (0 to 72 hours, 24 by default, never later than its own expiry); a key can be rotated once while its replacement is active. Unknown, revoked and expired keys give the same 401; repeated failures from one address use the `strict` policy of the security contract and raise a `token_abuse` event when the limit is hit. A key outside its scope gets 403 naming the scope. The limit is a counter per key and minute in `api_key_windows` (one atomic upsert; `X-RateLimit-Limit`, `-Remaining` and `-Reset` on every answer including errors, `Retry-After` on 429). Usage per key and day is in `api_key_usage`; the last use time and address are marked at most once a minute; every 200th request of a day checks whether the day is more than five times the average of the seven days before (days without requests count as zero) and raises a security event `other` with reason `api_usage_anomaly`. Audit entries are written for create, change, rotate and revoke (and by the database trigger on `api_keys`), and every mutating public call must return an audit entry (metadata holds the key id and mode). Not built: an IP allow list per key, key expiry notices (16.11 cron), the usage page (16.1.b).

D3 (2026-10-23). Sandbox (16.1.a). The tables of the other STEPs have no sandbox flag and may not be changed, so a sandbox key never touches them: it reads and writes `api_sandbox_records` (resource, a jsonb document, optimistic version), a table of its own. The first sandbox key of a company seeds a small demo set (two clients, two products, two invoices, an estimate and a payment) and a reset removes the records and seeds again. The wrapper tells the handlers the mode of the key; the resource layer of 16.1.b must choose the source with `dataSourceFor(mode)`. The isolation is therefore a rule of the resource layer plus the separate table, not a database wall; the check script tests the rule and 16.1.b tests each resource with a sandbox key.

D4 (2026-10-23). Public API resources (16.1.b). Routes are under `app/api/public/v1/**`, each wrapped by `withPublicApi`; the endpoint list is one registry (`lib/integrations/public-registry.ts`) that the OpenAPI 3.1 document (`/api/public/v1/openapi.json`, open to everyone, cached 5 minutes), the documentation page and the check script all read, and the check script fails when a route file has no registry entry or the other way round. The JSON schemas of the document are made from the same Zod schemas that validate the requests (`lib/integrations/openapi.ts`; the project has no schema generator package, so the converter handles the kinds of schema the API uses and throws on any other). Field names are snake_case; money is text with up to four decimals; the currency is always `USD`; every answer is `{ data, meta }` with `meta.correlation_id`, `meta.version` and, for lists, `meta.next_cursor`. Live reads: clients, products, invoices (with items on the single read), payments and estimates, read straight from the tables of STEP 08, 09 and 10 with the company of the key (read only, soft-deleted rows excluded). Internal fields are never returned: cost prices, notes, credit and risk fields, processor ids, payer address and country, card identity, internal notes. Lists use a cursor on the id (UUID v7, time ordered; the cursor is the id in base64url and anything else is refused with 400), `limit` 1 to 100 (25), `sort` `created_desc` or `created_asc`, `updated_since`, and filters per resource (status, email, kind, sku, client id, issue date range, invoice id). Sandbox keys read the sandbox table with the same filters, sort and paging in memory (`selectRows`, tested without a database). Writes: `POST` for clients, products, invoices and estimates (an `Idempotency-Key` is required) and `PATCH` for clients and products (the `version` is required, a mismatch gives 409) work on sandbox keys only; a live key gets 501 with a plain message (BLOCKERS B1, request R1). Sandbox invoices and estimates are drafts priced with `Money` (quantity times price, tax per line, rounded half up to four places); an invoice or estimate needs an existing sandbox client. Payments are read only. Audit entries of sandbox writes use resource types `sandbox_client`, `sandbox_product`, `sandbox_invoice` and `sandbox_estimate`. Open endpoint: `GET /api/public/v1/status` returns `operational`, the version and the time (the incident feed of feature 2148 is not built: the incidents of STEP 04 are internal and have no public flag). Not built: the payment link endpoint (B1), client statements, the SDK package (feature 2206; a package request is not made yet), webhook endpoint resources (16.2), the usage dashboard beyond the per-key table, and an API changelog feed. Developer portal (`/developers`, owner only): the key list with state, last use and expiry, a form that makes a key and shows the secret once with a copy button, rotate (secret shown once, old key works 24 more hours), revoke, a key page with scopes, limit and 30 days of usage, and the documentation page (authentication, limits, pagination, idempotency, sandbox, errors, money, the endpoint table and a changelog). The key actions need the fresh identity check; the pages say so when it is missing.

D5 (2026-10-23). Outgoing webhooks (16.2). Migration `S16_002_webhooks_out` (`webhook_endpoints`, `webhook_deliveries` as the outbox, `webhook_delivery_attempts` as the append-only log). Events: a company subscribes an endpoint to business events only (`WEBHOOK_EVENTS` in `config/s16-api.ts`: invoice, estimate, payment, dispute, payout, client and subscription events); security, sign-in, KYC, file, expense and payroll events never leave the platform (feature 2164's "payment.received" is `payment.captured`). The body is `{ id, type, created, api_version, data }` where `data` is the payload of the domain event as the owning STEP published it; the platform does not filter that payload, so a STEP must not put internal fields into the payload of a subscribable event. Fan-out: the event handler `webhookout.fan-out` writes one delivery per active endpoint of the event's company that subscribed (a database unique index on endpoint and event makes a second delivery of the same event change nothing). Sending: the cron job `s16-webhooks` runs every minute, takes due deliveries with a claim function (`for update skip locked`, 60 second lock) and sends each; the first try therefore happens within a minute of the event. Signing: `X-KD-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">`; during the 24 hour overlap after a secret rotation the header holds two `v1` values (new and old secret); other headers are `X-KD-Event`, `X-KD-Event-Id` (the receiver's dedupe key), `X-KD-Delivery` and `X-KD-Attempt`. The secret is `whsec_` plus 40 random characters, shown once, kept encrypted with the encryption contract (purpose `oauth-tokens`, scope the company) and decrypted only to sign. The create and rotate routes are not idempotent for the same reason as API keys (D2). Retries: eight tries in all, after a failed try 1 minute, 5 minutes, 30 minutes, 2, 6, 12 and 24 hours; then the delivery is `dead`. Any 2xx is success; 3xx is a failure (redirects are never followed), and so are timeouts (10 seconds), connection and certificate errors. Switch-off: after 10 failed tries in a row (across deliveries; any success resets the count) the endpoint becomes `disabled`, the owner is told (audit entry and notification) and no automatic delivery is sent; setting it active again clears the count; an owner may also pause an endpoint. A deleted, paused or switched-off endpoint cancels its waiting deliveries. Test ping: one signed `webhook.test` event sent at once and answered in the request; it works for a paused or switched-off endpoint and never changes the failure count. Replay: a finished delivery (not one still waiting) is copied as a new `replay` delivery with the original payload and a fresh signature time, tried with the full retry schedule, and only for an active endpoint. The SSRF guard (`lib/integrations/ssrf.ts`) has two layers: when the address is saved (and again before every try) it must be https, with no credentials or fragment, port 443 or 1024 to 65535, a host name that is not an IP address in any spelling (decimal, hex, octal and short forms are normalised by the URL parser and then refused) and not `localhost`, a single label, or ending in `.local`, `.internal`, `.localhost`, `.lan`, `.localdomain`, `.home.arpa`, `.corp`, `.intranet` or `.private`; at connect time the host name is resolved, every address must be public (IPv4 private, loopback, link-local including the cloud metadata address, shared, documentation, multicast and reserved ranges; IPv6 loopback, unique local, link-local, multicast, documentation, Teredo, and IPv4 inside mapped, NAT64 and 6to4 addresses), and the connection goes to the address that was checked so the name cannot change in between. The answer body is read up to 2000 characters. Limits: 20 endpoints per company. Pages: `/developers/webhooks` (list, add with the secret shown once, test, pause or switch on, remove, and the instructions for checking a request) and an endpoint page with the secret ending, the old secret's end time, the switch-off reason, the delivery log and a send-again button. Permissions `integrations.webhook.read` and `.manage` (owner by default). Not built: a public API resource for webhook endpoints (scopes `read:webhooks` and `write:webhooks` exist and are used by 16.6), per-event filters on payload fields, a per-endpoint rate limit, mutual TLS, an IP allow list for the receiver's side (our sending addresses are not fixed), and e-mail to the owner when an endpoint is switched off (the in-app notice is sent).

D6 (2026-10-23). WhatsApp: connection, templates, sending, inbound, consent (16.3.a). Migration `S16_003_whatsapp` (`whatsapp_accounts`, `whatsapp_templates`, `whatsapp_contacts`, `whatsapp_messages`). Facts come from the official Meta pages read this session (`docs/integrations/whatsapp.md`, with sources, date and the list of what was not read). Each company brings its own WhatsApp Business Account and Meta app (the access token of a system user and the app secret, both encrypted with purpose `oauth-tokens`); there is one account per company. The webhook address is per account, `/api/webhooks/whatsapp/<random 32 character key>`, so the platform knows which app secret to check; the verify token is made by the platform, shown once and kept as a hash. A new account starts in sandbox mode: nothing is sent to Meta, templates are approved at once and sent messages are recorded as delivered with a made-up id, so the whole flow can be tried; the owner switches to live. The Graph API version is `v26.0` (the version of the send-message pages; one setting in `config/s16-whatsapp.ts`). Sending: free text (at most 4096 characters) needs the person's 24 hour window to be open (the person wrote in the last 24 hours); a template needs the status APPROVED; both need the person to have opted in or the window to be open, and never go to a person who opted out. The rule is applied twice: in the service before anything is written (with a plain reason) and in the database (a trigger refuses an outgoing message to someone who opted out, or who neither opted in nor wrote in 24 hours). Opt-in is recorded by the owner with where the person agreed (source), or by the person with a start word; opt-out by the owner or by a stop word. The stop and start words are our own rule (STOP, STOP ALL, UNSUBSCRIBE, CANCEL, END, QUIT, OPT OUT, OPTOUT; START, UNSTOP, SUBSCRIBE; exact match after trimming and dropping punctuation, so "please stop" does not opt out) because Meta's pages list none. A person who opted out is not set back to "no decision". Decisions are also written to the platform consent log (purpose `whatsapp`) on a best-effort basis; the contacts table, per company, is the source of truth because the consent contract looks a subject up without a company. An idempotency key makes a repeated send return the first message (unique per company). The inbound webhook checks `X-Hub-Signature-256` against the account's app secret before the body is parsed; a bad signature raises a `webhook_signature_invalid` security event and answers 401; an unknown key answers 404; the GET handshake answers 403 for every failure (unknown address, wrong mode, wrong token). It stores each incoming message once by its id (a repeated delivery changes nothing and Meta's retries are safe), opens the 24 hour window, applies stop and start words, moves our messages forward by status (sent, delivered, read, failed; a status never goes back, and failed and read are final, in code and in the database; a read can arrive without a delivered), and updates the template status from `message_template_status_update` events. Templates: header (text only), body, footer, positional or named parameters with example values, no buttons, no media header; created at Meta through `POST /{waba}/message_templates`, listed and synced with the default fields, deleted with the template id so only that language goes. Not built (not read in the documentation or outside 16.3.a): media messages and the media upload API (inbound media is stored as its type only), template buttons and media headers, the template library (16.3.a lists it in the feature list; it needs the library endpoint, not read), template editing, the Application Subscriptions API (the owner subscribes in the Meta dashboard), automation rules, campaigns and bulk sending and the tier limit (16.3.b), a WhatsApp number per client picker, and a live test against Meta (the host `graph.facebook.com` is not reachable from this environment).
