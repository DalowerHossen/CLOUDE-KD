# STEP 04 decisions

- D1 (04.1) CSP: scripts use a per-request nonce with 'strict-dynamic' and no 'unsafe-inline'. `style-src-attr 'unsafe-inline'` stays because React inline style props and the animation library need it; `<style>` elements carry the nonce. Trusted Types are sent as a report-only header first, because the Turnstile loader assigns a script URL as text; enforcement follows once the report shows no violation.
- D2 (04.1) The SSRF guard checks the address at socket open time (custom lookup) as well as before the request, so DNS rebinding cannot reach private addresses. Redirects are never followed.
- D3 (04.3) `app/layout.tsx` (STEP 01) mounts `CsrfInit`, a client component that adds the `x-csrf-token` header to every same-origin state-changing fetch call. The token is a signed cookie (`kd_csrf`, readable by script by design of the double-submit pattern); it is replaced at sign-in and sign-out. The Origin (or Referer) check is applied in addition. Server-to-server routes (`/api/webhooks/`, `/api/cron/`, `/api/public/`, `/api/health`) are exempt from CSRF and from the user-agent check because they authenticate by secret or signature.
- D4 (04.3) The proxy was run against a production build (dummy environment): headers present, `/dev/*` answers 404, empty and scanner user agents answer 403, a POST without or with a foreign origin answers 403, a POST with a valid token reaches the route, and every script tag carries the nonce.
- D5 (04.5) Network intelligence documentation check. Confirmed from search results of the provider documentation: IPQualityScore response fields (`fraud_score`, `country_code`, `proxy`, `vpn`, `tor`, `active_vpn`, `active_tor`, `connection_type`) and MaxMind anonymizer traits (`is_anonymous`, `is_anonymous_vpn`, `is_hosting_provider`, `is_public_proxy`, `is_residential_proxy`, `is_tor_exit_node`). Not confirmed online in this session: the IPQualityScore request URL (key in the path) and the MaxMind web service path and basic authentication. The adapters in `lib/security/network/providers.ts` use `https://ipqualityscore.com/api/json/ip/<key>/<ip>` and `https://geoip.maxmind.com/geoip/v2.1/insights/<ip>` with `accountId:licenseKey` as basic credentials; the owner confirms both on the provider pages when the key is created. The Tor list URL is `https://check.torproject.org/torbulkexitlist`.
- D6 (04.5) With `NETWORK_INTEL_PROVIDER=none` only the Tor exit list and the address blocks are checked, so VPN traffic cannot be detected; production needs a provider. Country blocks and geo-fencing are values in `config/security.ts` (a deploy changes them); whitelist and address blocks are edited on `/admin/security`.
- D7 (04.6/04.7) Country-based impossible travel: only the country of an address is known (from the provider cache), so "another country within 2 hours" is the signal. Risk scores live in `risk_scores` and lose 10 percent a day; every signal is also kept in `fraud_signals` (append-only). Zero-tolerance actions (ban address, end sessions, lock sign-in) run from `services/fraud/reaction.ts`, connected to security events at start-up (`config/boot/s04-security.ts`). The "alert" action is picked up by the alert engine of 04.11.
- D8 (04.7) The `security` service is registered with all six operations. `riskScore` takes the worst of user, device and address scores plus a quarter of the second worst; a blocked address counts as 100.
- D9 (04.6) `app/(dashboard)/layout.tsx` (STEP 01) mounts `DeviceCollector`. It sends a coarse hash (time zone, language, screen, platform, cores) once per browser session and is switched off on payment, card and password pages. No keyboard events are read anywhere.
- D10 (04.8) Tokens are 128-bit random values with a 128-bit HMAC signature (`HMAC_TOKEN_SECRET`); only the SHA-256 hash is stored. The signature is checked first, so guessed tokens never reach the database. Lifetimes are limited to 7, 30, 90 or 365 days and to the plan entitlement `token.expiry_days` when the entitlement service is present. More than 5 addresses on one token in 24 hours is treated as a leak and revokes it.
- D11 (04.8) OTP recipient resolvers exist for `invoice` (client e-mail) and `hub` (client id) only; other document types register their own with `registerOtpRecipientResolver`. The OTP e-mail template lives in `emails/security/`, which was added to `config/ownership.json` for STEP 04.
- D12 (04.9) `lib/webhook/` holds only generic helpers (HMAC-SHA256 hex signature, constant-time compare, timestamp window of 300 seconds, in-memory replay cache). The signed string and header names of each processor are decided by that processor's adapter from its official documentation (STEPs 10 to 12). The durable duplicate guarantee is the unique key on `webhook_events` (STEP 10) and `kd_idempotency_*`; the memory cache only stops fast repeats on one instance.
- D13 (04.10) SIEM forwards `security_events` over HTTPS only (SSRF-guarded requests, 10 s timeout, cursor on the time-ordered event id, at most 1000 events per destination per run, a failing destination never blocks the others). Supported renderings: Splunk HEC, Elastic bulk (ECS-style), Datadog logs, syslog (RFC 5424), CEF and LEEF as text over HTTPS, and a JSON gateway format for CloudWatch, Sentinel and Chronicle. Native request signing for those three (AWS SigV4, Sentinel shared key, Chronicle OAuth) is not implemented, so the owner points them at an HTTPS gateway of their own. The authorization header of each product (Splunk, ApiKey, DD-API-KEY, Bearer) follows each vendor's usual convention and was not re-read from vendor documentation in this session; the owner confirms it when the first destination is created.
- D14 (04.10) A destination starts from the newest event at the time it is created (no history replay). Credentials are encrypted with the STEP 05 encryption service (purpose `pii`); until it is installed a destination can be created without a credential only.
- D15 (04.10) Correlation rules are code (`lib/security/siem/rules.ts`); one open finding exists per rule and subject, and a repeat hit refreshes it. `onSiemFinding` lets the alert engine (04.11) hear about new findings. The fraud console API moved to `app/api/admin/security/fraud/**` because `app/api/admin/fraud` is not in the STEP 04 ownership row.
- D16 (04.11) Alert engine: one open alert per dedupe key; a repeat inside 5 minutes only counts, a repeat after 5 minutes notifies again; an unacknowledged alert moves up one level every 15 minutes (levels 0 to 2); a silence mutes every severity except critical and lasts at most 7 days; a critical alert opens a SEV1 incident by itself. Security events of high or critical severity and SIEM findings raise alerts through `config/boot/s04-alerting.ts`.
- D17 (04.11) Channels: Slack, Discord, generic webhook, PagerDuty and an SMS gateway (HTTPS) plus e-mail to the on-call roster. Payload shapes follow each product's usual incoming format (Slack `text`, Discord `content`, PagerDuty Events API v2 `routing_key`/`event_action`/`payload`); they were not re-read from vendor documentation in this session and the owner confirms them with the test button when a channel is created. SMS needs a provider-side HTTPS gateway of the owner's; no SMS provider is built in. Slack and Discord addresses contain a secret and are shown shortened.
- D18 (04.11) Incident lifecycle is enforced in the database (`kd_incident_transition`): detected, acknowledged, mitigating, resolved, closed; a resolved incident can be reopened to mitigating; SEV1 and SEV2 cannot be closed without a post-mortem of at least 20 characters. Metrics are measured over incidents detected in the last 90 days: time to detect (started to detected), to acknowledge and to resolve.
- D19 (04.11) Health: `/api/health` (liveness) and `/api/health/ready` (database) are plain route handlers without the API wrapper so probes never depend on the rate limiter or the database; they return no detail. Details are on `/admin/health` for platform staff.
- D20 (04.11) Sentry: `sentry.server.config.ts` starts with PII scrubbing (`lib/security/sentry-scrub.ts`: cookies, request bodies, query strings, auth headers and addresses removed, only the user id kept, e-mail and card-like text masked). It starts from `config/boot/s04-sentry.ts` when `SENTRY_DSN` is set. Browser and edge reporting need `instrumentation-client.ts` and an edge config, which belong to the Integrator (shared files); requested in DEPENDENCY_REQUESTS.
- D21 (04.11) Credentials of SIEM destinations and alert channels use the encryption service of STEP 05 (purpose `pii`). Until it is installed, channels and destinations that need a key cannot be saved.
- D22 (04.12) Scope items not built, with the reason: per-form one-time CSRF tokens (the signed double-submit cookie plus the Origin check protects every state-changing request, so a second token adds no protection); an Upstash limiter adapter (the adapter interface exists, the database limiter is the default); native request signing and the UDM schema for the CloudWatch, Sentinel and Chronicle forwarders (D13). Files moved to match the ownership row: alerting helpers live in `lib/security/alerting/`, the health report in `services/alerting/health.ts`, the fraud admin API in `app/api/admin/security/fraud/`.
