# STEP 11 - Requests to the Integrator

**R1 Braintree webhook destination check (STEP 10 file `lib/payment/webhook-route.ts`, `services/payment/webhook-core.ts`, contract `types/contracts/payment-adapter.ts`).** When a webhook URL is created in the Braintree Control Panel, Braintree first sends `GET <url>?bt_challenge=<hex>` and expects the body `<public key>|<HMAC-SHA1 of the challenge>` (this is the `verify` method of Braintree's own SDK; the documentation pages themselves do not describe it). The pure function is ready: `braintreeChallengeResponse(ctx, challenge)` in `lib/payment/adapters/braintree/webhook.ts`. STEP 11 may not read the credential store of STEP 10 and may not add a hook to the contract, so the route `app/api/webhooks/braintree/route.ts` only exports `POST`. Please add an optional adapter hook `webhookChallenge?(context, query: Readonly<Record<string, string>>): string | null` to the contract, a `GET` export in `processorWebhookRoute` that builds the context like `contextFor` in `webhook-core.ts` (rate limited, answers `text/plain` 200, or 404 when the hook returns null), and `export const GET = processorWebhookRoute('braintree')` is then enough in the route file (STEP 11 will add that one line when the hook exists). Until then a Braintree webhook destination cannot be created from the Control Panel; card payments themselves are not affected (no card result needs a webhook).

**R2 Content security policy for 3D Secure challenges (STEP 04 `lib/security/csp.ts` / `proxy.ts`, STEP 10 `lib/payment/csp.ts`).** BlueSnap states that its 3D Secure flow opens the card issuer's own address, which varies by issuer, and that the policy "should be as permissive as possible and leverage the `*` token; any other policy will likely result in a failure" (https://developers.bluesnap.com/v8976-Tools/reference/3-d-secure-for-api). Braintree's 3D Secure (a Cardinal challenge) likewise loads an address that its configuration returns at run time. The payment page policy lists exact origins only (`PROCESSOR_ORIGINS`), so a challenge can be blocked. Please decide a rule for the payment page, for example `frame-src https:` (and `connect-src https:`) only for processors whose 3D Secure is enabled, never for `script-src`; or leave 3D Secure off for these two processors. Until then the 3D Secure step of BlueSnap and Braintree must be tested in the sandbox with the policy on.

**R3 Status table generator (`scripts/gen-processor-status.sh`, shared `scripts/`, STEP 10 file `docs/processors/README.md`).** SCOPE item 11.9 names `scripts/gen-processor-status.sh`, but the script does not exist and `scripts/` and `docs/processors/README.md` (generated by `scripts/verify/step10-readme.ts`) are not STEP 11 paths. Please add the script (or extend the README generator) so that it reads `docs/processors/*.md` and `*.verify.md` and adds one row per processor (documentation date, sandbox status from the verify record, blockers). Until then the table in `docs/steps/STEP-11/HANDOFF.md` section 2 is the status table.

**R4 Billing contact in the checkout input (`types/contracts/payment-adapter.ts`, STEP 10 `services/payment/payments.ts`).** Verifone Checkout needs the payer's billing first and last name, address, city, country and e-mail for 3D Secure (error 126 otherwise); Authorize.Net and Square report no 3DS result. `CheckoutSessionInput` has only amount, invoice, company, return address and policy. If 3DS for Verifone is wanted, add an optional `billing` object (names, address lines, city, region, postal code, country, e-mail) to `CheckoutSessionInput`; STEP 11 then sets `supportsThreeDS: true` for Verifone.
