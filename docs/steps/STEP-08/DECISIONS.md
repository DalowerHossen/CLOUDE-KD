# STEP 08 decisions

- D1 (08.1) Clients are one table `clients` with the billing and shipping address as flat columns, tags as a text array and custom field values as small JSON; the contact people are rows in `client_contacts` (the first one is the primary contact), replaced in one database step. The billing postal code and country are required when a client is created or changed (REQ-VERIFY compares them with the payer); the quick form used while writing an invoice asks only for name, optional e-mail, postal code and country. The database allows an empty value so that imported and anonymized records can exist, and the contract returns null in that case.
- D2 (08.1) Later STEPs reach the client record through three things only: the `clients` contract (`getById`, `getBilling`), the events `client.created` and `client.updated`, and the registries in `lib/crm/hooks.ts` (delete guard, merge handler, timeline, statement, export, anonymize). The invoice STEP must register a delete guard (a client with invoices cannot be deleted, only archived); until it does, delete is allowed. The contract checks the company of the signed-in caller when there is one, so a foreign client is "not found".
- D3 (08.1) Custom fields (`custom_field_defs`) are shared by clients, products and suppliers: the owner defines key, label, kind (text, number, date, choice, yes/no), choices and "required"; values are checked against the definitions on every save and unknown keys are refused. Money in the client record (opening balance, credit limit, credit balance) is decimal text in the API and `numeric(18,4)` in the database; the credit balance is changed by the payments STEP, not by the form.
- D4 (08.2) Search is one database function (`kd_client_search`): pg_trgm similarity plus plain "contains" on name, e-mail, phone, contact person and tax number, filters (state, tag, country, risk, "owes money"), four sort orders (name, date added, balance owed, last invoice) and keyset pages (the cursor is the last row's sort value and id), always filtered by company. Wildcard characters typed by the user are plain text. Balance and last invoice come from columns on the client record that the invoice and payment STEPs keep current with `kd_client_set_balances` (they are the only writers); until then they stay zero.
- D5 (08.2) Duplicates: creating a client first asks `kd_client_duplicates` (same e-mail, same tax number, or name similarity of 0.6 or more). If anything matches, the server answers 409 `duplicate` with the candidates and the form offers "Create anyway" (`confirmDuplicate: true`). A review page lists look-alike pairs. Merge (owner only, fresh step-up) first calls the merge handlers other STEPs register (they point their records to the kept client), then one database step fills the empty fields of the kept client, combines tags and contacts (ten at most), adds balances, moves the history, soft deletes the other client and stores a snapshot in `client_merges`.
- D6 (08.2) Timeline: notes, calls, meetings and e-mail entries written in this STEP, system entries (created, archived, reactivated, merged), plus whatever the registered timeline providers return. Statement: opening balance plus open documents and payments from registered providers, aging buckets (not due, 1 to 30, 31 to 60, 61 to 90, over 90 days) added with decimal arithmetic. The statement PDF and e-mail need the `pdf` contract of STEP 09, so the statement is a printable page for now.
- D7 (08.3) Client data management: per-client export is one JSON file (record, contacts, activity, merges, privacy requests, plus sections that other STEPs add through export providers); it is audited and uses the strict rate policy. Marketing consent and the preferred way of contact are fields of the client; turning consent on or off is also written to the consent log (subject `client:<id>`, purpose `email_marketing`). "Do not contact" blocks the statement e-mail.
- D8 (08.3) Privacy requests are the company's own (the company is the controller of its clients' data), so they do not use the platform data-subject request table. Anonymize replaces names, contacts, addresses, notes, free text history and merge snapshots, keeps ids, country and all amounts so the accounts still add up, and marks the record. Delete does the same and also removes the client from the lists, and is refused while a delete guard says something depends on the client. The owner acts directly after a fresh step-up; a staff request goes through the approval engine (`client.anonymize`, level L1) and the job `client-privacy` (every 5 minutes) applies the owner's decision. Other STEPs remove their own personal data through the registered anonymize handlers.
- D9 (08.3) Bulk actions (archive, reactivate, delete, add or remove a tag, set risk, set payment terms) take up to 200 clients, show the count before applying, handle each client separately and report how many were done and why the others were not. Each kind of change also needs its own permission. The statement e-mail template is `invoice.client-statement` (the `invoice.` prefix lets a company edit the wording and keeps the unsubscribe header off documents).
- D10 (08.4) Catalog: one table `products` holds products, services and bundles (`kind`, fixed after creation); variants, bundle items and per-client prices are separate tables. SKU and barcode are unique per company without regard to case, among live items. Only physical products can track stock. Prices and costs are US dollars (`numeric(18,4)`); the default tax rate is a percentage (`numeric(7,4)`) and the tax category is one of standard, reduced, zero, exempt; the tax tables and the actual tax calculation belong to the invoice STEP. Units are free short text with suggestions. Up to five pictures per item go through the storage contract (category `attachment`) and are read only through their product by a plain handler (`GET /api/products/<id>/images/<file>`), which is added to the plain-handler list of `step04-static.mjs`.
- D11 (08.4) Price rule (`lib/catalog/resolve.ts`, `priceFor` in `services/product/client-rates.ts`): the price agreed with the client wins, then the volume tier for the quantity (the highest "from quantity" not above it), then the variant price, then the item price. The picker (`GET /api/products/picker`) returns active items (one row per active variant) with the price for one unit and the default tax rate; the invoice STEP uses it and `priceFor`. A bundle is sold as one line at its own price; the items inside it are for stock. Duplicates: same SKU, same barcode or a similar name (0.6) warn before creating; the database also refuses an exact SKU or barcode twice.
- D12 (08.4) Deleting an item is blocked while it is in a bundle or while a registered guard (`lib/catalog/hooks.ts`, for example "on an invoice") says so; archive or deactivate instead. Removing a variant is blocked by registered variant guards (the stock sub-step registers one for variants with stock).
- D13 (08.5) Stock is changed only by the database functions `kd_stock_move`, `kd_stock_transfer` and `kd_stock_move_many`. They lock the level row (`for update`), refuse a change that would take the quantity below zero (error `KD001`, nothing changes), write one row to the append-only ledger `stock_movements` (update and delete are refused by a trigger) and return the new balance. An idempotency key makes a repeat request a no-op. A transfer locks both warehouses in a fixed order so opposite transfers never deadlock. `scripts/verify/step08-stock.sh` proves this against a real database: 60 parallel sales of 20 units end with 20 sold and 40 refused, 80 opposite transfers have no deadlock, and 25 requests with one key apply once.
- D14 (08.5) Alerts: a level changes state to "low" (at or below the product's reorder level) or "out" (zero); the notification contract tells the company once per change of state (types `stock.low`, `stock.out`). The event name `stock.low` of SCOPE is not in the fixed event list of the contracts, so no domain event is published; the Integrator may add `stock.low` and `stock.out` (DEPENDENCY_REQUESTS).
- D15 (08.5) Invoices and stock: the worker `inventory.invoice-stock` takes stock when `invoice.sent` arrives and gives it back on `invoice.voided`, reading `lines: [{ productId, variantId?, quantity }]` and `invoiceId` from the event payload (the invoice STEP must send them; events without lines are ignored). The invoice id is the idempotency key. A shortage never blocks the invoice: the company is told (`stock.short`) and corrects by hand. Services, bundles and items that do not track stock are skipped. Stock confirmation "on paid" is not built because the invoice STEP decides when stock leaves; it can use either event. Adjustments always record a reason (damage, loss, return, correction, found, other); "set the counted quantity" computes the change under the lock.
- D16 (08.5) Warehouses: a default warehouse is created on first use; exactly one default per company; codes are unique; a warehouse with history can be switched off but not deleted. Registered guards stop deleting an item or removing a variant that still has stock.
- D17 (08.6a) Valuation: every receipt creates a cost layer (quantity, unit cost, optional batch number and expiry date). The method is set per product: average cost (moving average of the warehouse), first in first out, or last in first out. Outflows use layers in the order of the method (earliest expiry first, then oldest, for average and first in first out; newest first for last in first out) and the cost of the outflow is written on the ledger (`cost_total`), so cost of goods sold is a sum over the ledger, less goods that came back. A transfer copies the used layers to the other warehouse, so cost, batch and expiry travel with the goods. Costs are rounded to four decimals at each movement; stock that has no layer (older than valuation) is valued at the average cost, else the item's cost. Stock value follows the method (average: quantity times average cost; the others: open layers). Cost reports need `inventory.costs` (owner by default).
- D18 (08.6a) Batches and expiry: a batch is the layer of a receipt. The job `stock-expiry` (daily) tells the company once about each batch that expires within 14 days or already expired; `/inventory/valuation` lists batches expiring within 30 days. `number_counters` and `kd_next_number` give gap-free document numbers (used by purchase orders and inventory documents).
- D19 (08.6b) Inventory documents: goods received, goods issued, sales return, purchase return (they move stock when posted, all lines or none) and packing slip and delivery note (printable, no stock effect). Numbers come from gap-free counters per kind and year (`GRN-2026-0001`, `ISS-`, `SR-`, `PR-`, `PS-`, `DN-`, `CNT-`). A draft can be changed or cancelled; a posted document is fixed (mistakes are corrected with a return, an adjustment or a count). The client or supplier on a document is a name typed in (the supplier table arrives in 08.7); a sales return from an invoice carries the invoice number in the reference. PDF output of these documents needs the `pdf` contract of STEP 09, so the documents have a print layout for now.
- D20 (08.6b) Stock counts: starting a count of a warehouse takes a snapshot of the expected quantities (one open count per warehouse). Counted items are set to the counted quantity when the count is completed, worked out under the lock so a sale during the count is not lost; items left empty are not changed; each line keeps the applied difference. Barcode lookup finds an item or variant by barcode or SKU; the scan page reads a hardware scanner's input and, where the browser has the BarcodeDetector API, the camera. The phone camera needs HTTPS and the user's permission.
- D21 (08.7) Suppliers: name, contact, e-mail, phone, https website, tax number, category, payment terms (days), address and custom fields; archive and reactivate; delete only while no purchase order exists. Search uses the trigram function `kd_supplier_search` with keyset paging. Supplier reads need `supplier.read`, changes `supplier.write`, deletes `supplier.delete`.
- D22 (08.7) Purchase orders: numbers `PO-YYYY-NNNN` from the gap-free counter. States: draft, pending approval, approved, sent, partly received, received, cancelled. Totals are worked out on the server per line with decimal arithmetic (quantity times cost, tax per line). An owner submitting a draft approves it directly; a staff member's order creates an approval request (`po.approve`, level L1) and the job `po-approvals` (every 5 minutes) applies the owner's decision (a rejection keeps the reason on the order). Sending e-mails the supplier with template `invoice.purchase-order`; the order must be approved first. Receiving works in parts, never above the ordered quantity, through `kd_po_receive`, which posts a goods-received document and moves stock in one transaction (batch and expiry optional per line); the order becomes partly received or received. Cancelling is possible until goods arrive. PDF output needs the `pdf` contract of STEP 09; the order has a print layout.
- D23 (08.8) Supplier bills: numbers `BILL-YYYY-NNNN`; a bill can follow a purchase order (one click fills the lines with what has arrived and is not yet billed) or stand alone (free-text lines such as freight). A draft can be changed; posting runs the three-way match in the database (`kd_bill_post`): for each line tied to an order line, the quantity billed so far (this bill and earlier open bills) must not exceed the quantity received, and the cost must be within one percent of the order. A bill that fails stays a draft; only a user with `bill.override` (owner by default) can post it anyway, and the bill then shows "posted although it did not match". A bill with nothing paid on it can be voided. No accounting entry is written here: the accounting STEP will read the bills and remittances (DEPENDENCY_REQUESTS).
- D24 (08.8) Money paid to suppliers is called a "remittance" (`supplier_remittances`, numbers `RM-YYYY-NNNN`). One remittance can pay several bills of one supplier; the amounts given to the bills must add up to the amount paid and none may exceed what the bill owes (checked under row locks in `kd_supplier_remit`). The route needs an Idempotency-Key header and the database also keeps the key, so a repeat returns the first result and changes nothing. A remittance can be cancelled (`kd_supplier_remit_void`), which reopens the bills. Only the owner records remittances by default (`remittance.write`).
- D25 (08.8) Payables aging uses the same buckets as the client statement (not due, 1-30, 31-60, 61-90, over 90 days) on the due date. The supplier statement shows an opening balance, bills (raise the balance) and remittances (lower it) with a running balance, the closing balance and the aging of open bills; it has a print layout (PDF waits for the `pdf` contract of STEP 09).
- D26 (08.9) Import framework: a company uploads a `.csv` or `.xlsx` file (up to about 7 MB and 5000 rows; the upload route takes the file as base64 in JSON so it passes the same checks as every other route). The file is kept through the storage contract (encrypted, in the company's Drive or Supabase Storage) and the job row `import_jobs` keeps the target, the column mapping, the duplicate choice and the counters. Steps: upload (columns are matched to fields by name and alias), preview (every row is checked with the target's rules; rows that duplicate a record in the system or another row of the file are counted and listed; the first 50 problems and duplicates are shown), run, or cancel. The run is a background job (`transfer.import`) that works through 100 rows at a time and queues itself again; counters are saved after each row so a restart continues without repeating rows. A row is handled in one of three ways chosen before the run: skip a duplicate, overwrite the existing record, or create anyway. Failed rows (with row number and reason, at most 500 kept) never stop the import; the owner gets a notification at the end and can download the error report.
- D27 (08.9) Reading without libraries: CSV is read by `lib/transfer/csv.ts` (quotes, line breaks inside quotes, byte order mark, delimiters comma, semicolon, tab, pipe; limits on rows, columns and cell length). `.xlsx` is read by `lib/transfer/xlsx.ts` with Node's `zlib` and `fast-xml-parser` (already a dependency): only the first sheet and the shared strings are unpacked, with limits on entries (300) and unpacked size (25 MB) against zip bombs; Zip64 files are refused; dates arrive as the serial number the file stores. Every cell is cleaned (control characters and angle brackets removed, 2000 characters at most) before any rule sees it.
- D28 (08.9) Export: `POST /api/export` returns the CSV text (at most 10000 rows) for the browser to save. It needs the list's read permission and `list.export` (owner by default), is rate limited with the strict policy, and writes an audit entry (`data.exported`, with row count and filter). The file ends with a watermark line `# KD-EXPORT <export id> | <company> | <person> | <time>` that the importer ignores; cells that a spreadsheet would run as a formula are prefixed with an apostrophe. The permission `data.export` of STEP 07 (company data export) is a different thing and is not reused.
- D29 (08.10) Import rules per list, in `lib/transfer/targets.ts` (pure, so they can be checked without a database). The columns are matched by name or alias and every value goes through the same Zod schema as the screen form, so the file cannot bring in anything the form would refuse. Clients: name, billing postal code and billing country are required (like the form); tags are separated by `;`; yes/no columns accept yes, no, true, false, 1, 0. Products and services: name and price are required; bundles are not imported (they need items); a service never tracks stock; the category is given by name and must already exist. Suppliers: name is required. Display currency is always USD and portal and contact preferences take the form defaults.
- D30 (08.10) Duplicates: clients match on e-mail, else tax number, else name; products on SKU, else barcode, else name; suppliers on e-mail, else name (case ignored). "Overwrite" changes only the fields that have a value in the file; all other fields of the existing record keep their value, and the change goes through the normal update (version check, audit entry). Rows that repeat another row of the same file are counted in the check and, in "skip" mode, skipped during the run.
- D31 (08.10) Bulk actions on products (archive, set active, set inactive, delete) and suppliers (archive, reactivate, delete) take up to 200 rows, show the count before applying, handle each row alone and report which could not be changed and why (for example an item in a bundle). Each action needs `product.bulk` or `supplier.bulk` plus the permission of the change itself. The export and import buttons on the three lists appear only for people who have `list.export` or `import.manage`.
