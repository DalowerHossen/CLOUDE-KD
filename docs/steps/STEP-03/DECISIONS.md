# STEP 03 decisions

- D1 (03.1) Supabase documentation check (REQ-LOCK item 8), 2026-10-16.
  - Access problem: the session network policy denies `supabase.com` (connection refused by the egress proxy). The pages could not be fetched directly. Findings below come from web search summaries of the official pages: Auth Hooks (https://supabase.com/docs/guides/auth/auth-hooks), Password Verification Hook (https://supabase.com/docs/guides/auth/auth-hooks/password-verification-hook), MFA Verification Hook (https://supabase.com/docs/guides/auth/auth-hooks/mfa-verification-hook), self-hosted hooks (https://supabase.com/docs/guides/self-hosting/self-hosted-auth-hooks). They must be confirmed against the primary pages by the owner before production (listed in HANDOFF).
  - Findings: the Password Verification Attempt and MFA Verification Attempt hooks are limited to the Teams and Enterprise plans on hosted Supabase. The Custom Access Token hook is available on Free and Pro. A hook may return `{ error: { http_code, message } }`; Auth then fails the request with that error. Hooks must answer within 2 seconds. A missing table used by a Postgres hook blocks every sign-in. An MFA hook reject signs the user out of all sessions.
  - Decision (two layers, valid on every plan):
    1. Primary enforcement: every sign-in goes through the platform API (`POST /api/auth/login`). The API checks `auth_login_state` first, then verifies the password with the Supabase Auth admin client, and records the outcome. The browser never calls Supabase Auth with a password.
    2. Defence at the auth server: a Custom Access Token hook (`public.kd_auth_access_token_hook`, S03 migration) refuses to issue or refresh a token while `auth_login_state.locked_until` is in the future for that user id. This also blocks direct calls to the Supabase Auth endpoints on Free and Pro plans. When the project is on Teams or Enterprise, the owner may additionally enable the Password Verification Attempt and MFA Verification Attempt hooks that point to `public.kd_auth_password_hook` and `public.kd_auth_mfa_hook` (same SQL file); they record failures and reject while locked.
    3. Public sign-up and public password sign-in on the Supabase project are switched off in the dashboard (HANDOFF steps); accounts are created by the platform API with the admin client.
  - Consequence: lock state is keyed by an HMAC of the normalized identifier (unknown accounts behave identically) and also carries `user_id` once the account is known, which is what the hook reads.
- D2 (03.3-03.7) Sign-in design. The browser never sends a password to Supabase. `POST /api/auth/login` checks the lock first (database), verifies the password with a throw-away Supabase client whose session is closed at once, applies the second factor, and only then creates the real browser session with a one-time token (`generateLink` + `verifyOtp`) through the request-bound server client. The half-finished state between the two steps is a signed HttpOnly cookie (`kd_pending`, 5 minutes) that holds no session. Our own TOTP (`two_factor_factors`, `backup_codes`) is used instead of Supabase MFA because backup codes, the shared failure counter and the forced setup are required.
- D3 (03.7) Cookies: SameSite=Lax with HttpOnly and Secure (production). Strict would drop the cookie on OAuth and payment-processor return redirects. Cross-site writes are stopped by the JSON-only mutating APIs plus the origin check of the security layer (STEP 04).
- D4 (03.7) The session end time (24 hours, 30 days with "remember me", 1 hour for impersonation) is enforced by the platform in `user_sessions.expires_at` on every request, not only by the Supabase JWT lifetime. A copied cookie on another device (different device cookie hash) ends the session and raises a security event; an address change inside a session writes a login event and a security event.
- D5 (03.8) OAuth login uses our own code flow (state + PKCE S256, signed HttpOnly cookie, callback handled as page + JSON API call). Existing accounts are never linked silently: linking needs the signed-in user (`mode=link`). Provider endpoints are the documented ones for Google OpenID Connect and GitHub OAuth (the documentation hosts could not be fetched in this session, see D1 of 03.1).
- D6 (03.11) `app/(dashboard)/layout.tsx` (STEP 01 file) mounts `ImpersonationBanner`. Ending an impersonation signs the browser out; the administrator signs in again (administrator tokens are never stored).
- D7 (03.4) Reset tokens live in `auth_login_state` (columns added in S03_002): one active token per identifier, single use, cleared when a lock starts, refused while locked.
