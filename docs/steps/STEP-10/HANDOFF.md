## 4. Adapter contract: final shape and what the core expects

`types/contracts/payment-adapter.ts` is unchanged. What the core relies on, which each adapter must honour:

- idempotency keys passed by the core: `<paymentId>:authorize`, `:capture`, `:void`, `:undo`, `<refundId>:refund`; `<linkId>:session:<uuid>` for checkout sessions;
- `metadata` of `authorize` carries `paymentId`, `invoiceId`, `companyId` (use it as the processor's reference so a webhook can be matched);
- return `cardIdentity` on approvals and, when the processor provides it, on declines (the failure counters depend on it); `avsPostalCodeMatch` when the processor checks the postal code; the 3DS result in `threeDS`;
- `declineCategory` through `mapDecline`; `insufficient_funds` is never counted; `processor_fraud_signal` blocks the card;
- `verifyWebhook` checks the signature of the raw body and the replay window the processor defines; `parseWebhook` fills `eventId` (unique per processor), `type`, `processorTransactionId`; the core never trusts the body for state;
- `getTransaction` must return the current state, including `threeDS`, `cardIdentity` and `avsPostalCodeMatch` (used when the payer returns from 3DS);
- a processor that cannot hold an authorization (no `supportsAuthCapture`) must implement `charge`;
- `AUTH_VALIDITY_HOURS_BY_PROCESSOR` in `config/payment-risk.ts` and `PROCESSOR_ORIGINS` in `config/processors.ts` are filled from the documentation record of each processor.

## 5. Routing rule fields

`name`, `priority` (1 to 100000, lowest first), `processorId`, `minAmount`, `maxAmount` (USD, inclusive, empty = open), `countries` (ISO codes of the invoice billing country, empty = any), `methods` (`card`, `wallet`, `local_methods`, empty = any), `plans` (`free|pro|business|enterprise`, empty = any), `enabled`. First match decides; none -> `routing_no_match`; matched processor unusable -> `processor_unavailable`.

## 6. Review queue states

`payment_reviews.status`: `pending` -> `captured` | `voided` | `expired`. The payment is `pending_review` while the review is pending. Reasons: `postal_code_mismatch`, `postal_code_missing`, `ip_country_mismatch`, `ip_country_unknown`, `invoice_data_missing`. Hold: `min(REVIEW_HOLD_HOURS=72, authorization validity)`; the job `payment-review-expiry` voids expired holds. Deciders: permissions `payment.review.decide` (payment_processor) or `fraud.payment_review.decide` (fraud_analyst), step-up required.

Other states: payment `created -> requires_action | authorized | captured | failed | pending_review | voided`, `captured -> partially_refunded -> refunded`; refund `requested | pending_approval | processing | succeeded | failed | rejected`; webhook event `received | processed | failed | dead_letter | ignored`; payment link `active | paid | expired | revoked`.

## 9. Known issues and limits

- No real adapter exists: the end-to-end run with a processor sandbox is pending (VERIFY.md section C). The flow check uses fake processors and an in-memory database; the service code was not run against a live PostgREST.
- Card identity arrives only with the processor answer (D3): a card that is blocked or over its failure limit is detected after the authorization and then voided; for single-step processors the charge is refunded at once.
- A timeout while the processor call is in flight fails the payment (`processor_error`); an authorization that the processor made anyway is not matched by the platform until the processor's webhook arrives or an administrator checks the processor dashboard.
- Refunds do not change the invoice (R1). A refund made in the processor's own dashboard only writes an audit entry.
- Payment links need an invoice; the link token appears in the page address (the platform sends `Referrer-Policy: strict-origin-when-cross-origin`, so the path is never sent to other sites).
- The fake database in `scripts/verify` supports only the calls the payment services make.
- Report days are UTC.
