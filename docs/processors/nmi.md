## 2. Authentication and credential fields
Server calls: JSON over HTTPS; the header `Authorization: <private security key>` (the bare key, no `Bearer`); `Content-Type: application/json`. Keys are created in the Merchant Portal under Settings, Security Keys. A **public** key with Checkout permission is the "tokenization key" that identifies the merchant to the browser scripts. Credential fields (names only): `privateKey` (secret), `tokenizationKey` (not secret), `webhookSigningKey` (secret; shown on the Webhooks settings page). Money: amounts are JSON **numbers** in major units with two decimals (`x.xx`); the adapter prints them from cents as bare numbers (never through floating point) in `nmi/shared-server.ts`.

## 4. Secure form - the two modes (REQ-NMI-MODES)
- **`collectjs` (default).** Collect.js tokenizes in the browser: `<script src="https://secure.nmi.com/token/Collect.js" data-tokenization-key="...">`, then `CollectJS.configure({ variant: 'inline', fields: { ccnumber: { selector, title }, ccexp: {...}, cvv: {...} }, callback(response), lookUpCallback(response) })`. `callback` receives `{ tokenType, token, card: { number, bin, exp, type, category, hash } }`. The token is **single use and expires 24 hours after creation**. NMI states Collect.js is for existing integrations. **Submission (read 2026-10-27, Collect.js Quick Start and Advanced Integrations):** `CollectJS.configure({ paymentSelector: '#button-id', variant: 'inline', fields: { ccnumber: { selector, title, placeholder }, ccexp: {...}, cvv: {...} }, callback(response), timeoutDuration, timeoutCallback, fieldsAvailableCallback })`. NMI binds the button named by `paymentSelector`; when the payer presses it Collect.js saves the data of the iframes and calls `callback` with `response.token`. `CollectJS.startPaymentRequest(event)` does the same from code. The script tag is `<script src="https://secure.nmi.com/token/Collect.js" data-tokenization-key="PUBLIC_KEY" data-variant="inline">`, one address for sandbox and production (the sandbox is selected by the keys). `price`, `currency` and `country` are needed only for Apple Pay and Google Pay (not used). Content security policy: `script-src`, `style-src`, `connect-src` and `frame-src` need `https://secure.nmi.com` (the wallet hosts only when wallets are used). The form is written: `components/payment/processors/nmi/index.tsx`.
- **`payment_component`.** The Payment Component (npm packages `@nmipayments/nmi-pay-react` and `@nmipayments/nmi-pay`, or Gateway.js) renders the fields and tokenizes: `<NmiPayments tokenizationKey onPay onChange onExpressCheckout onFieldsAvailable />`; `onPay({ token, lookupData })` shows the component's own pay button and expects a promise of `true` (success) or an error text; `onChange({ token, complete, lookupData })` is for 3DS flows; `resetFields()` after a failed payment. The npm registry (read 2026-10-27) lists `@nmipayments/nmi-pay-react` and `@nmipayments/nmi-pay` with the latest version 1.1.1 (peer dependencies of the React package: react and react-dom `>=16.8.0 || ^19.0.0`). The package request is in `docs/steps/STEP-12/DEPENDENCY_REQUESTS.md`; the form of this mode waits for the Integrator to add the package, until then the checkout shows "unavailable" for the `payment_component` mode.
Both modes end the same way: the server receives a payment token and calls `nmi/shared-server.ts`. Our payment token = the NMI payment token.

## 5. Operations (REST v5, JSON)
- Authorize: `POST /v5/payments/auth`; sale (authorize and capture): `POST /v5/payments/sale`. Body: `amount` (number), `currency`, `payment_details: { payment_token }`, `billing_address` (`zip`, `country`, ...), `order_details` (`order_id`, `ip_address`, ...), `dup_seconds` (duplicate window), `partial_payments`, `cardholder_auth`, `cit_mit`. Answer `200 TransactionResponse`: `object: "transaction"`, `id`, `amount` (string `x.xx`), `currency`, `auth_code`, `avs_response`, `cvv_response`, `status`, `response` (`1` approved, `2` declined, `3` error), `response_text`, `response_code`, `payment_details` (`card_number` masked, `card_exp`, `card_hash`, `card_type`, `card_bin`, `cavv`, `eci`), `billing_address`, `order_details`, `actions[]` (`type`, `amount`, `success`, `response`, ...). Errors: `400/401/404` with `{ type, error_code, message, ref_id, details }`.
- Capture: `POST /v5/payments/{payment_id}/capture` `{ amount }` ("equal to or less than the authorized amount"). The adapter captures only the full authorized amount.
- Void: `POST /v5/payments/{payment_id}/void` (`void_reason` only for EMV); only unsettled payments.
- Refund: `POST /v5/payments/{payment_id}/refund` `{ amount, payment }`; only settled payments; amount `0.00` would refund everything, so the adapter always sends the real amount. A full refund of a payment that is still `pendingsettlement` is done as a void.
- Look up: `GET /v5/payments/{payment_id}` (404 not found). `condition` values in the webhook body: `pending`, `pendingsettlement`, `in_progress`, `abandoned`, `failed`, `canceled`, `complete`, `unknown`.
- Connection test (per mode): the tokenization key must be present and well formed; then `GET /v5/payments/kd-connection-check` - 404 (or 400) means the private key was accepted, 401 means refused.
- Our `processorTransactionId` is the payment `id`.

## 6. 3D Secure
3DS is a separate browser step (Gateway.js `get3DSecure()`, `createUI`, events `challenge`, `complete`, `failure`) whose result (`cavv`, `xid`, `eci`, `cardHolderAuth`, `threeDsVersion`, `directoryServerId`) is sent in `cardholder_auth`. It needs the payer's first and last name, e-mail, address, city, state, country and postal code, which the platform's checkout input does not carry (STEP 11 request R4). The adapter declares `supportsThreeDS: false`; every result is `{ requested: false, completed: false, authenticated: false, liabilityShift: null }`. Sandbox 3DS test cards exist (frictionless 4100000000000100; challenge 4100000000005000, code 12345 passes).

## 7. Card identity (REQ-CARD)
`payment_details.card_hash` ("Card hash") when the gateway returns it (type `fingerprint`); the documents do not say how it is computed or whether it is stable across payments. When it is empty the adapter builds `bin|last4|exp|type` from `card_bin`, the masked `card_number`, `card_exp` and `card_type`.

## 8. Decline mapping
Source: `response_code` (Payment API response codes) with `response` 2.
- insufficient_funds: 202, 203
- invalid_number: 220, 221, 222, 461
- invalid_expiry: 223, 224
- invalid_cvv: 225
- processor_fraud_signal: 250, 251, 252, 253
- do_not_honor: 200, 201, 204, 226, 240, 260, 261, 262, 263, 264
- processor_error: 300, 400, 410, 411, 420, 421, 440, 441, 460
- other: 430 (duplicate) and everything else
`response` 3 (error in data or system) is reported as `error`. Success code 100. AVS: ZIP matches for X, Y, D, M, 2, 6, W, Z, P, L, 1, 5; mismatch for A, 3, 7, N, C, 4, 8; the rest are unknown.

## 9. Webhooks
Created in the Merchant Portal (Settings, Webhooks, Create); the URL must be `https` with valid TLS; events are selected by category (transactions, check status, recurring, settlement, chargebacks, card updater), most with `success`, `failure` and `unknown` variants. Body: `{ event_id, event_type, event_body }`; transaction events carry `event_body.transaction_id`, `transaction_type`, `condition`, `requested_amount`, `card`, addresses. **Signature**: header `Webhook-Signature: t=<nonce>,s=<signature>`; `signature = hex(HMAC-SHA256(signing key, nonce + "." + raw body))`; the key is the "webhooks signing key" of the Webhooks settings page. The page gives no time limit for the nonce, so there is no timestamp window. Deliveries come only from `104.192.32.81` to `.87` and `104.192.36.81` to `.87` (the platform cannot check the source address in the adapter). Retries: up to 20 over 3 days while the answer is not HTTP 200.
- Events used: `transaction.sale.success`, `transaction.capture.success` -> payment.captured; `transaction.auth.success` -> payment.authorized; `transaction.void.success` -> payment.voided; `transaction.refund.success` -> payment.refunded; `transaction.sale.failure`, `.auth.failure`, `.capture.failure` -> payment.failed; everything else -> unknown (the chargeback event names are not listed).
- `event_id` is unique and used as the event id. `processorTransactionId` = `event_body.transaction_id`. The body has no timestamp, so the time of receipt is used.

## 10. Idempotency
The REST API v5 reference documents **no idempotency header**. The only duplicate protection is the `dup_seconds` window on supported processors (set to 0 to disable). The adapter sends no idempotency key and relies on the processor's default duplicate check; a retried authorization after a timeout is therefore not provably safe (known limit). Capture, void and refund read the payment first, so a repeated capture or void is answered from the stored state.

## 13. Merchant Sign-Up API (partner onboarding of sub-merchants)
Source: docs.nmi.com, API Reference: Merchant Sign-Up (read 2026-10-27). Meant for NMI Payments partners; it creates a merchant application, sends it to NMI's risk review and reports the decision by webhook. A merchant that already has an account is boarded with the Account Management endpoints instead (not used here).
- **Servers**: sandbox `https://sandbox.signup.nmi.com/api/v1`; production `https://secure.nmi.com/api/v5/signup`.
- **Authentication**: OAuth 2.0 client credentials. `POST /oauth/token` JSON `{ grant_type: "client_credentials", client_id, client_secret, scope }` where `scope` is `"*"` or a list of `packages:read`, `applications:read`, `applications:write`, `subscriptions:read`, `subscriptions:write`. Answer `{ token_type: "Bearer", expires_in, access_token }`; the token lives 60 minutes. The client id and secret are those of the "Partner OAuth2 Apps" box of the NMI keys page (the box that says: use these apps to onboard merchants via the Sign-Up API). They are not the Partner Keys and not the Merchant Keys.
- **Packages** (the form template of an application, defined by NMI for the partner): `GET /packages` (query `page`, `per_page` 10, 20, 50 or 100) and `GET /packages/{package}` (`pkg_...`) giving `package_rules[]`, `fields[]` and `collections[]`. A field has `id` (`fld_...`), `name`, `required`, `type` (`integer`, `string`, `choice`, `multiselect`, `boolean`, `decimal`, `date` as YYYY-MM-DD, `percent`, `website`, `account_number`, `email`, `phone`, `routing_number`, `ssn`, `federal_tax_id`, `postal_code`) and limits (`min`, `max`, `regex`, `choices`, `default`). A collection (`col_...`) is a repeatable group of fields with `min` and `max` records (for example owners).
- **Application**: `POST /applications` `{ package_id, fields: [{ id, value }], collections: [{ id, records: [{ id, fields: [{ id, value }] }] }] }` gives the full application (`id` `app_` plus 16 hex digits, `package_id`, `status`, `fields`, `collections`, `created_at`, `updated_at`); `GET /applications` (filters `status`, `updated_from`, and others), `GET /applications/{application}`, `PATCH /applications/{application}` (only while `draft`). Statuses: `draft`, `submitted`, `approved`, `rejected`, `underwriter_requested_information`, `requested_information_sent`, `boarded`. Errors: 404 `{ code, message }`, 422 `{ code, message, errors[] }`.
- **Legal consent**: `GET /applications/{application}/legal-consent` gives `{ url }`; the merchant must sign there before submission. NMI offers a helper script (`LegalConsent.load(url, { selector, overlay }, { onLoad, onAccepted, onError })`) whose only documented address is the sandbox one (`https://sandbox.signup.nmi.com/build/consent-helper-1.0.0.umd.js`); the production address is not stated, so the platform opens the consent URL in the merchant's own browser tab instead of embedding it.
- **Documents**: `POST /applications/{application}/documents` multipart `type` (`Void Check`, `Marketing Materials`, `3 Months of Statements`, `Driver License`, `SSN Card`, `Form SS4`, `Other`) and `file` (png, jpg, jpeg or pdf, at most 20 MB); only in `draft` or `underwriter_requested_information`. NMI recommends the three months of statements when `fld_average_ticket` is 1000 or more or `fld_high_ticket` is 2500 or more.
- **Submit**: `POST /applications/{application}/submit` (query `skip_merchant_email`); the status is then always `submitted`. When NMI asks for more (`underwriter_requested_information`) the partner answers with `POST /applications/{application}/info` `{ note }`.
- **Idempotency**: header `Idempotency-Key` (10 to 100 characters, a UUID is suitable) on every write; a replay answers with the header `Idempotent-Replayed: true`.
- **Webhooks**: `POST /subscriptions` `{ callback_url (at most 1024), secret (6 to 64 characters), events[] }` gives `sub_...`; also list, get, update and delete. Delivery body `{ event_id, event_type, event_body }`; the signature is the header `Signature` = `hash_hmac('sha256', body, secret)` (hex, over the raw body). Events: `application.updated.data.requested` (`app_id`, `dba`, `pending_reason`), `application.approved` (`app_id`, `dba`), `application.declined` and `application.cancelled` (`reject_reason`), `application.merchant.boarded` (`app_id`, `dba`, `mid`, `gateway_id`), `application.merchant.closed` (`mid`, `reject_reason`), and merchant events (`merchant.chargeback.added`, `merchant.deposit.new`, `merchant.first-batch`, `merchant.processing.start`, `merchant.processing.stop`, `merchant.residuals.published`, `merchant.retrieval.added`, `merchant.statement.new`). The body of the application events may carry `partner_identifier`. The pages give no replay window and no retry rule for these webhooks.
- **Sandbox behaviour**: the decision follows `fld_monthly_volume`: 100,000 or more gives `application.updated.data.requested`; 5,000 to 99,999 gives `application.approved`; under 5,000 gives `application.declined`.
- **Keys of a boarded merchant**: the Sign-Up API itself gives no keys. After `application.merchant.boarded` the webhook carries `mid` and `gateway_id`; the keys are created through the Partner API, section 13a.

## 14. Where each key goes in the platform (Admin, Payment processors, NMI, Credentials)
NMI's key page (My Keys) has four boxes. Each one has one place:
- **Merchant Keys, `api` key (private)** -> field "Private security key". Used for every payment, capture, void, refund and lookup.
- **Merchant Keys, `tokenization` key (public)** -> field "Tokenization (public) key". Used by the browser card form.
- **Webhooks settings page of the gateway (Settings, Webhooks)** -> field "Webhook signing key". Used to check payment webhooks sent to `/api/webhooks/nmi`.
- **Partner OAuth2 Apps, Client ID and Client Secret (Sign-Up)** -> fields "Partner OAuth2 client ID" and "Partner OAuth2 client secret". Used only to onboard merchants (section 13).
- **Partner Keys (Gateway)** -> not used by the platform yet.
- **Live API address** -> field "Live API address", only for a live account, as NMI gave it (section 3).
The sign-up webhook secret is chosen by the platform operator (6 to 64 characters), entered in "Sign-up webhook secret" and sent to NMI when the subscription is created; sign-up events arrive at `/api/webhooks/nmi-signup`.

## 13a. Partner API: merchant keys (read 2026-10-27, docs.nmi.com "Create Merchant API Keys")
`POST /v4/merchants/{gateway_id}/security_keys` on the API host (sandbox `https://sandbox.nmi.com/api`; the production address is the one the operator enters, section 3). Header `Authorization: <v4 API key generated in the Partner portal>` (the "Partner Keys" box of the key page, API: Gateway). Body `{ description (required), permissions (required, any of transaction, cart, tokenization, collectCheckout), userId (optional, the primary user by default) }`. Answer `{ objectType: "securityKey", id, keyText, userId, description, permissions }`; `keyText` is the key to use. The platform creates two keys per boarded merchant: `transaction` (the private key for the payment API) and `tokenization` (the public key of the browser form), and saves them as the company's own merchant account. The merchant's webhook signing key is not created by any call on these pages: it is shown on the merchant's Webhooks settings page, so a company account works without it and payment results are then read from NMI's direct answers.
New credential field: `partnerKey` (secret, optional).
