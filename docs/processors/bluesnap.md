## 2. Authentication and credential fields
HTTP Basic: `Authorization: Basic base64(<API user key>:<API password>)` (exactly one space after `Basic`), `Content-Type: application/json`, `Accept: application/json`; the header `bluesnap-version: 3.0` pins the API version (without it the account's setting is used). Credentials come from the Merchant Portal, Settings > API Settings; sandbox and production credentials are different. Credential fields (names only): `apiUsername` (the API user key, not secret), `apiPassword` (secret). **Authorized IPs:** BlueSnap rejects API calls from addresses that are not on the account's list (up to 15 addresses or a subnet), unless "Disable IP Checking" is selected; the page calls that option a security reduction to be used only without a static address. The platform's servers must therefore call from fixed addresses that are listed (recorded as a deployment requirement in the handoff).

## 3. Environments
API: sandbox `https://sandbox.bluesnap.com`, production `https://ws.bluesnap.com`. Browser domain for Hosted Payment Fields: sandbox `https://sandpay.bluesnap.com`, production `https://pay.bluesnap.com`; the script is `<domain>/web-sdk/5/bluesnap.js`. Using the wrong environment's URL breaks the form. BlueSnap's PCI note: in production, card-data services are limited unless Hosted Payment Fields are used (SAQ A).

## 4. Secure form
Hosted Payment Fields (iframes for number, expiry and security code). The **server creates the token first**: `POST /services/2/payment-fields-tokens` (empty body) answers `201 Created` with the token at the end of the `Location` header (read case-insensitively; HTTP/2 lower-cases header names). The token expires after 60 minutes and is single-use once a payment request has consumed it. Browser: load the script, put `<div data-bluesnap="ccn">`, `data-bluesnap="exp"` and `data-bluesnap="cvv"` in the page, call `bluesnap.hostedPaymentFieldsCreate({ token, onFieldEventHandler: { onError(tagId, errorCode, errorDescription), ... }, style, ccnPlaceHolder, expPlaceHolder, cvvPlaceHolder, '3DS': true })` after the DOM is ready, and on submit `bluesnap.hostedPaymentFieldsSubmitData(callback, threeDSecureObj)`; the callback receives `cardData` (card type, last four digits, expiry, bin, issuing country) or `error[]` (`tagId`, `errorCode`, `errorDescription`; `10` invalid or empty field, `22013` card type not accepted, `14040` token expired, `14041` token not found, `14042` no card linked to the token, `400`, `403`, `404`, `500` service errors). With the payment data bound to the token, the **token is our payment token** (`pfToken`) and the amount is fixed by the server in the payment request. To use 3D Secure, the submit button needs `data-bluesnap="submitButton"` so BlueSnap can disable it during setup, and the script should be downloaded only once per page load.

## 5. Operations (JSON, `/services/2`)
- Authorize: `POST /services/2/transactions` with `cardTransactionType: "AUTH_ONLY"`, `amount` (decimal number), `currency: "USD"`, `pfToken`, `merchantTransactionId` (1 to 50 characters, our unique reference), **`storeCard: false`** (the default is `true`, which would vault the card; we never vault), `transactionInitiator: "SHOPPER"`, `cardHolderInfo: { zip, country }` (all fields optional; the zip drives AVS). 200 answers with the `cardTransaction` object: `transactionId`, `amount`, `currency`, `cardTransactionType`, `processingInfo` (`processingStatus`, `authorizationCode`, `avsResponseCodeZip`, `avsResponseCodeAddress`, `cvvResponseCode`, ...), `creditCard` (`cardLastFourDigits`, `cardType`, `binNumber`, `cardSubType`, `issuingCountryCode`, ...), `threeDSecure` (`authenticationResult`), `fraudResultInfo`. The sample shows `processingStatus` as `success` while the table says `SUCCESS`, so it is compared case-insensitively. A refusal is **HTTP 400** with `{ message: [{ errorName, code, description, invalidProperty? }] }`.
- Capture: `PUT /services/2/transactions` with `cardTransactionType: "CAPTURE"`, `transactionId`, optional `amount` (default the whole authorization; a smaller amount is allowed, and several partial captures only when `supportsMultiPartialCapture` is true). Card schemes hold an authorization for roughly 3 to 10 days.
- Void: `PUT /services/2/transactions` with `cardTransactionType: "AUTH_REVERSAL"` and `transactionId`; only within **8 days** of the authorization; the whole amount is reversed.
- Refund: `POST /services/2/transactions/refund/{transactionId}` with optional `amount`, `reason` (up to 4000 characters), `cancelSubscriptions: false`. BlueSnap first tries to void the transaction and refunds only if it cannot; full or partial; transactions less than 2 years old. The answer has `refundTransactionId`, `refundStatus` (`SUCCESS` or `PENDING`), `amount`. Error 14004 includes "transaction has not been cleared yet, wait 3 to 7 days"; 14009 / 14022 already refunded; 14023 another refund in process; 14007 period expired.
- Look up: `GET /services/2/transactions/{transactionId}` (the full `cardTransaction`, with `refunds` and `openToCapture`).
- Fraud review: `processingStatus` `PENDING_MERCHANT_REVIEW` means the fraud service holds the transaction for the merchant; `PUT /services/2/transactions/approval?transactionid=<id>&approvetransaction=true|false` approves or cancels (not used by the adapter; the platform's review is separate).
- Connection test: there is no ping. The adapter creates a Hosted Payment Fields token (`POST /payment-fields-tokens`), which proves the user key, the password and the IP authorization, and costs nothing.
- Our `processorTransactionId` is the BlueSnap `transactionId` (it stays the same for authorization, capture and reversal); a refund result carries `refundTransactionId`.
- Authorization lifetime: the platform hold uses 72 hours (the shortest of the 3 to 10 days quoted).

## 6. 3D Secure
Supported inside Hosted Payment Fields: `'3DS': true` in the setup object and a `threeDSecureObj` passed to `hostedPaymentFieldsSubmitData` with at least `amount` (number), `currency`, and `authenticationIndicator` (`'01'` for a payment); more fields (billing name, address, city, state, zip, country, email, phone) make a frictionless result more likely. The issuer challenge opens in the page. The result is bound to the token, and the **server reads it from the transaction response**: `threeDSecure.authenticationResult` is one of `AUTHENTICATION_SUCCEEDED` (eligible for chargeback liability shift), `AUTHENTICATION_FAILED`, `AUTHENTICATION_INCOMPLETE` (challenge not finished), `AUTHENTICATION_UNAVAILABLE`, `AUTHENTICATION_BYPASSED`. Our reading: `requested` = the policy is not disabled; `completed` = a result other than incomplete is present; `authenticated` = `AUTHENTICATION_SUCCEEDED`; `liabilityShift` = true for succeeded, false for failed, bypassed and unavailable, null when there is no result. Soft declines `THREE_D_SECURITY_AUTHENTICATION_REQUIRED`, `STRONG_CUSTOMER_AUTHENTICATION_REQUIRED` and `THREE_D_SECURE_FAILURE` map to `three_ds_failed`. **Content security policy:** BlueSnap states that, because the 3D Secure URLs depend on the card issuer, the policy "should be as permissive as possible and leverage the `*` token" and that "any other policy will likely result in a failure". The platform's payment page policy lists exact origins only, so the issuer challenge can be blocked; this is recorded as request R2 for the Integrator and as a handoff limit.

## 7. Card identity (REQ-CARD)
No fingerprint or token is documented for a card that is not vaulted (and `storeCard` is false). The response's `creditCard` has `binNumber` (first 4 to 6 digits), `cardLastFourDigits` and `cardType`, but no expiry (the expiry is returned only for vaulted shoppers). The adapter builds the identity `bin|last4|brand` (type `fingerprint`) when `binNumber` is present and returns no identity otherwise (a key of brand and last four alone would match thousands of unrelated cards). Known limit: two different cards with the same BIN, last four digits and brand share an identity (rare; errs toward counting more).

## 8. Decline mapping
Source: HTTP 400 `message[].errorName` (and `code`) of the card transaction error list (read in full), the refund errors and the fraud errors. Mapping used:
- insufficient_funds: `INSUFFICIENT_FUNDS` (the sandbox card page spells the trigger `INSUFFICENT_FUNDS`; both are accepted), `LIMIT_EXCEEDED`
- invalid_number: `INVALID_CARD_NUMBER`, `INVALID_CARD_TYPE`, `TRANSACTION_CARD_NOT_VALID`
- invalid_expiry: `EXPIRED_CARD`
- invalid_cvv: `CVV_ERROR`
- three_ds_failed: `THREE_D_SECURITY_AUTHENTICATION_REQUIRED`, `STRONG_CUSTOMER_AUTHENTICATION_REQUIRED`, `THREE_D_SECURE_FAILURE`
- processor_fraud_signal: `CARD_LOST_OR_STOLEN`, `PICKUP_CARD`, `HIGH_RISK_ERROR`, `RESTRICTED_CARD`, `FRAUD_DETECTED`, `FRAUD_ERROR`
- do_not_honor: `DO_NOT_HONOR`, `CALL_ISSUER`, `PROCESSING_GENERAL_DECLINE`, `INVALID_TRANSACTION`, `ACCOUNT_CLOSED`, `NEW_ACCOUNT_INFORMATION_AVAILABLE`, `PROCESSING_TRANSACTION_NOT_AUTHORIZED`
- processor_error: `GENERAL_PAYMENT_PROCESSING_ERROR`, `PAYMENT_GENERAL_FAILURE`, `BLS_CONNECTION_PROBLEM`, `PROCESSING_TIMEOUT`, `SYSTEM_TECHNICAL_ERROR`, `THE_ISSUER_IS_UNAVAILABLE_OR_OFFLINE`, `INCORRECT_SETUP`, `REFUND_FAILED`
- everything else (including `PROCESSING_DUPLICATE`, `AUTHORIZATION_*`, `TRANSACTION_ALREADY_CAPTURED`, `INCORRECT_INFORMATION`, `INVALID_AMOUNT`, `PROCESSING_AMOUNT_ERROR`, the refund errors, request validation errors, token errors 14040 to 14042): other.
HTTP handling: 400 and 422 are normal failures; **403** can mean a role problem, a missing resource, or a request blocked by BlueSnap's defenses, and it is also what a wrong password or an unlisted IP address looks like in practice, so a 403 on the token request (connection test) is reported as "credentials, permissions or IP not accepted" and on a payment call as a failed payment with the code; 401 throws a validation error naming the credentials; 429 and 503 ("rate too high", "service temporarily unavailable") and 5xx throw (the same idempotency key is safe to retry); 409 (code 60102, the same idempotency key is still in progress) throws as well. AVS: `processingInfo.avsResponseCodeZip` `M` -> postal match true, `N` -> false, `U` and anything else -> unknown. Card code: `cvvResponseCode` is informational (BlueSnap's AVS and CVV fraud rules, set in the Merchant Portal, decide the decline).

## 9. Webhooks (IPN)
BlueSnap sends webhooks (called IPNs) as HTTP POSTs of **form-encoded** text (`transactionType=CHARGE&invoiceAmount=30.00&...`) to a URL set in the Merchant Portal or through `POST /services/2/notification-config/` (body `ipnDestinations[]` with `ipnUrl` and one `send...` flag per type: `sendAuthOnly`, `sendCharge`, `sendDecline`, `sendRefund`, `sendChargeback`, `sendChargebackStatusChanged`, `sendFraudDecline`, `sendChargePending`, ...). The page read gives no event id, and says retries happen (the search summary of the setup page speaks of up to 11 attempts, an empty HTTP 200 answer, and an optional authentication that adds the headers `bls-signature` and `bls-ipn-timestamp` with a key set in the Merchant Portal).
**Blocker B1 (docs/steps/STEP-11/BLOCKERS.md):** the algorithm of `bls-signature` (what is hashed, the key's role, the timestamp format) and BlueSnap's source addresses are on `support.bluesnap.com`, which cannot be reached here, and the pages that could be read do not describe them. The platform may not accept a webhook it cannot authenticate, and the algorithm may not be written from a third party's description. So the adapter's `verifyWebhook` **always refuses** (fail closed) and `parseWebhook` maps every IPN to `unknown` with no transaction id. Until B1 is resolved, **do not enable IPNs** for the platform URL in the Merchant Portal (each delivery would be refused with a security event). Payments, voids, captures and refunds do not depend on webhooks (their results are in the API answers); later changes (a pending refund completing, chargebacks) are read with a status check, and chargebacks are not seen automatically.

## 10. Idempotency
Header `idempotency-key` (maximum 64 characters; letters, digits and hyphens only; kept 24 hours) is accepted by Auth Only, Auth Capture, Capture, Auth Reversal and Refund. A repeat with the same key and request returns the first answer; the same key with another request is `60101` (HTTP 422); the same key while the first is running is `60102` (HTTP 409); a key that is too long or has other characters is `60103` / `60104`. The core's key contains a colon, so the adapter sends the first 40 hexadecimal characters of its SHA-256 (deterministic, so a retry sends the same value). The capture, reversal and refund requests are keyed the same way.

## 12. Limits and capabilities
`supportsAuthCapture` true; `supportsThreeDS` true (with the content security policy limit of section 6); `supportsRefund` true; `supportsPartialRefund` true; `supportsRecurring` false; `supportsPayout` false; `isMerchantOfRecord` false; one mode `hosted_fields`; currencies `USD`. `AUTH_VALIDITY_HOURS_BY_PROCESSOR.bluesnap = 72`. A refund of a transaction that has not cleared (3 to 7 days) can fail with 14004 (BlueSnap tries a void first); the failure is reported as a declined refund with that code.

## 12a. Content security policy
Origins named by the pages read: `https://sandpay.bluesnap.com` and `https://pay.bluesnap.com` (script and frames; the card icons are under `https://pay.bluesnap.com/web-sdk/5/assets/cards/`). 3D Secure needs the issuers' own origins (section 6). `PROCESSOR_ORIGINS.bluesnap` carries the two BlueSnap domains; the 3D Secure origins are request R2.
