# Authorize.Net - documentation record

## 1. Sources read

- https://developer.authorize.net/api/reference/index.html (full API reference: endpoints, authentication, createTransactionRequest and response, refund, void, prior authorization capture, getTransactionDetails, getUnsettledTransactionList, authenticateTestRequest)
- https://developer.authorize.net/api/reference/features/acceptjs.html (Accept.js and the hosted payment information form AcceptUI), /api/reference/features/payment-transactions.html (transaction types, settlement, fraud settings), /api/reference/features/webhooks.html (webhooks)
- https://developer.authorize.net/hello_world/testing_guide.html and /hello_world/sandbox.html (sandbox), https://developer.authorize.net/api/reference/responseCodes.html with its data file https://developer.authorize.net/api/reference/dist/json/responseCodes.json (479 response codes)

- **Not reachable from this environment:** `api.authorize.net` (the XSD at /xml/v1/schema/AnetApiSchema.xsd) and `apitest.authorize.net` are refused by the network policy. The element order below therefore comes from Authorize.Net's own open-source SDK bindings (`AuthorizeNet/sdk-python`, `authorizenet/apicontractsv1.py`, generated from the XSD on 2024-08-28), checked against the order of the reference page. The sandbox API cannot be called from here even with credentials unless the network policy allows those two hosts.

## 2. Authentication and credential fields
Every call carries `merchantAuthentication: { name: <API Login ID>, transactionKey: <Transaction Key> }` in the body (no header). The browser form needs the API Login ID and the **Public Client Key** (it cannot start a transaction, so it is safe in the page). Webhooks are signed with the **Signature Key**. All four come from the Merchant Interface: Account > Settings > Security Settings > General Security Settings > API Credentials and Keys, and Manage Public Client Key. Credential fields (names only): `apiLoginId` (not secret; up to 25 characters), `transactionKey` (secret; up to 16 characters), `publicClientKey` (not secret), `signatureKey` (secret). Sandbox and production credentials are separate; using one in the other environment gives response reason code 13.

## 3. Environments
JSON POST to one URL: sandbox `https://apitest.authorize.net/xml/v1/request.api`, production `https://api.authorize.net/xml/v1/request.api`; `Content-Type: application/json`. The API is XML-based and JSON is translated to XML, so **the order of elements must follow the schema** (otherwise the request is refused); the orders used are in section 5. Browser scripts: sandbox `https://jstest.authorize.net/v3/AcceptUI.js`, production `https://js.authorize.net/v3/AcceptUI.js` (hosted form); the plain `Accept.js` (v1) is for forms that type the card number in the merchant's own inputs and is **not used** (it would put card entry in our page). Sandbox account: https://developer.authorize.net/hello_world/sandbox.html ; keep the sandbox in Live Mode (test-mode transactions are not stored and return transaction id 0).

## 4. Secure form
The hosted payment information form of Accept.js (AcceptUI): a button of class `AcceptUI` with data attributes `data-apiLoginID`, `data-clientKey`, `data-billingAddressOptions='{"show":true,"required":true}'`, `data-paymentOptions='{"showCreditCard":true,"showBankAccount":false}'`, `data-acceptUIFormBtnTxt`, `data-acceptUIFormHeaderTxt` and `data-responseHandler="<global function name>"`. The script must be loaded **after** the button exists. Clicking opens Authorize.Net's own lightbox with the card number, expiry, card code and (optionally) name and postal code. The response handler receives `{ opaqueData: { dataDescriptor, dataValue }, messages: { resultCode, message[] }, encryptedCardData: { cardNumber (masked), expDate, bin }, customerInformation }`. The nonce `dataDescriptor` + `dataValue` replaces the card in the API call and is valid for **15 minutes**. If the form's postal code field is used, the nonce carries it and AVS uses it (a `billTo.zip` in the API call would override it). Our payment token = `dataDescriptor` and `dataValue` joined with `:` (the descriptor has no colon). Messages: `I_WC_01` success; errors `E_WC_*` (full list read, e.g. `E_WC_21` wrong API Login ID or client key).

## 5. Operations (createTransactionRequest, JSON)
Body: `{ createTransactionRequest: { merchantAuthentication, refId, transactionRequest } }`; `refId` is echoed (up to 20 characters). Element order inside `transactionRequest`: transactionType, amount, currencyCode, payment, profile, solution, callId, terminalNumber, authCode, refTransId, splitTenderId, order, lineItems, tax, duty, shipping, taxExempt, poNumber, customer, billTo, shipTo, customerIP, cardholderAuthentication, retail, employeeId, transactionSettings, userFields, ... Inside `payment`: creditCard, bankAccount, trackData, encryptedTrackData, payPal, opaqueData; inside `opaqueData`: dataDescriptor, dataValue. Inside `order`: invoiceNumber (20 characters at most), description. The response `createTransactionResponse` has `messages` (`resultCode` `Ok` or `Error`, `message[]` with `code` and `text`) and `transactionResponse`: responseCode, authCode, avsResultCode, cvvResultCode, cavvResultCode, transId, refTransID, transHash, accountNumber (masked, e.g. `XXXX0015`), accountType, `messages[]` (`code`, `description`), `errors[]` (`errorCode`, `errorText`), networkTransId. Amounts are decimal text (`"120.50"`).
- Authorize: `transactionType: authOnlyTransaction`, `amount`, `payment.opaqueData`, `order.invoiceNumber`, `customerIP` (IPv4, dot-decimal, 15 characters at most). `responseCode`: `1` approved, `2` declined, `3` error, `4` held for review.
- Capture: `priorAuthCaptureTransaction` with `amount` (optional when capturing the whole amount) and `refTransId`. Allowed within 30 days of the authorization, once per authorization, for at most the authorized amount (a smaller amount is allowed; more needs a new authorization).
- Void: `voidTransaction` with `refTransId`; only before settlement (error 327 or 310 otherwise).
- Refund: `refundTransaction` with `amount`, `payment.creditCard` = `{ cardNumber: <last four digits>, expirationDate: "XXXX" }` and `refTransId`; only after the transaction **settled** (error 50 "awaiting settlement and cannot be refunded"), up to the settled amount in total (errors 51, 55), within 180 days of settlement by default. The last four digits are read from the original transaction's masked `accountNumber`. A refund is a new transaction with its own `transId`.
- Look up: `getTransactionDetailsRequest { merchantAuthentication, transId }` -> `transaction` with `transactionStatus` (authorizedPendingCapture, capturedPendingSettlement, settledSuccessfully, refundPendingSettlement, refundSettledSuccessfully, voided, declined, expired, couldNotVoid, communicationError, generalError, settlementError, approvedReview, failedReview, underReview, FDSPendingReview, FDSAuthorizedPendingReview, returnedItem), `responseCode`, `responseReasonCode`, `AVSResponse`, `cardCodeResponse`, `authAmount`, `settleAmount`, `payment.creditCard.cardNumber`.
- Connection test: `authenticateTestRequest { merchantAuthentication }` (answers `Ok` when the Login ID and Transaction Key are valid for the environment).
- Our `processorTransactionId` is the **transId** of the authorization (it stays the handle for capture, void and refund); a refund result carries the refund's own `transId`.
- Authorization lifetime: an authorization that is not captured within **30 days** expires. The platform hold uses the default of 168 hours.
- Settlement: after a capture Authorize.Net settles within 24 hours; the payment is then refundable and no longer voidable.

## 6. 3D Secure
The reference lists `cardholderAuthentication` (authenticationIndicator and cardholderAuthenticationValue for results of a **third-party** 3D Secure product) as **deprecated and not to be used**, and describes no 3D Secure of its own in the pages read. So `supportsThreeDS` is false, the platform asks for the `disabled` policy, and every result is `{ requested: false, completed: false, authenticated: false, liabilityShift: null }`. Response reason codes 116, 117 and 118 concern those authentication values and are not produced by this adapter. Known limit recorded for the handoff.

## 7. Card identity (REQ-CARD)
The server only ever sees the masked number (`XXXX1111`) and the card brand; no fingerprint or token is documented for a card that is not stored in a customer profile (storing a card is not done here). The bin and expiry that the browser form reports (`encryptedCardData`) come from the payer's browser and cannot be trusted. A key made of brand and last four digits alone would match about ten thousand unrelated cards and could block innocent payers. So the adapter returns **no card identity** (`null`); the core then skips the identity-based rules (blacklist and per-card limits) for this processor. Known limit recorded for the handoff.

## 8. Decline mapping
Source: `transactionResponse.errors[0].errorCode` (the response reason code; the data file with 479 codes was read in full) and `responseCode`. Mapping used:
- insufficient_funds: none documented as a distinct code (the issuer's reason is not passed on).
- invalid_number: `6`, `37`, `315`, `200`
- invalid_expiry: `7`, `8`, `316`, `317`, `201`
- invalid_cvv: `44` (processor declined the card code), `65` (card code filter), `45` (AVS and card code filters), `78`
- three_ds_failed: none.
- processor_fraud_signal: `4` (response code "pick up card" per the code table), `41`, `250` (blocked IP), `251` (fraud filter), `254` (declined after manual review)
- do_not_honor: `2`, `3` (voice authorization referral), `128`
- processor_error: `19` to `26`, `35`, `57` to `63`, `120` to `122`, `170` to `173`, `180`, `181`, `192`, `261`, `901`, `36`, `52`, `152`, `209`, `220`, `223`, `224`, `24`, `29` to `31`, `34`, `38`, `43`
- everything else (including `27` and `127` AVS mismatch, `11` and `318` duplicate, `13` wrong credentials, `17` and `28` card type not accepted): other. Credential errors (`13`, `32`, `123`) throw a validation error that names the credentials; HTTP 5xx or an unreadable answer throws (retry is possible; there is no idempotency key, see section 10).
Held for review: `responseCode` `4` (reason codes 104 to 110, 193, 252, 253) is a **pending** result, not a decline. AVS: `avsResultCode` `Y`, `Z`, `W`, `X` -> postal match true; `A`, `N` -> false; `B`, `E`, `G`, `P`, `R`, `S`, `U` -> unknown. Card code: `cvvResultCode` `M` matched, `N` not matched (informational; the merchant's filters decide the decline). The AVS and card code filters are set in the Merchant Interface (Basic Fraud Settings); a mismatch then arrives as a decline with reason code 27, 44, 45 or 65.

## 9. Webhooks
Notifications are POSTs of JSON with the header `X-ANET-Signature` (read lower-cased). The hash is HMAC-SHA512 of the **body** with the **Signature Key**. The page read does not give the header's exact form or whether the key is used as text or as hex bytes. So the adapter accepts the digest with or without a leading `sha512=` and in either letter case, and computes it with the key taken as text **and** (when the key is a hexadecimal string) as the bytes it spells; either match is accepted (both need the secret key). The sandbox run must confirm which one Authorize.Net uses. Compare in constant time; an empty body or missing header is refused.
Body: `{ notificationId, eventType, eventDate, webhookId, payload: { responseCode, merchantReferenceId, authCode, avsResponse, authAmount, entityName, id } }`; for payments `entityName` is `transaction` and `id` is the transId. `notificationId` is unique per notification. Delivery: answer 200 at once; on failure up to 10 attempts (three at three-minute intervals, three at eight-hour intervals, four at 48-hour intervals), after which the webhook is set inactive. So no five-minute window is applied (a retry is hours old by design). Webhooks are created in the Merchant Interface (Account > Webhooks) or with the Webhooks REST API at `/rest/v1/webhooks` (HTTP Basic with the Login ID and Transaction Key); a Signature Key must exist first. The webhook URL may contain only letters, numbers, dot, hyphen, underscore and forward slash.
Events used: `net.authorize.payment.authorization.created` -> payment.authorized; `net.authorize.payment.authcapture.created`, `net.authorize.payment.capture.created`, `net.authorize.payment.priorAuthCapture.created` -> payment.captured; `net.authorize.payment.refund.created` -> payment.refunded; `net.authorize.payment.void.created` -> payment.voided; `net.authorize.payment.fraud.approved` -> payment.authorized; `net.authorize.payment.fraud.declined` -> payment.failed; `net.authorize.payment.fraud.held` and everything else -> unknown. `processorTransactionId` = `payload.id` for a transaction payload. A refund's webhook carries the refund's own transId, which the platform does not know, so it is applied by asking the processor (the core always does that). There are no dispute events in the webhook list read.

## 10. Idempotency
**There is no idempotency key.** The documented protections are: the duplicate transaction check (the same data within two minutes gives reason code 11, or 318 from the processor; the `duplicateWindow` setting can widen it up to 28800 seconds) and `refId`. The adapter leaves the default window (a longer window would also reject a payer's legitimate second attempt with the same amount and card) and sends `refId` = the first 20 hexadecimal characters of the SHA-256 of the core's key (the core's key is unique per step, and the value is echoed in responses and in webhooks as `merchantReferenceId`). Consequence: if a request times out after Authorize.Net accepted it, an immediate retry is answered with the duplicate error, which the adapter reports as a failed payment (reason `11`), while the first authorization may exist; it expires after 30 days if never captured and is visible in the Merchant Interface. Known limit recorded for the handoff.

## 12. Limits and capabilities
`supportsAuthCapture` true; `supportsThreeDS` false (section 6); `supportsRefund` true (settled transactions only; before settlement a full refund is done as a void); `supportsPartialRefund` true (after settlement); `supportsRecurring` false; `supportsPayout` false; `isMerchantOfRecord` false; one mode `accept_hosted`; currencies `USD` (the merchant account's currency is used; no `currencyCode` is sent). A capture may be for less than the authorized amount, but only once. The merchant needs the card, AVS and card code filters configured in the Merchant Interface for the platform's rules to see mismatches.

## 12a. Content security policy
The pages read name only the script hosts `https://jstest.authorize.net` and `https://js.authorize.net`. They do not list the host of the lightbox frame or of the tokenization request. `PROCESSOR_ORIGINS.authorizenet` therefore carries those two hosts and `https://*.authorize.net` (the same registrable domain as the named hosts). The exact origins are an open question (section 13).

## 13. Open questions
None that block the adapter. Sandbox-only confirmations (listed in `authorizenet.verify.md`): the exact form of the `X-ANET-Signature` value and which form of the key is used; whether the JSON answer starts with a byte order mark (the adapter strips one if present); the exact JSON field names of `errors` and `messages` inside `transactionResponse` (arrays of objects as in the reference sample); that a response reason code 4 means "pick up card" for a `responseCode` 2; the origins of the AcceptUI lightbox for the payment page policy; and whether `getTransactionDetails` returns the last four digits of the card in `payment.creditCard.cardNumber` (the refund needs them).
