## 2. Authentication and credential fields
GraphQL requests use HTTP Basic: `Authorization: Basic base64(publicKey:privateKey)` (an API key pair from the Control Panel). Every request also sends `Braintree-Version: <YYYY-MM-DD>` (required; the docs recommend the date the integration started) and `Content-Type: application/json`. Credential fields (names only): `publicKey` (not secret), `privateKey` (secret), `merchantAccountId` (not secret, optional: the merchant account that fixes the currency; the default merchant account is used when empty). The merchant id is not needed for GraphQL calls. Browser calls never use the private key: the server creates a **client token** (`createClientToken`) and the browser SDK uses it.

## 3. Environments
GraphQL endpoint (single POST URL for queries and mutations): sandbox `https://payments.sandbox.braintree-api.com/graphql`, production `https://payments.braintree-api.com/graphql`. Sandbox is a separate account with its own keys (https://www.braintreepayments.com/sandbox). Browser SDK scripts (version named on the pages read: 3.146.0): `https://js.braintreegateway.com/web/3.146.0/js/client.min.js`, `hosted-fields.min.js`, `three-d-secure.min.js`; the client token carries the environment.

## 4. Secure form
Hosted Fields (iframes for the card number, expiration date and security code; the postal code can be a hosted field or passed as `billingAddress.postalCode` in the tokenize call, and the hosted field value wins when both exist). Steps: `braintree.client.create({ authorization: clientToken })`, `braintree.hostedFields.create({ client, fields, styles })`, `hostedFields.tokenize({ billingAddress: { postalCode } })` returns `{ nonce, details: { bin, cardType, lastFour, expirationMonth, expirationYear } }`. The nonce is a single-use payment method; in the GraphQL API it is the **id of a single-use PaymentMethod** (`paymentMethodId`). It is consumed by the first charge or vault call. With 3D Secure the nonce is upgraded in the browser (section 6). Our payment token = the (upgraded) nonce.

## 5. Operations (GraphQL)
Always HTTP 200; the body has `data`, `errors` and `extensions.requestId`. A recommended client timeout is 60 seconds. `errors[].extensions.errorClass` is one of AUTHENTICATION, AUTHORIZATION, INTERNAL, UNSUPPORTED_CLIENT, NOT_FOUND, NOT_IMPLEMENTED, RESOURCE_LIMIT, SERVICE_AVAILABILITY, VALIDATION; `legacyCode` identifies the validation error. Braintree returns data unencoded, so everything read from it is treated as untrusted text.
- Client token: `mutation { createClientToken(input: { clientToken: { merchantAccountId } }) { clientToken } }` (input optional).
- Authorize: `authorizePaymentMethod(input: { apiRequestKey, paymentMethodId, transaction: { amount, orderId, merchantAccountId, riskData: { customerIp, customerBrowser, deviceData } } })` -> `transaction { id legacyId status amount { value currencyCode } orderId paymentMethodSnapshot statusHistory }`. `amount` is decimal text ("11.23"). A processor decline or gateway rejection is **not** an error entry: the transaction comes back with status `PROCESSOR_DECLINED`, `GATEWAY_REJECTED` or `FAILED` and the reason sits in `statusHistory`.
- Capture: `captureTransaction(input: { apiRequestKey, transactionId, transaction: { amount } })`; result `SUBMITTED_FOR_SETTLEMENT`. A partial amount can be captured; more than the authorization cannot.
- Void: `voidTransaction(input: { apiRequestKey, transactionId })` -> `transaction { id status }` (the schema reference lists only `transaction` and `clientMutationId` on the payload; the guide page shows an `errors` list with codes such as `TRANSACTION_CANNOT_BE_VOIDED`, which the reference does not define, so the adapter does not select it and reads failures from the standard `errors` array). A void is possible while the status is AUTHORIZED or SUBMITTED_FOR_SETTLEMENT.
- Refund: `refundTransaction(input: { apiRequestKey, transactionId, refund: { amount, orderId } })` -> `refund { id status amount { value } refundedTransaction { id } }`. Allowed only when the transaction is `SETTLING` or `SETTLED` and not fully refunded; partial refunds are allowed. `reverseTransaction` voids or fully refunds depending on the state. Before settlement a refund is refused, so a full refund of a payment still `SUBMITTED_FOR_SETTLEMENT` is done as a void; a partial refund at that time is refused with a clear message (settlement happens nightly).
- Look up: `node(id: "<transaction id>") { ... on Transaction { ... } }`.
- Connection test: `query { ping }` answers `pong` (proves the format and the host, and with the keys the 401 check), then `createClientToken` proves the keys work.
- Ids: GraphQL ids are Base64 text; the guides' sample `dHJhbnNhY3Rpb25fazZqdHZ4NWM` decodes to `transaction_k6jtvx5c`, so a legacy id (used by webhooks) maps to the GraphQL id as Base64 of `transaction_<legacyId>` (shown without padding in that sample). Our `processorTransactionId` is the GraphQL transaction id.
- Authorization lifetime before it expires: Visa 8 days (3 days for merchant-initiated recurring or unscheduled), Mastercard 30 days preauthorization or 7 days final, American Express 7 days, Discover/Diners/UnionPay/JCB 30 days. Expired status: `AUTHORIZATION_EXPIRED`.

## 6. 3D Secure
3D Secure runs in the browser: after `tokenize`, `braintree.threeDSecure.create({ version: 2, client })` and `threeDSecure.verifyCard({ amount, nonce, bin, email?, billingAddress?, onLookupComplete(data, next) { next(); } })`. The callback `onLookupComplete` is required. The result `payload.nonce` is a **new nonce** (the first was consumed) and is the one the server charges; `payload.threeDSecureInfo` is for convenience only: the SDK states that only values looked up on the server may decide how to process the transaction. The server reads the outcome from the transaction's `paymentMethodSnapshot ... creditCard.threeDSecure.authentication`: `authenticationStatus` (enum, e.g. `AUTHENTICATE_SUCCESSFUL`, `AUTHENTICATE_ATTEMPT_SUCCESSFUL`, `AUTHENTICATE_FAILED`, `AUTHENTICATE_UNABLE_TO_AUTHENTICATE`, `LOOKUP_NOT_ENROLLED`, `LOOKUP_ERROR`, `CHALLENGE_REQUIRED`), `liabilityShifted`, `liabilityShiftPossible`, `cardEnrolled`, `version`, `eciFlag`. Braintree states that `authenticate_successful` and `authenticate_attempt_successful` shift chargeback liability. 3D Secure must be enabled on the account by Braintree (merchants outside the EEA are not enrolled automatically; American Express SafeKey needs a separate request). Fields and the 3DS information are lost if a 3D-Secured nonce is vaulted without verification (not relevant: we never vault).
Our reading: `requested` = an authentication object with a status exists; `completed` = the status is a terminal outcome (not `CHALLENGE_REQUIRED`, not empty); `authenticated` = `AUTHENTICATE_SUCCESSFUL`; `liabilityShift` = `liabilityShifted`. The attempt outcome (`AUTHENTICATE_ATTEMPT_SUCCESSFUL`) gives a liability shift but is not a full authentication, so it is `completed` with `authenticated` false. The gateway rejection reason `THREE_D_SECURE` maps to `three_ds_failed`; processor code 2099 "Cardholder Authentication Required" also maps to `three_ds_failed`.

## 7. Card identity (REQ-CARD)
`CreditCardDetails.uniqueNumberIdentifier` "uniquely represents any credit card number, for cards stored in a merchant's vault" and is returned only when `origin` is null; the page does not say it exists for a one-time (not vaulted) card. The adapter uses it when present (type `fingerprint`, value `uid:<identifier>`) and otherwise builds `bin|last4|expiry|brand` from the snapshot (`bin`, `last4`, `expirationMonth`, `expirationYear`, `brandCode`). We never vault, so the fallback is the normal case until the sandbox run shows otherwise. Known limit of the fallback: two different cards with the same BIN, last four, expiry and brand would share an identity (rare; errs toward counting more).

## 8. Decline mapping
Source: `statusHistory[].processorResponse.legacyCode` (the processor response code table of 2000 to 3000, read in full: 2000 Do Not Honor, 2001 Insufficient Funds, 2004 Expired Card, 2005 Invalid Credit Card Number, 2006 Invalid Expiration Date, 2010 Card Issuer Declined CVV, 2012/2013/2014/2047/2053 lost, stolen, fraud or pick up, 2099 Cardholder Authentication Required, and 2109-2999 generic processor decline), plus the gateway rejection reason and the decline type. Mapping used:
- insufficient_funds: `2001`, `2002`, `2003`
- invalid_number: `2005`, `2007`, `2008`, `2009`, `2051`, `2108`
- invalid_expiry: `2004`, `2006`
- invalid_cvv: `2010`; gateway rejection reasons `CVV`, `AVS_AND_CVV`
- three_ds_failed: `2099`, `2058`; gateway rejection reason `THREE_D_SECURE`
- processor_fraud_signal: `2012`, `2013`, `2014`, `2021`, `2047`, `2053`; gateway rejection reasons `FRAUD`, `RISK_THRESHOLD`, `PAYMENT_METHOD_BLOCKED`
- do_not_honor: `2000`, `2038`, `2046`, `2015`, `2019`, `2020`, `2041`, `2043`, `2044`, `2057`, `2104`, and the generic range `2109` to `2999`
- processor_error: `2025`, `2026`, `2034`, `2105`, `2106`, `3000`, plus a `FAILED` transaction status and gateway rejection reasons `APPLICATION_INCOMPLETE`, `TOO_MANY_CONFIRMATION_ATTEMPTS`
- everything else (including `DUPLICATE`, `AVS`, `EXCESSIVE_RETRY`, `UNION_PAY_ENROLLMENT_REQUIRED`, and set-up errors): other.
AVS: `processorResponse.avsPostalCodeResponse` of `AvsCvvResponseCode` (BYPASS, DOES_NOT_MATCH, ISSUER_DOES_NOT_PARTICIPATE, MATCHES, NOT_APPLICABLE, NOT_PROVIDED, NOT_VERIFIED, SYSTEM_ERROR): `MATCHES` is a match, `DOES_NOT_MATCH` a mismatch, anything else unknown. AVS and CVV rules that reject are configured in the Control Panel and appear as `GATEWAY_REJECTED` with reason `AVS`, `CVV` or `AVS_AND_CVV`. The `declineType` (`SOFT` or `HARD`) is kept in the raw code text for support, not used for the category.

## 9. Webhooks
Braintree posts `application/x-www-form-urlencoded` with two parameters, `bt_signature` and `bt_payload`. The payload is Base64 text (only `A-Za-z0-9+=/` and newlines) of an XML document: `<notification><timestamp>...</timestamp><kind>...</kind><subject>...</subject></notification>`. **Verification** (from the SDK source): the signature value is a list of `publicKey|signature` pairs joined by `&`; take the pair whose key equals our public key; the signature is the hex of HMAC-SHA1 with the key `SHA1(privateKey)` (binary digest) over the payload text, tried both as received and with a trailing newline appended; compare in constant time. There is no timestamp in the signed data other than the one inside the payload, and Braintree resends a failed delivery every hour for up to 3 hours in sandbox and up to 24 hours in production, so the platform does **not** apply a five-minute window here (retries are hours old by design); replay protection is the unique event id. The listener must answer 2xx within 30 seconds. **Destination check** (from the SDK's `verify` method; the pages read do not describe it): when a webhook URL is created, Braintree sends `GET <url>?bt_challenge=<20 to 32 hex characters>` and expects `<public key>|<HMAC-SHA1 of the challenge>` (same key as above). The helper `braintreeChallengeResponse` exists; wiring a `GET` handler needs a hook in the STEP 10 route (recorded as request R1 in `docs/steps/STEP-11/DEPENDENCY_REQUESTS.md`). Notifications may arrive out of order, so the timestamp in the payload is used for ordering.
Events used: dispute kinds `dispute_opened` -> dispute.opened; `dispute_under_review`, `dispute_disputed` -> dispute.updated; `dispute_won`, `dispute_lost`, `dispute_accepted`, `dispute_auto_accepted`, `dispute_expired` -> dispute.closed; transaction kinds `transaction_settled` -> payment.captured and `transaction_settlement_declined` -> payment.failed (these two exist only for ACH and SEPA direct debit, so they do not fire for cards). Everything else -> unknown. There is **no** webhook for card authorization, capture, void or refund results: those results are returned by the API calls themselves, and later changes (settlement, authorization expiry) are read with the transaction lookup. The dispute notification carries the disputed transaction (`subject/dispute/transaction/id`, a legacy id), converted to the GraphQL id (section 5), so dispute events reach the core with a transaction id. The notification has no unique id of its own on the pages read, so the event id is `bt_` plus the SHA-256 of the payload text (a retry carries the same payload).

## 10. Idempotency
`apiRequestKey` on authorize, capture, void, refund and reverse. A second request with the same key and the same input returns the same transaction in its current status; a different input, or a request while the first is in flight, is a VALIDATION error; the key is remembered for 30 days; a request that fails with AUTHENTICATION, AUTHORIZATION, NOT_FOUND, RESOURCE_LIMIT or NOT_IMPLEMENTED does not use up the key. The core's keys are sent as they are (they are within the 255 character limit of the field the page names for `clientMutationId`; the `apiRequestKey` page gives no length limit).

## 12. Limits and capabilities
`supportsAuthCapture` true; `supportsThreeDS` true; `supportsRefund` true; `supportsPartialRefund` true (after settling starts); `supportsRecurring` false; `supportsPayout` false; `isMerchantOfRecord` false; one mode `hosted_fields`; currencies `USD` (the merchant account fixes the currency; the account must be a USD merchant account). `AUTH_VALIDITY_HOURS_BY_PROCESSOR.braintree = 72` (the shortest period in the table for customer-initiated card payments is 7 days for American Express and for Mastercard final authorizations, so 72 hours is safely inside every brand). Settlement happens nightly after capture; a refund is possible only from `SETTLING`. Device data (Kount) is not collected in this release: the Advanced Fraud Tools need `deviceData` from a data collector component, which is outside this adapter; the Control Panel basic rules (AVS, CVV, duplicate, risk threshold) work without it.

## 12a. Content security policy
The pages read name these hosts: the SDK scripts at `https://js.braintreegateway.com` and the GraphQL host `https://payments.braintree-api.com` (sandbox `https://payments.sandbox.braintree-api.com`). The pages read do not list the hosts of the Hosted Fields frames or of the 3D Secure challenge (the 3DS configuration returns the Cardinal script address at run time), so `PROCESSOR_ORIGINS.braintree` carries `https://js.braintreegateway.com`, `https://*.braintreegateway.com` (frames and assets of the same registrable domain as the script host) and `https://*.braintree-api.com`. The Cardinal 3DS origins are an open question (section 13).

## 13. Open questions
None that block the adapter. Sandbox-only confirmations (listed in `braintree.verify.md`): whether the transaction id is returned with or without Base64 padding (the webhook id conversion relies on it); whether `uniqueNumberIdentifier` is returned for a one-time card (the fallback identity covers both); the exact field names of the AVS response inside `statusHistory` for a hosted-fields nonce; that `Braintree-Version` with today's date is accepted; the dispute notification XML element names (`subject/dispute/transaction/id`); the origins of the 3D Secure challenge (Cardinal) that the payment page policy must allow.
