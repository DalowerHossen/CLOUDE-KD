## 2. Authentication and credential fields
Server calls: `Authorization: Bearer <access token>`, `Square-Version: <YYYY-MM-DD>` (the latest version in the change log read is `2026-09-16`) and `Content-Type: application/json`. The token of the other environment is refused with `UNAUTHORIZED`. Credential fields (names only): `applicationId` (not secret; the Web Payments SDK needs it), `locationId` (not secret; the location that receives the payments, which must be the same in the browser and in every payment request), `accessToken` (secret; a seller access token or a personal token for the seller's own account), `webhookSignatureKey` (secret; the signature key of the webhook subscription), `webhookUrl` (not secret; the exact notification URL of that subscription, because it is part of the signature). Money is never sent as a decimal: Square takes the smallest unit (cents) as an integer.

## 4. Secure form
Web Payments SDK card element: `window.Square.payments(applicationId, locationId)`, `payments.card()`, `card.attach(element)` renders Square's own hosted frame with number, expiry, security code and postal code (USD needs a postal code). `card.tokenize(verificationDetails)` returns `{ status: 'OK', token }` or `{ status, errors }`. `verificationDetails` = `{ amount: '10.00', currencyCode: 'USD', intent: 'CHARGE', customerInitiated: true, sellerKeyedIn: false, billingContact: { givenName, familyName, email, ... } }`; Square runs its risk check and, when a mandate or the seller's Risk Manager rule asks for it, shows the 3D Secure challenge inline, then returns a **single payment token** (the newer flow that replaces `verifyBuyer` and the separate verification token). Our payment token = this single-use token (the `source_id` of CreatePayment). The amount shown in the SDK is only for authentication; the server fixes the real amount.

## 5. Operations (REST, JSON)
- Authorize: `POST /v2/payments` with `source_id` (the token), `idempotency_key`, `amount_money: { amount, currency: "USD" }`, `autocomplete: false`, `location_id`, `reference_id` (invoice id, text), `customer_details: { customer_initiated: true, seller_keyed_in: false }`, `delay_duration` and `delay_action: "CANCEL"`. The answer `{ payment }` has `status` `APPROVED` (authorized, held) or `FAILED`; a refusal is an HTTP 4xx answer with `errors` (`category`, `code`, `detail`, `field`).
- Capture: `POST /v2/payments/{payment_id}/complete` (optional `version_token`); no amount field, so the **full** authorized amount is captured; result `COMPLETED`. A partial capture is not possible.
- Void: `POST /v2/payments/{payment_id}/cancel`; result `CANCELED`.
- Refund: `POST /v2/refunds` with `idempotency_key` (**at most 45 characters**), `payment_id`, `amount_money`, `reason`; only for `COMPLETED` payments (an `APPROVED` card payment is cancelled, not refunded: `REFUND_ERROR_PAYMENT_NEEDS_COMPLETION`); at most 20 refunds per payment, at most 1 year old; partial refunds allowed; the payment stays `COMPLETED` and `refunded_money` grows. The `refund` answer has `status` `PENDING` (usually hours, at most 14 days for cards), `COMPLETED`, `REJECTED` or `FAILED`.
- Look up: `GET /v2/payments/{payment_id}`; refund: `GET /v2/refunds/{refund_id}`.
- Our `processorTransactionId` is the **payment id**; a refund result carries the refund id.
- Connection test: `GET /v2/locations/{location_id}` -> `location.status` `ACTIVE` and `capabilities` containing `CREDIT_CARD_PROCESSING`, `currency` `USD`.
- Authorization lifetime: card-not-present payments are cancelled automatically after **7 days** by default (`delay_duration` `PT168H`, `delay_action` `CANCEL`); the value can be 1 minute up to less than the default. The adapter sets `PT144H` (6 days) so the platform hold is always inside the processor hold. (36 hours applies to card-present payments only.)

## 6. 3D Secure
Authentication happens inside `card.tokenize` (section 4); Square decides by mandate (UK/EEA, Japan) or by the seller's Risk Manager rule. The server must say who started the payment: `customer_details.customer_initiated: true` for a payer-present payment. In a mandated market a payment without authentication is declined with `CARD_DECLINED_VERIFICATION_REQUIRED`. **The Payment object has no field that reports whether 3DS ran or its result** (searched in the OpenAPI schema: the only mentions are the verification token fields, which the new flow no longer uses). So the adapter cannot prove authentication: it declares `supportsThreeDS: false`, the platform then asks for `disabled` 3DS policy, every result is `{ requested: false, completed: false, authenticated: false, liabilityShift: null }`, and a decline `CARD_DECLINED_VERIFICATION_REQUIRED` maps to `three_ds_failed`. Liability shift is stated by Square for successfully authenticated Mastercard, American Express, JCB, Visa, Diners Club and Discover payments. Known limit recorded for the handoff.

## 7. Card identity (REQ-CARD)
`payment.card_details.card.fingerprint` ("Square-assigned identifier, based on the card number, to identify the card across multiple locations within a single application"; example `sq-1-...`) -> `{ type: 'fingerprint', value }`. When it is absent the adapter builds `bin|last_4|exp_month/exp_year|card_brand` from the same object (`bin` is returned only by the Payments API).

## 8. Decline mapping
Source: `errors[].code` (164 codes read from the schema). Mapping used:
- insufficient_funds: `INSUFFICIENT_FUNDS`
- invalid_number: `INVALID_CARD`, `INVALID_ACCOUNT`, `INVALID_CARD_DATA`, `UNSUPPORTED_CARD_BRAND`
- invalid_expiry: `CARD_EXPIRED`, `INVALID_EXPIRATION`, `INVALID_EXPIRATION_YEAR`, `INVALID_EXPIRATION_DATE`, `EXPIRATION_FAILURE`, `BAD_EXPIRATION`
- invalid_cvv: `CVV_FAILURE`, `VERIFY_CVV_FAILURE`
- three_ds_failed: `CARD_DECLINED_VERIFICATION_REQUIRED`
- do_not_honor: `CARD_DECLINED`, `GENERIC_DECLINE`, `CARD_DECLINED_CALL_ISSUER`, `TRANSACTION_LIMIT`, `CARDHOLDER_INSUFFICIENT_PERMISSIONS`, `PAYMENT_LIMIT_EXCEEDED`
- processor_error: `INTERNAL_SERVER_ERROR`, `SERVICE_UNAVAILABLE`, `GATEWAY_TIMEOUT`, `BAD_GATEWAY`, `REQUEST_TIMEOUT`, `RATE_LIMITED`
- everything else (including `ADDRESS_VERIFICATION_FAILURE`, `VERIFY_AVS_FAILURE`, `INVALID_POSTAL_CODE`, `CARD_TOKEN_USED`, `CARD_TOKEN_EXPIRED`, `CARD_NOT_SUPPORTED`, `AMOUNT_TOO_HIGH`, `AMOUNT_TOO_LOW`, `IDEMPOTENCY_KEY_REUSED`, request errors): other.
Error categories: `PAYMENT_METHOD_ERROR` and `INVALID_REQUEST_ERROR` are normal payment failures; `AUTHENTICATION_ERROR` (bad token, `ACCESS_TOKEN_EXPIRED`, `ACCESS_TOKEN_REVOKED`, `INSUFFICIENT_SCOPES`) throws a validation error naming the credentials; `API_ERROR` and `RATE_LIMIT_ERROR` and HTTP 5xx or 429 throw (retry with the same idempotency key is safe). AVS: `card_details.avs_status` `AVS_ACCEPTED` -> postal match true, `AVS_REJECTED` -> false, `AVS_NOT_CHECKED` -> unknown. (Square's AVS covers the postal code the payer typed in Square's own form.)

## 9. Webhooks
Header `x-square-hmacsha256-signature` (read lower-cased). Signature = Base64 of HMAC-SHA-256 with the subscription's **signature key** over the **notification URL immediately followed by the raw request body** (from Square's SDK helper; the docs state the three inputs: key, notification URL, raw body); compare in constant time; refuse an empty body. Body: `{ merchant_id, type, event_id, created_at, data: { type, id, object: { ... } } }`; `event_id` is unique and repeated for a resend (use it to skip duplicates). Delivery: answer 2xx at once (10 seconds before a duplicate is sent); retries with growing delay for **up to 24 hours** (1, 2, 4, 8, 16, 32, 60 minutes, 2 hours, ...); no ordering guarantee; a subscription with no 2xx for three weeks is disabled. So no five-minute window is applied (retries are hours old by design); `created_at` is kept for ordering. Source addresses: production 54.245.1.154, 34.202.99.168; sandbox 54.212.177.79, 107.20.218.8 (informational; not used for trust).
Events used (subscribe to these in the Developer Console): `payment.created`, `payment.updated` -> by `payment.status`: `APPROVED` payment.authorized, `COMPLETED` payment.captured, `CANCELED` payment.voided, `FAILED` payment.failed, others unknown; `refund.created`, `refund.updated` -> payment.refunded when `refund.status` is `COMPLETED`, otherwise unknown (the refund status stays in the payload); `dispute.created` -> dispute.opened; `dispute.state.updated` -> dispute.closed when `dispute.state` is `WON`, `LOST` or `ACCEPTED`, otherwise dispute.updated; `dispute.evidence.created`, `dispute.evidence.deleted` -> dispute.updated. `processorTransactionId` = `data.object.payment.id` for payments, `refund.payment_id` for refunds, `dispute.disputed_payment.payment_id` for disputes (so disputes reach the core with a payment id).

## 10. Idempotency
`idempotency_key` in the body of CreatePayment and RefundPayment (refund limit 45 characters; the CreatePayment text names no limit but the same scheme is used). A repeated key with the same request returns the first response; the same key with another request is `IDEMPOTENCY_KEY_REUSED`. The core's keys (`<paymentId>:authorize` is 46 characters) can exceed 45, so the adapter sends the first 40 hexadecimal characters of the SHA-256 of the core's key: deterministic, so a retry sends the same value. CompletePayment and CancelPayment take no key; both are safe to repeat (a second call answers `DELAYED_TRANSACTION_CAPTURED` / `DELAYED_TRANSACTION_CANCELED`, which the adapter reads as success after checking the payment status).

## 12. Limits and capabilities
